# RectoPDF specification

Started 2026-11-06. Research and reasons are in `docs/research/`, concepts in `docs/concepts/`, the sign-off summary in
`docs/SIGNOFF.md`. **[DECIDE]** marks a question only the owner can answer. Items marked *default* follow a recommendation the owner
hasn't answered yet: "Lets start the build out" was taken as a go on those, and they can be overruled.

## 1. Product

A PDF reader for the Mac (Windows later) that stays fast and small however many large PDFs are open, offers the tools people
usually pay for, and lets an agent search a document instead of receiving all of it. App: **RectoPDF**. CLI: `recto`.

**Must be excellent:**
1. Memory and speed with many large PDFs open.
2. A calm screen with the maximum vertical reading space.
3. An agent that requests what it needs.
4. Saving that never damages a file or a signature.

**Never:** claim a signature is "valid" without checking it; leave content recoverable after claiming to remove it; send anything
off the machine unasked (the daily update check is the one standing exception, decision 24); change the user's file without an explicit save.

## 2. Performance budgets

A missed budget is a bug. The whole process tree counts, on release builds, on an M4-class Mac. Details in the platform report, §4.

## 3. Architecture

**Rust decides, the host draws.** A native AppKit host (no SwiftUI in the main window) over a Rust core through UniFFI. WinUI 3 later.
*Rejected:* Rust GPU toolkits (a Metal swapchain adds 105–184 MiB and loses native accessibility and IME); Tauri and Electron (a blank
webview is 56.7 MiB across four processes); PDFKit as the viewer (3–5 s main-thread stall at 10k pages, and it damages forms on save).

**Three tab tiers:** *Cold* is a record with no handle. *Warm* adds its contents and page table. *Hot* is the visible tab. Promotion is
fast because everything is rebuilt from disk.

**Two engines, one writer.**
- **PDFium without V8 or XFA** draws pages and supplies selection, search text and highlight positions. It runs in a sandboxed,
  killable worker behind a `RenderBackend` seam. Measured in `docs/research/2026-11-06-renderer-spike.md`: text and vector pages at 2x
  are p50 2.06 ms, p95 8.64 ms. Cancelling isn't always prompt and one hostile file reached 4 GiB, so the worker gets a **hard memory
  limit, a per-page deadline with kill, and retirement at 64 MiB** (amends the benchmark's rule). Built in `recto-render-service`: details in `docs/ENGINEERING.md`. **Not sandboxed yet; shipping without the sandbox is a release blocker.**
- **Memory limit sequence** (owner approved, 2026-11-06): 512 MiB per worker; a page that hits it retries alone with up to 1 GiB if the Mac has memory free; failing that, a lower-resolution version that says so, so a page is never blank. A page that fails all the way down isn't retried, and one heavy worker runs at a time. Exports and printing draw in tiles under the same limits. **An on-screen page never waits and may show low resolution; an export waits for the heavy slot and never saves a low-resolution file** (owner, 2026-11-07).
  *Rejected:* MuPDF (AGPL), poppler (GPL). hayro stays the challenger: as fast, pure Rust, but no cancel call and it reached 843 MiB where PDFium peaks at 113.
- **Visible regions are drawn in one pass** (owner, 2026-11-06: "4s to render a map is too slow. We can do better"). Tiles stay the cache unit, but a separate render call per tile cost 46–55 ms each on a heavy map, so 72 tiles took 3.7 s against 0.7 s for one pass.
- **Search text needs a normaliser.** PDFium returns line-end hyphens as U+FFFE, plus NBSP and CRLF, which defeat plain `rg`.
- **PDFium returns hidden text** (14 of 17 techniques, and real files contain it), so hidden text is flagged for the agent as untrusted, never dropped silently, because an OCR layer is invisible too.
- **The lopdf fork's `IndexedReader`** owns file structure with no renderer running. Its append-only writer is the only code that
  writes files. *Rejected:* upstream lopdf, which has no indexed reader; PDFium's writer, which would be a second writer.
- **Agreement gate:** when the two parsers disagree about a file, it stays readable but saving and signing turn off.

**distillPDF was parked** (owner, 2026-11-06) and is back in work for the agent's text (owner, 2026-11-07: "Spin up agents to do the distillpdf work, they need to test to ensure no regressions"). RectoPDF uses it only in the `recto-headings` helper, for generated contents, built as a workspace of its own so its lopdf features never reach the app. Find and highlights stay on PDFium, because they must line up with the page on screen.

**Pages reach the screen** as `CALayer`s holding IOSurface tiles, 512 px, zero copy, off-screen tiles purgeable. The host makes each surface and a worker draws in it, sent over a Mach port it was given at spawn. See `docs/ENGINEERING.md`, "The app".

## 4. Screen design

Reference: `docs/concepts/`. Rules from the owner:

- **No top bar.** Maximum vertical reading space; nothing sits above or over a page.
- **Tabs live in the sidebar.** Tapping the active PDF folds or opens its contents.
- **A PDF's contents have a maximum height and scroll inside it** (owner, 2026-11-07: "The left sidebar toc should have a max height within scroll so it doesn't push everything of screen"). The other tabs and the sidebar's footer stay on screen however long the contents are, and the contents follow your place on their own, smoothly (owner, 2026-11-07: "The toc should auto scroll to where you are in the document (smoothly so you don't notice it in a elegant way)"). They have a dead zone and move in separate repositions (owner, 2026-11-07: "It can whoosh with smooth acceleration at both ends. It can have a \"dead-zone\" so it doesn't react to small scrolls within the window, so basically it repositions, stays still (while user is reading slowly scrolling) then repositions after the user is scrolling a bit."). If you scroll the contents yourself, they stay where you put them until you've stopped using them and your section changes. **The contents take at most about 60% of the sidebar's height,** and a shorter outline only what it needs (owner, 2026-11-07: "The max height of toc does not seem to be working", then "yes" to a true maximum of about 60%). The other tabs share what's left, and a long tab list scrolls by itself in it.
- **Hovering over a shortened name shows it in full, at once and in the row's own colour,** for tabs and contents entries alike (owner, 2026-11-07: "Hovering over the file name in the sidebar reveals the full name right?", then "The hover delay before showing the full toc name makes in not intuitive, and the expanded name should have the color of the title").
- **A contents section with sections under it folds from a chevron on the left of its name** (owner, 2026-11-07: "there should be a collapse toggle button for sections with sub chapters on the left side of the headers"). The chevron comes with the pointer, and what's folded comes back with the session.
- **The sidebar's scroll thumb is always shown, slim, with no track** (owner, 2026-11-07: "The sidebar thumb should always be visible, and lets hide the rail", "the thumb should be thinner", and for both scrollers "the scroll thumb always visible, the rail always hidden"), whatever the system's setting, only when there's something to scroll, and over the margin rather than taking width. Text from a file is shown cleaned, and never as a command.
- **A file's own contents are never altered; a bad or missing one gets a generated alternative on offer** (owner, 2026-11-07: "dont modify the bad toc, but offer a generated toc using distillpdf"). Generated contents come from distillPDF's detected headings, built only when asked for, in a killable helper with a memory limit, and always labelled as generated. The file's own entries stay one tap away. At rest it's one quiet line over the contents, which stays put while they scroll: *Generate contents* for a file whose own are missing or look bad, then *Generated contents* over the list, with what that means on hover. A heading whose text has no ink under it never appears. "Look bad" is Rust's rule (`recto_core::verdict`), told from what a warm tab already has, and an agent sees it as `verdict` in `recto contents`.
- **At rest the sidebar is only names and contents.** The rail fills as you read. Chevron and page numbers appear on hover.
- **The macOS menu bar is the home of every command** (owner, 2026-11-06: "Not all options need to be in the sidebar. A lot can be in the macos top bar instead"). Menus: File, Edit, View, Go, Pages, Mark Up, Tools, Window, Help. Map: `docs/concepts/menumap-light.png`. Rust decides which items exist and which are enabled. ⌘K finds any command.
- **The `⋯` panel holds only what you touch while reading** (owner: "let the … menu toggle open a compact menu in lower part of left sidebar with tabs", and 2026-11-07: "I cant see the settings menu", then "yes" to having it now). At rest only the `⋯` shows. For now it opens with Rotate and paper colour (white, warm, dark), with no placeholders for what doesn't exist yet. **The panel is for tools** (owner, 2026-11-07: "The sidebar menu is more for tools, like edit mode etc. When not in edit mode rotate page will rotate all pages together (it still enables save to commit the adjustment). Usefull when there is a scan issue or similar, for a quick fix."): outside edit mode, *Rotate left* and *Rotate right* turn every page together, as one unsaved edit that one Undo takes back, with the red window button's dot showing it's unsaved; in edit mode they turn the page being read. Turned pages are drawn turned: the page's layer is turned on the screen, and what was drawn of a page is kept, as a turn changes nothing of its pixels. Turning every page a quarter changes their shape and so the fit, so what shows is drawn at the new scale, and turning back draws nothing new. Edit has Undo and Redo on ⌘Z and ⇧⌘Z, and `recto page rotate all --by 90` is the same for an agent. Later it gets two tabs, View (zoom, paper, layout) and Mark up, plus an **Edit PDF** button. A tool started from the menu bar that needs choices, such as Compress, opens here, in place of the tabs.
- **Editing tools show in the sidebar only in edit mode** (owner, 2026-11-06: "These are tools in the sidebar only visible when in edit mode"). The panel changes to the edit tools when you enter with ⌘E, the Pages menu or Edit PDF, and Done returns to reading. In the Pages menu, Rust enables those items only in edit mode.
- **Saving looks and works like a native Mac app** (owner, 2026-11-06: "I want something that looks more like a native save / save as feature. Like word etc"). With unsaved changes, the red window button shows its dot and a Save icon appears beside the window controls. `⌘S` saves, `⇧⌘S` and File > Save As open the system's save sheet, and closing asks Don't Save, Cancel or Save. Tools change the open document (Compress has Apply) and never have their own save buttons.
- **Agent icon at the top right**, in the empty margin: an AI four-point star (owner, 2026-11-07: "The agent logo in the upper right is wrong, it should be a ai 4 point star"). It opens the agent panel and stays in the same spot.
- **Three paper colours: white, warm and dark** (owner, 2026-11-07: "We have two paper color modes: white and dark, let's add a yellowed white option that's better for the eyes"). Any of them works with a light or dark window. Paper colour only changes the screen: exports, snapshots, copied images and saved files stay true. Signing always shows the true page. Dark paper turns text and page over and leaves smaller pictures alone, a little dimmed. **A page that's mostly a picture isn't flipped:** a map or a full-page photo keeps its true colours and is dimmed so it doesn't glare (owner, 2026-11-07, answering "should pages that are mostly a picture be dimmed instead of flipped? I recommend yes": "I agree"). **Each image is judged by its own pixels:** one with a predominantly white background flips with the page and lands on the paper's tone, whatever share of the page it covers: scanned pages, embedded letters, screenshots of documents, charts and diagrams, with no bright box or hard edge (owner, 2026-11-07: "Im seeing an issue: in dark mode scanned pages appear bright white: We need to detect scanned images (with predominently white bg, and flip and match grey tone paper color", and "similar with images with white bg"). A photo or other image without a white background stays as it is on a text page, or dims when it's most of the page. **Text on dark paper keeps its weight,** and the curve that does it is for text and lines only: coloured areas, as a chart's, turn over as before, so they keep their colours (owner, 2026-11-08). One decision per image, kept, so a preview, sharp tiles and low-resolution tiles never disagree. When an image can't be judged, or a page has too many to tell apart, the whole page is judged by its pixels, and anything uncertain is left alone or dimmed and never flipped, as a flipped photo looks like a negative. A photo inside a scan flips with the rest, which is accepted.
- **Selecting text works as it does on a Mac** (owner, 2026-11-07: "And select text should work natively"). Drag selects across lines and pages, two clicks take a word, three a line, shift extends and a click elsewhere clears. ⌘A takes the document, as PDFKit's `selectAll:` does on a Mac, and ⌘C and Edit > Copy copy it, in reading order. **A copy of body text leaves out running heads, footers and page numbers** (owner, 2026-11-07: "When selecting across pages the page number is copied. Both footer and header should be ignored when coppying body text."), across pages and within one, and selecting only a header copies it, over a page break too. `recto text` marks them in `chrome_spans` and leaves its text unchanged (owner, 2026-11-08). An I-beam over text and the system's selection colour on every paper. The highlight is a layer of the page's, not in its tiles or the file. Text is read as the selection reaches a page, and a copy stops at 16 MiB, 100,000 pages or 2 minutes and says where. A selection belongs to what's on screen, so it goes with a change of tab.
- **Right-click a page for its layout** (owner, 2026-11-07: "In the right click menu you can select side by side layout, with and without header page"): *Single Page*, *Side by Side*, and *Side by Side, First Page Alone*, which puts the first page alone on the right as a book's cover is. The same three are in View, ticked as the right-click menu ticks them, and `recto view --layout single|two-up|two-up-cover` sets them. Each tab keeps its own layout, and session restore brings it back. Two pages share the room a single page has up to twice the reading width, line up at the top, and a row is as tall as its taller page. Changing layout keeps the page being read and how far down it, and the zoom; the reader's page is whichever page of a row they went to or were on. Clicks, drags and selection go by the page under the pointer, or the nearer page of its row.
- **A margin above the first page and below the last** (owner, 2026-11-08: "add some margin above the first page, and below the last page"): 24 points, a little over twice the 10-point gap between pages, in every layout. Going to page 1, or opening a tab at its start, shows it.
- **The page number is always in the lower right** (owner, 2026-11-07: "The page number should always be visible in the lower right."), as a small quiet pill in the margin's corner, with the sidebar shown or hidden. It's over a page only when a page fills the width there.
- **The zoom level sits in the top right, just left of the agent icon, in its row** (owner, 2026-11-07: "We dont need detailed zoom options in the left sidebar menu. Zoom is pretty natural to people. Instead lets show the zoom level in upper left and clicking the zoom value enables you to type in zoom level or reset", then 2026-11-08: "The zoom level should be in the upper right of the app (not in the sidebar)"). It's a quiet `125%`, where 100% is the page's real size, as in other Mac apps, in the top right margin the agent icon already has, so nothing new sits over the page. With the agent icon hidden it takes the icon's place, at the same 12-point margin from the edge, and the page's scroller stops below whatever's there. A fitted page keeps 96 points clear to its right, against 56 to its left, so the corner never sits over a page at any window width; with room the page is centred, and in a narrow window it moves left of centre rather than under the corner. Clicking it opens a small field with the number to type over and *Fit* before it; Return applies a level, held to the zoom limits, and Escape or clicking away leaves it. What isn't a level changes nothing. ⌘+, ⌘−, ⌘-scroll, plain + and −, and pinching are as they were. `recto view --zoom 150%` takes a level too.
- **Comparison view** (owner, 2026-11-08: "Ctrl clicking more then one pdf should enable comparison view, right click menu can enable separate scroll (default) and synced scroll. Zoom is always synced."). ⌘-click or ⌃-click a tab in the sidebar to put it side by side with what's showing, and again to take it out; down to one, it's alone. A plain click on a tab, opening a PDF, or going to a tab that isn't side by side returns to one. At most three, the live documents' own number, and a fourth is refused in words. Each pane is its own document in its own place, laid out its own way, and the compared tabs read as active in the sidebar. The pane being read is the one last scrolled or clicked in: the page number, the contents, the layout menu, Copy and Select All are its, and a press in another pane takes the selection there. Right-click has *Separate Scroll*, the default, and *Synced Scroll*, which keeps the panes page for page from where it went on, at the same depth in each page, each waiting at its own end, and says beside the page number when their lengths differ. Zoom is one magnification for every pane, the level in the top right the pane being read's, so with pages of different sizes each is its own fit times that. **Each pane's name is a quiet pill in its lower left corner,** as the page number is in the lower right, the one read in the accent colour: nothing goes above or over the page, and no reading height is spent. Panes share the window's width with a hairline between and narrower margins, and only the pane at the right keeps the top right corner clear. `recto compare --tabs "#1,#2" [--sync on|off]` and `recto compare --off` do the same, and session restore and an update bring back which tabs, synced or not with its starting pages, and each pane's place.
- **The sidebar shows and hides by a button just right of the window's controls** (owner, 2026-11-08: "Actually instead of focus view, simply have a sidebar icon to the right of the traffic light buttons that toggles sidebar on and of. No need mor a separate mode"). There's no focus mode. The button is the Mac's sidebar symbol, quiet, and stays with the sidebar hidden, as it's the way back; View has *Hide Sidebar* and *Show Sidebar* on ⌃⌘S, and `recto view --sidebar on|off` does the same. Hiding it changes nothing else: the page keeps its reading width, and the window's controls stay. A record from a build with focus view on comes back with the sidebar hidden.
- **File > Open Recent** lists the last 20 files opened, newest first, by name, with Clear Menu, as on any Mac, and kept in the state record. ⌘K offers the same list (`AppCore::recent_files`, `AppCore::open_recent`). `recto recent` gives the names, and whole paths from Control; `recto recent clear` empties it.
- **A file moved, replaced or deleted while it's open or asleep is said plainly, and nothing of the old file is shown as the new.** When the app comes back to the front, each file showing is looked at, as a tab is when it's shown and when it wakes: a move is followed and said, a new version is read and said to have been changed by something other than RectoPDF, and a file gone says it can't be found. Unsaved edits stay, and nothing is written to the file.
- **A password-protected PDF asks for its password on the system's sheet** (coordinator's brief, 2026-11-08), in Rust's words, with a secure field. The password opens the file and draws it, is held in memory while its tab is open, and is never stored, logged, journaled or put in the state record, so a protected tab asks again after a quit or an update. Five wrong passwords in a row and it stops asking, and says so, until the file's opened again. An agent can't give or read a password: no command takes one, and an agent's own reads of the file stay refused (exit 8), as protected documents need the person's consent per document (agent report §5.5).
- A neutral signature mark, never a green tick in v1.

## 5. Agent

- **`recto stop` doesn't quit the app someone is using.** In a normal app it refuses, and says only the user quits the app. A quiet QA run stops when told. A default, by the coordinator's decision of 2026-11-07, until the owner says otherwise.
- The app starts the user's **existing `claude` install** if there is one, and never handles credentials. If it's missing, the panel shows
  setup steps and the reader works as normal.
- **The agent requests what it needs.** The first prompt holds facts about the PDF (size, pages, text status, outline) plus the question,
  the current page number and any selection. Page text is never included.
- **`recto search` offers ripgrep-style and BM25 search directly** (owner, 2026-11-07: "Shouldn't we enable ripgrep and bm25 directly in our search? That way the agent can use it through cli, and the user can use it if they want. My repo mcp-methods have a working ripgrep implementation you can copy if you want."). In process, so no `rg` binary is run.
- Tools limited to `Read` and `Grep` over a per-document folder, in a fully locked-down run. Never `Bash(rg ...)`: `rg --pre` executes text
  that comes from the PDF. Exact arguments: agent report, §1.
- `recto` CLI on a local socket with levels Off, Read-only, Control and Full (*default:* Off). Signing needs a human gesture and is never
  reachable by an agent. Until the app's settings exist, the user sets the level with `recto permission set <level>` at a real terminal.
- **Below Full, an agent can throw away only agents' edits, never the owner's.** Each edit step records who made it. At Control, an edit that clears undone steps, `discard`, and `close` with undone steps are allowed if every step that would be lost is an agent's, and refused with exit 5 otherwise, saying those are the user's edits. A tab with unsaved edits doesn't close at any level: `discard`, then `close`. At Full, what's lost is the holder's call. An agent's `undo` of the owner's edits doesn't hide them: answers say so, the sidebar model has it, and the session's own close refuses until they're redone or discarded.
- **What an agent may save** (*default*, the coordinator's, 2026-11-08): at Control, `recto save` of what's appended, as nothing is lost (every byte stays in the file, undo goes past the save, and the first save keeps the original), and `recto save-as` to a new file. Replacing another file, and a save that rewrites the file, need Full. Save only when the user asks.
- [DECIDE] Whether a public release waits for Anthropic's written answer on subscription use. *Default:* yes, with an API-key route too.

## 6. Scope: everything in one build

"We build everything in one go, but we test as we build." Build order follows dependencies only.

| Group | Features |
|---|---|
| Reading | Lazy open, tabs, contents, Find, paper modes, the sidebar's button, session restore |
| Agent | Panel, corpus, `recto`, generated skill |
| Annotations | Highlight, underline, strikeout, note, ink. Notes autosave beside the file, and go into the PDF on Save (*default*) |
| Forms | Filling, owned by the Rust core and lopdf (*default*). No JavaScript; detect and explain. Dynamic XFA detected only (*default*) |
| Signing | **Placeholder for now** (owner, 2026-11-06): the labelled image option, a neutral "signature present, not checked" report, and the final seams in `recto-sign`. No file is signed cryptographically until it's built properly to the official standards (ISO 32000-2, ETSI EN 319 142, RFC 5652, RFC 3161) |
| Edit PDF | **An edit mode** (owner, 2026-11-06: "pdf edit mode that lets you edit text, drag and drop pdfs into the app to add more pages to an existing pdf, rearrange pages, turn/rotate individual pages"). **Pages:** the page area becomes a grid; drag to rearrange, drop PDFs to add their pages, rotate, delete, extract, split. Edits are a small list applied on Save: instant, about 8 B a page, and undoable. **Text:** click text and type. Lines rewrap inside their text block, as in Foxit's Edit Text; other blocks don't move, and nothing flows across pages. It keeps the PDF's font; a character the font lacks uses an embedded fallback font. See `docs/research/2026-11-06-foxit-editing.md` |
| Security | Password protection |
| Saving | **Built, by append** (2026-11-08): turns, moves and added pages; deletes and signed copies come with the rewrite. **Save** and **Save As**, atomic, never partly written. Adding things appends to the file. **Removing things (delete a page, redact, compress) rewrites it, so the old data is really gone.** If a change would break a signature, Save is off and Save As explains why. One backup of the original on first save (*default*) |
| Compare | Text first, read-only |
| Compress | **Low, Medium, High to a fixed image DPI, then save.** Start: 220, 150, 96 DPI. Measured at printed size; never enlarges, leaves text, vectors and 1-bit scans alone; cleans the file first. Apply changes the open document, then it saves normally |
| OCR | Tesseract, with **Save as searchable PDF**: an invisible text layer with an embedded Unicode font, in a helper process |
| Extraction | **Click an image to copy it losslessly.** **Snapshot tool:** drag a box for text, PNG, SVG and JPG, all on the clipboard at once |

**SVG is hand-rolled** (owner, 2026-11-06): a small streaming generator in `recto-svg` that writes as it reads PDFium's page objects through the worker, with no
document held in memory. Paths, clips, images and text are direct. Anything SVG or PDFium's calls can't express (PDFium has no way to read a shading, a pattern, a blend mode or a soft mask) is embedded as a raster of just that element and reported, and content outside the snapshot box is left out rather than hidden.
*Rejected:* `hayro-svg` as a dependency, and PDFium, which has no SVG output as far as we know.

**Text in an SVG** is exact outlines with invisible real characters over them, so it looks right and can be selected (*default*, 2026-11-07). `--text paths` drops the characters, and `--text selectable` drops the outlines, for the smallest file, in whatever font the reader has.

**JPG honesty:** a JPG is lossless only when it's the original bytes of one image. Anything else is re-encoded and says so.

**A passed-through JPEG keeps its original bytes** (owner, 2026-11-07: "Lets do original bytes"): EXIF, XMP, comments and bytes after its end all stay, so it's byte-identical to the one in the PDF, and the answer says what's there, with counts. What isn't a sound JPEG, or doesn't mean what the page means by it, goes as PNG. **`recto export svg --strip-metadata`** (owner, 2026-11-07: "Just add it in the cli for now (agent option)") takes that out, keeping what affects how the picture looks, and the compressed image data stays byte-identical. CLI and agent only, with no app UI, and it's off by default. A box leaves out the document's title, and so does stripping.

**Where a JPEG would look different from the page, what's around it is corrected and the picture stays** (owner, 2026-11-07, about JPEGs going out as PNG: "Cant we fix the decoding instead?"). The compressed picture stays byte-identical, and the answer counts such a JPEG apart from original bytes. EXIF that says to turn it is set to upright. A profile of its own that the page doesn't go by is taken out, and a profile the page says it's in goes with it, within a size limit. A JPEG with a mask keeps its picture, with the mask beside it as lossless grey through SVG's own `<mask>`. PNG stays for what that can't make right: CMYK, a `/Decode` or `/ColorTransform` that changes the picture, a mask blended ahead of time, a cut image and anything that isn't a sound JPEG. `--strip-metadata` keeps its meaning and doesn't undo these.

| Added by the owner, 2026-11-06 | Redaction, remove hidden data, watermarks and Bates numbers, create form fields, measure tools |

Signature trust through EU lists comes later, with the signing work.

**Hidden text in a copy is left out, with a quiet notice saying how many characters went** (decided by the owner, 2026-11-07). `recto text` keeps them, marked, since an agent is told about them and a clipboard can't be.

**Text copy on a PDF whose permissions forbid copying gets a small notice with "Copy anyway"**, for that file while it's on screen (decided by the owner, 2026-11-07). **An agent keeps `recto copy --anyway`, and each use goes in the activity log** (owner, 2026-11-07, passed on by the coordinator). Without it, `recto copy` is exit 8.

[DECIDE] Image copy and snapshot on such PDFs (*default:* the same notice, as for text). Open-source readers differ: pdf.js and Evince ignore the flag by default, Okular obeys it with a setting to turn that off, and SumatraPDF blocks text copy but still copies as an image.

**Left out:** paragraph reflow and image replacement (for now), conversion to Word or Excel, creating PDFs from Office files, sending documents for signature,
print production, portfolios, 3D and media, V8.

## 7. Decision log

Numbered so they can be cited. Newest last.

1. **Name RectoPDF, CLI `recto`.** The name must say it's a PDF reader. Free on crates.io, PyPI, npm, Homebrew and GitHub on 2026-11-06; trademarks unchecked.
2. **Native AppKit over Rust.** Lowest measured memory.
3. **Developer ID, not the Mac App Store.** A sandboxed child can't see `rg` or `claude`.
4. **Use the existing `claude` install.** Owner: "Use the existing claude install if it exists."
5. **The agent pulls, the app never pushes text.** Owner: "That hands off the decisions to the agent."
6. **Your lopdf fork, plus PDFium.** Neither can do the other's job; upstream lacks the lazy reader.
7. **Park distillPDF.** Owner, 2026-11-06.
8. **No top bar.** Owner: "We need to maximize vertical reading space."
9. **One build.** Owner: "We build everything in one go, but we test as we build."
10. **Hand-rolled SVG.** Owner: "we can probably handroll an efficient svg generator". Streaming suits the memory goal.
11. **Mac first, Windows later** (*default*). The core is cross-checked for Windows from the first commit.
12. **Permissive or closed licence** (*default*). Rules out MuPDF and poppler.
13. **Signatures are a placeholder for now.** Owner: "lets do a signature place holder for now. We can build it out properly later using the official standards. So structure the code accordingly." A placeholder never produces anything that looks like a signature.
14. **All five extra tools are in this build.** Owner answered yes on 2026-11-06.
15. **PDFium confirmed for now.** Fast on 5,689 real pages; two lines of the benchmark's rule fail, so the rule is amended as in §3.
16. **Normal Save and Save As.** Owner, 2026-11-06. Replaces the earlier save-to-a-copy default.
17. **Commands live in the macOS menu bar;** the sidebar panel keeps only what you use while reading. Owner, 2026-11-06.
18. **Edit mode is in, including text editing.** Owner, 2026-11-06. Reverses the earlier call to leave text editing out. Text edits work on a whole block, matching Foxit's baseline.
19. **Exports wait for the heavy slot; they never come out at low resolution.** Owner, 2026-11-07. An export needing the larger limit waits, bounded and cancellable, and draws sharp, or is refused with no file written. On-screen pages stay as they were: low-res at once, never waiting.
20. **2026-11-07: below Full, an agent can throw away only agents' edits, never the owner's.** Replaces "nothing is lost without Full". That rule was there to stop an agent erasing the owner's edits by undoing and editing, but it also trapped ordinary work: an agent that did `page move`, `undo`, `page delete 2` was refused, couldn't close either, and had to ask for Full to clean up its own edits. A blind agent got stuck exactly there. Recording who made each step keeps the protection where it was needed and lifts it where it wasn't.
21. **The renderer is sandboxed in a nested helper app, not an XPC service** (*default*, 2026-11-07). launchd delays an XPC service's next start by up to 10 s after a short run, and one service process can't give each document its own worker without private API. The helper keeps the child process, socket pair and shared memory, and drops its Mach send rights once PDFium has loaded, because the App Sandbox alone let a test app start outside the sandbox. Not yet built into production, and same-team library validation, notarization and Gatekeeper need a real Developer ID to test. See `docs/research/2026-11-07-sandbox-spike.md`.
22. **A search corpus is built when someone asks for it, never on open** (2026-11-07), and **search text is kept for 90 days with a maximum size** (owner, 2026-11-07: "For search text keeping, 90 days with a max size feels good"). A search, `recto index` and `recto wait indexing-done` ask. One indexer runs at a time. It goes in the user's caches, marked to stay out of Spotlight and backups, is capped at 2 GiB in all and 512 MiB a document, the least recently used going first and anything unused for 90 days. Those are looked at whenever a build ends, however it ended, and on the first ask of every session, so they fire with nothing being built. A new version of a file takes the old one's text away. A password-protected document's text is never written, and a file on anything but APFS isn't indexed, since its times can't show it's been replaced. The search itself is a pass over a text file rather than a trigram or word index, because that's already fast enough on the largest real documents here: see `docs/ENGINEERING.md`. The folder an agent reads is made only when asked for, from that same text, so the text is kept once. Its key is the file's identity rather than a hash of all its bytes, as the agent report had it, because every search asks for the key.
23. **App state is recovered exactly, on every launch and across an update.** Owner, 2026-11-07: "It's crucial that app state is perfectly recovered before and after update". One record in the state folder holds everything the user can see or has changed: the window's frame and full screen, appearance and paper, sidebar width, folds and panels, the tabs in order, the active tab, each tab's place, zoom and rotation, Find, edit mode, and unsaved edits with their undo history and who made each step. Keyboard focus, which window is frontmost and the exact scroll position are part of it, as is what's selected once selection exists. It has to be good enough to update while the user is using the app (decision 24). Written atomically and read back. Tabs come back cold, at no more than a cold tab's cost. A test compares the whole `qa state` before and after, so anything new is carried over or named as an exception; it can't be forgotten. The exceptions are shown, never silent: a password isn't stored, so a protected PDF asks again; a file that changed or moved meanwhile says so, and its edits are kept and nothing is written to it. A record from a newer version is left untouched and not overwritten, so going back to the previous app still works. Restoring on a normal launch, and restoring agent levels only as the level's file already does, are *defaults*.
24. **Updates are hands-off, from GitHub releases, as in Seedwell.** Owner, 2026-11-07: "a check for updates button in the top bar, that turns into a update to… button if new version has been released. App settings should have a auto update toggle, and we check for updates once per day." "Top bar" is the macOS menu bar, since nothing sits above the page: *Check for Updates…* in the RectoPDF menu (*default*), which reads *Update to X.Y.Z…* once a release is found. One switch in Settings, *Update automatically*. The daily check runs whichever way the switch is set, and sends GitHub an ordinary download request with no document data. Rust decides what's on offer, when to check and when to install, and the host draws. A download is installed only if its checksum, Developer ID team and Gatekeeper check pass. The state is written and read back before the app quits, or the update doesn't go ahead. If the new version doesn't start, the previous one comes back with the same state. Development builds check only when asked and never replace themselves. Owner, 2026-11-07: "it should recover state so perfectly that it can update while the user is using it. But for auto update let's update in a window the user hasn't touched the app for 30 minutes". So *Update to X.Y.Z…* installs at once, mid-use, with no prompt about unsaved edits, because they're carried over. Everything slow happens first: the app quits only once the download is verified and the state is written and read back, so the gap is one quit and one launch, and the app reopens with the same window frontmost, keyboard focus and exact scroll position. An automatic install runs once the user hasn't touched the app for 30 minutes, whether or not it's frontmost. A running save or export finishes first, and so does an agent command, in both cases. The switch starts on (owner, 2026-11-07); an app in the background reopens without taking focus. *Defaults, 2026-11-07:* a window closed with the app still running stays closed across an update, and any other launch opens one. The download goes through the system's `curl`, so no HTTP or TLS code stays in the app. The installer is a small program of ours in the bundle rather than a script, swaps the app with one atomic rename, and keeps the previous app beside it in a hidden folder. A new version has come up once its first correct frame is showing and it has drawn a page of its own through the real renderer: a timer can force a first frame and a sleep file can fill one, neither says the renderer loads, and one of the user's PDFs that won't draw says nothing about the version. After three launches of a new version that don't come up, the next one goes back to the previous one. The installer checks once more, at the moment of the swap, that what's waiting is what was verified. *Update automatically* is kept in `updates.json`, so a lost record can't turn it back on, and one that's unreadable counts as off. An update arriving while the app was in the background goes behind everything, isn't key, and waits to go into full screen until the user comes to it. An update that gets as far as quitting the app and reopening it for nothing says so, and three times of that is the last by itself. `recto update check` needs Control, and `recto update install` and changing `recto settings` need Full. A release that fails its checks, or doesn't start, isn't installed by itself again, and can still be chosen from the menu.
25. **State goes to disk by what happened, not on a timer, and edits are appended, not rewritten** (2026-11-07, for the owner's rule on SSD wear; the policy is the coordinator's *default*). Each tab with unsaved edits has one append-only journal of compact steps: a rotation or a move is a few bytes, an added PDF is a reference, a pen stroke is written when it ends, and typing when the block is committed. The journal also serves memory: undo steps past a byte cap leave memory and are read back from it if they're undone, with no extra write. Owner, 2026-11-07: "edit should also keep undo, redo history of edits until save has been applied." And: "We don't want to add the undo redo history to the file itself, but we can have a rolling save redo history on the system, so it kind of in the temp files per PDF." So history never goes in the PDF. It rolls: the last 1,000 steps or 64 MiB per PDF, whichever comes first (owner: "1000 steps and 64mb is good"), held in a private file per PDF in Application Support rather than a real temp folder, which macOS clears and this is the only copy of unsaved work. Rolling off loses the undo, never the edit: the journal keeps a checkpoint of the current edits, so the document is complete whatever has rolled off, and edits are never refused for size. Below Full, an agent's steps can't push out the owner's. History survives sleep, a crash, a restart and an update. Owner, 2026-11-07: "after a save you might still have regrets and want to make changes. But you definitely don't want history to leak into the pdf file". So a Save doesn't end the history. It marks the saved point: the document reads as unsaved again once undone or redone away from that point, and undoing back to it reads as saved. Nothing from the history is ever written into a PDF, and a test proves it by searching a saved file's bytes for marked text that was only ever in the history. *Defaults:* a confirmed redaction or hidden-data removal clears the history, because otherwise what was removed could be recovered from it; so does a file changed outside the app, since its steps no longer apply. A history is kept 30 days after the PDF was last open, within 1 GiB in total, oldest out first, is left out of backups, and Clear Edit History removes it on request. A step whose page data can't be kept within the limits rolls off, and the file's one backup stays as the way back. Replacing text counts as removing for the Saving rule in section 6: a Save that changed text rewrites the file, so the old words don't stay in its bytes. A new edit after undoing replaces the undone steps, as on any Mac (decision 20 still governs whose can be replaced). The place in a document is written at most once a minute, only if it changed. Quit, going to the background and an update write at once, and only an update's hand-off forces the drive to flush. So a crash can lose up to 5 s of edits and a minute of place, and a quit or an update loses nothing. Disk use has caps too, and the bytes written are measured from the process's own counter in a test. Owner, 2026-11-07: "It's fine to keep in memory for a while, and then as it goes dormant we store to disk." So a tab in use keeps its edits and undo history in memory, with the journal there only for crashes. A tab goes dormant once it hasn't been active or edited for 5 minutes (*default*): then, once, its journal is compacted, its page preview is written if the place changed, and its undo history leaves memory. A memory cap or memory pressure makes that happen sooner, so the budget always wins. A dormant tab that's touched again reads back only what it needs. Owner, 2026-11-07: "When it's on deep sleep, we want its state to be stored on disk, not on memory. But it needs to be stored in a way that's quick to recover without any delay." So a sleeping tab costs a cold tab's memory, and its sleep file holds what the first frame needs without opening the PDF: a low-resolution preview of the place it was at, the page table and the contents. Tapping it shows the right place at once, then sharpens. A sleep file is checked against the PDF's file stamp, is treated as hostile, and can always be thrown away and rebuilt from the PDF, unlike the journal.
26. **A PDF can only be opened once.** Owner, 2026-11-07: "Two tabs of the same pdf? This shouldn't be possible. A pdf can only be opened once". Opening a file that's already open goes to its tab, from the menu, a drop, the CLI or an agent. "The same" means the same file on disk, so a symlink or hard link to it is the same PDF; a copy is another file. An agent's `recto open` answers with the existing tab and says so.
27. **A rewritten copy of a signed PDF is unsigned, never broken.** Owner, 2026-11-07: "II agree with this signature approach", after Acrobat users report it refuses such changes and the usual way round is an unsigned copy. A change that needs a rewrite (deleting a page, redaction, compress, replaced text) turns Save off on a signed PDF. Save As makes a new copy with every signature removed: its field, its value and its drawn box, with document-level signature permissions (`/Perms`, DocMDP) and the form's signature flags. It says "The new copy won't be signed. The original keeps its signature." Additions are appended, so the signature stays valid. The signed original is never touched, and nothing ever calls a signature valid. A signature drawn into page content isn't a signature field and stays as page content.
