# PDF signing: what "real" signatures take, and what RectoPDF should ship

**Track:** R3, R5, R7, R8, R13 for RectoPDF (`recto`). **Date:** 2026-11-06. **Status:** research finished, small spike run.

The owner asked: "I want to support pdf signing, so we need to see how that is supported." Folio only stamps images.
This report says what doing better takes.

## 1. The answer

**Do it, in three layers, and do not sell a fourth we cannot deliver.**

1. **Ship certificate signing in v1: PAdES B-B and B-T, approval signatures, keys from Keychain, Windows CNG or a `.p12`.**
   This beats Folio on day one and needs no contract with anyone. The hard part is small: an append-only writer and
   about 1,500 lines of CMS and PDF plumbing.
2. **Ship an honest reader in v1.** Report cryptographic integrity, what the signature covers and whether anything changed
   afterwards. Never print the bare word "valid". Full trust evaluation (EU Trusted List, revision classifier) comes
   later. It is the largest piece of work here, and it is where 24 of 26 viewers were broken in 2021.
3. **Reading Norwegian BankID signatures is the best value for Norway, and it is free.** Since 2026 BankID output is
   PAdES with a qualified certificate chaining to the EU Trusted List. Recto can show that correctly once layer 2 has the
   trust list.
4. **Do not promise "Sign with BankID" in a free desktop app.** BankID signing is a merchant service: a partner, a
   contract, a client secret and a backend. There is no route for an unaffiliated desktop binary. Same shape for Buypass.

**Three findings you would not guess:**

- **SEID-SDO is the past.** Norwegian BankID moved to a single issuer, Stø AS. Its new signing solution does not support
  SEID-SDO "except in B2B - for now" [P-s]. The Norwegian Trusted List, issued today, lists Stø as qualified and marks the
  old bank-run BankID CAs withdrawn from 2026-11-08 [P]. Do not build SDO support for v1.
- **The engine is closer than expected, and has one trap per corner.** Using only the fork's public API, my spike signed 243
  of 244 real PDFs with byte-identical prefixes. `pdfsig` accepted all 243 and pyHanko strict accepted 232; 10 of the rest are hybrid
  files it refuses by policy [M]. But the fork encrypts `/Contents`, can't read signature objects in AES files on the indexed route, breaks
  files with a junk prefix, and orphans the whole document if it was recovered [M]. Upstream 0.47 fixes the encryption pair and exposes
  `Writer` [P, not run]. Fork is at 0.45.
- **A green tick in Acrobat is not something code can earn.** It comes from the certificate's issuer: AATL or the EU
  Trusted List. Of the Norwegian issuers, only Buypass roots are on the AATL file Adobe published on 2026-10-15. Commfides,
  Stø/BankID, Signicat and Scrive are not [P]. Those can only go green through the EU list.

**This conflicts with sibling report RD7**, which recommends "report only" and asked which meaning of signing the owner
intends. The owner's words and the Folio comparison answer that: certificate signing. See [DECIDE] S1.

## 2. Kinds of signing and what each one gives

Spec text: ISO 32000-1:2008 §12.8 [P], ETSI EN 319 142-1 V1.2.1 (2024-01) [P]. ISO 32000-2 is the current base but I read it
only second-hand (§15).

| Kind | What it proves | Survives later edits | Acrobat display | eIDAS position | What it needs |
|---|---|---|---|---|---|
| **Visual stamp** (Folio) | Nothing. A picture on a page | Anyone can change the file silently | No signature panel entry | At most a plain electronic signature; Art. 25(1) says it can't be refused *solely* for being electronic [P] | Nothing |
| **`adbe.pkcs7.detached`** | File unchanged since signing, plus a certificate name | Yes, by byte range | Depends on issuer | Plain or advanced, by facts | Any key |
| **PAdES B-B** (`ETSI.CAdES.detached`) | As above, plus the signing certificate is bound by a signed attribute. Time is only claimed (`/M`) | Yes | Depends on issuer | Can meet Art. 26 advanced; qualified if Art. 3(12) is met | Any key |
| **PAdES B-T** | Adds a trusted time from a timestamp authority | Yes | Shows the timestamp | Same | A TSA |
| **PAdES B-LT** | Adds certificates and revocation data in `/DSS`, so it checks offline later | Yes | "LTV enabled" | Same | CA's OCSP or CRL |
| **PAdES B-LTA** | Adds a document timestamp over everything, re-timestampable as algorithms age | Yes | Same | Same | TSA and revocation data |
| **Certification** (DocMDP) | Author's statement of which later changes are allowed. P=1 none, P=2 forms and signing, P=3 also annotations (Table 254) | By design | Blue-ribbon style "certified" state [S] | Orthogonal | At most one per document; must be the first signed field (§12.8.1, §12.8.2.2) |
| **Approval** | "I sign this version". Many allowed | Yes | Listed per signature | Orthogonal | Field in `/AcroForm` |
| **Field lock** | `/Lock` (`Action` All, Include, Exclude; Table 233) and the matching FieldMDP transform (Table 256) mark fields whose later change breaks the signature | By design | Fields become read-only | Orthogonal | Prepared field |
| **Document timestamp** (`ETSI.RFC3161`) | Time only, no person | Yes | Listed as a timestamp | Art. 41 if qualified | TSA |
| **UR3 usage rights** | Unlocks features in Adobe Reader | No use to us | n/a | n/a | Adobe's key. **Never** |

**PAdES baseline is stricter than a plain PDF signature** (EN 319 142-1 §4.1, §6.3 and notes) [P]:

- `SubFilter` is `ETSI.CAdES.detached`; a DER `SignedData` with **one signer** only; **nothing encapsulated**.
- `content-type` is `id-data`, `message-digest` present, and `signing-certificate-v2` preferred ("should use ... in
  preference", note f).
- **The `signing-time` attribute shall not be present.** Claimed time goes in `/M`, which is required.
- `/ByteRange` covers the whole file except `/Contents` (note k). `/Cert` shall not be present.
- `/Reason` is out if `commitment-type-indication` or a policy is present (notes d, m).
- B-LT needs a `/DSS`; `/VRI` "should not be used" (note v). B-LTA needs a document timestamp after the DSS (notes x, y).

**Algorithms for new signatures**, ETSI TS 119 312 V2.1.1 (2026-06) [P]: SHA-256, -384, -512 recommended; SHA-224 legacy to
2028; SHA-1 discontinued (Table D.1). RSA ≥ 3000 bits recommended; 1900 to 2999 bits legacy, **no new certificates after
2026-12-31**, those issued must expire by 2028-12-31 (Table 6). PKCS#1 v1.5 legacy, PSS recommended (§6.2.2.1). P-256
recommended (Table 3). Verifiers shall support ML-DSA and SLH-DSA (Table A.1).

### Green tick in Acrobat

| Situation | Result | Evidence |
|---|---|---|
| Self-signed or private CA | Math fine, signer not trusted: "validity unknown" style warning, not green. Reader can add it by hand; Adobe advises against that | [S] Adobe community and Acrobat 9 guide. Adobe's help pages returned 403 to every tool |
| Chain to an **AATL** root | Green, automatically | [S] for behaviour. The list itself is [P] |
| Chain to an **EU Trusted List** qualified service | Green, labelled qualified under 910/2014, from a local snapshot up to about 30 days old | [S] search snippet of Adobe's EUTL page |
| Technically valid certificate, but AATL issuer requires hardware keys | Software-held keys don't get AATL certificates: GlobalSign and IdenTrust say hardware or token only | [S] AATL Technical Requirements v2.0 (June 2017) on a mirror |

**Measured:** `trustlist.adobe.com/tl12.acrobatsecuritysettings`, signed 2026-10-15, holds 311 certificates [P]. Norwegian
matches: **Buypass Class 3 Root CA** and **Buypass Class 3 CA 3** (plus an expired CA 1). No Commfides, BankID, BankAxept,
Stø, Signicat or Scrive. Also present: SSL.com, Sectigo RSA Document Signing, GlobalTrust 2020 AATL, LuxTrust, InfoCert.

**What this means for a Recto user:** a free self-signed identity proves tampering, not identity, and every recipient sees a
warning in Acrobat. To go green the user buys a hardware or cloud certificate. Recto cannot change that and must say so.

## 3. Mechanics

**The sequence** (ISO 32000-1 §12.8.1, EN 319 142-1) [P]:

1. Append an incremental update (§7.5.6) containing the signature dictionary, the widget, and changed page and AcroForm
   objects, with a new xref and trailer whose `/Prev` points at the old xref. **No earlier byte changes.**
2. `/Contents` is a hex string whose full space is reserved first ("must be allocated before the message digest is
   computed"). `/ByteRange` is written with fixed-width slots, then patched.
3. Hash everything except the `/Contents` value, build signed attributes, DER-encode them with the `SET OF` tag (RFC 5652
   §5.4), hash again and have the key sign that.
4. Assemble `SignedData`, hex it into the reserved hole, pad with zeros.
5. For B-T: send the hash of the signature value to the TSA (RFC 3161 `messageImprint`; only a hash leaves the machine) and
   add the token as an unsigned attribute. That must fit in the same hole, so it is done before the hole closes.
6. For B-LT: **another** incremental update adds `/DSS` with `Certs`, `OCSPs`, `CRLs`. For B-LTA: another update adds a
   `/DocTimeStamp` signature with its own byte range. Each DSS update should keep the previous values (EN §5.4.1).

**Reserve size.** Must be large enough first time: a hash change after overflow means asking for the PIN again. References:
PDFBox default `0x2500` = 9472 bytes (`SignatureOptions.java:44`, 3.0.8); iText 8192 plus chain, plus 4192 for OCSP plus TSA
estimate (`PdfSigner.java:611-626`, 9.8.0); pyHanko 16 KB of hex, i.e. 8 KB binary (`pdf_byterange.py:95`, v0.38.1) [P].
Recommendation [E]: 32 KB binary for B-T. It costs 64 KB of file, once.

### 3.1 What the writer must guarantee

| # | Guarantee | Why |
|---|---|---|
| W1 | Bytes `0..old_len` are copied, never re-serialised | Any change voids earlier signatures |
| W2 | Offsets of the `/Contents` hole and `/ByteRange` slots come from the writer, not from a search | A search can match attacker text. pyHanko records them while writing (`pdf_byterange.py:105-113`) |
| W3 | `/ByteRange` values are direct, fixed width, padded with spaces | §12.8.1: values in the signature dictionary "shall be direct objects"; patching must not move bytes |
| W4 | `/Contents` is never encrypted, and the other strings in that dictionary are | EN 319 142-1 §5.5 [P] |
| W5 | Keep `/ID` and restore `/Encrypt`, set `/Prev` to the real last xref, `/Size` never shrinks | Otherwise readers lose revisions |
| W6 | New xref section type matches the file's: table for a table or hybrid file, stream for a stream file | Readers that follow one kind fail on a mix |
| W7 | Offsets above 4 GiB don't wrap, or are refused | Silent corruption |
| W8 | Refuse: recovered xref, non-zero header offset, xref chain loop, failed agreement gate, DocMDP P=1, encryption bit forbidding it | Each produces a broken or dishonest file |
| W9 | Append to `/Fields` and `/Annots`; never replace | Otherwise earlier signatures vanish. **My first spike did exactly this**, §4.5 |
| W10 | Hash and write in a temp file beside the target, fsync, rename. Never touch the input in place. Stream, don't load | Memory budget; crash safety; PIN prompts can take minutes |
| W11 | The `PrepareResult` is a value that can wait for a remote or human signer, then fill | Needed for tokens and CSC. pyHanko's `PreparedByteRangeDigest` is the model (`pdf_byterange.py:116`) |
| W12 | Re-open and verify the finished file with our own reader before replacing anything | A bad signature is worse than none |

### 4.5 Spike: what actually happened [M]

Throwaway crate in the session scratchpad, depends on the fork by path, builds with `heavy.sh`. Uses **only the public API**.
It appends a signature dictionary, widget and AcroForm through `IncrementalDocument`, then a script finds sentinels in the

Independent checks: **pyHanko 0.38.1** (`PdfFileReader(strict=True)` and non-strict, with the test cert as trust root) and
**poppler `pdfsig` 26.04.0**.

|---|---|---|---|
| Classic xref (596 bytes) | Yes | Signature is Valid, total document signed | strict: intact, valid, trusted, `ENTIRE_FILE`, modification `NONE` |

| Result | Files |
|---|---|
| Signed; prefix identical; `pdfsig` valid; pyHanko **strict** intact, valid (138 classic, 94 xref stream) | **232** |
| Same, but pyHanko strict refuses **hybrid** files by policy; non-strict passes | 10 |
| Same, but pyHanko strict objects to a free xref entry ("next generation 0"); non-strict passes. `physics_optics_2607.28482`, not investigated: may be the input file or our section | 1 |

**So the byte mechanics held on 243 of 244 attempted real files, and the prefix was byte-identical on all 243** [M]. Two limits: the corpus run used the first spike build, which replaces `/Annots` and `/AcroForm` (W9), so files with existing forms or annotations lost them in the output. That doesn't affect what is being tested here, the byte range and xref. And it doesn't show the files render the same, because page and pixel comparison wasn't part of it.

**Engine assets.** `assets/Incremental.pdf` passes pdfsig but pyHanko errors with `KeyError '/Type'`: the asset's first revision has an xref stream with no `/Type /XRef`. The input is malformed, not our append.

**Second signature.** A pyHanko signature on top of an engine-signed file: pdfsig reports both valid, the first "not total document". pyHanko strict: first `ENTIRE_REVISION`, modification `FORM_FILLING`, docmdp OK; second `ENTIRE_FILE` [M]. **My first spike version replaced `/Annots` and `/Fields`, so a second engine signature silently dropped the first from the document.** That was my bug, not the engine's, and it is why W9 and test R3 exist.

timestamps, DSS, Acrobat, EU DSS validator, any OS key store, any real token, files over 4 GiB, linearized files in depth.

## 5. Verification in a viewer

### 5.1 Status is a record, not a boolean

Rust computes this; the host draws it. Every field is reported, and the headline is derived from it.

| Field | Values |
|---|---|
| `form` | `pades` / `pkcs7_detached` / `pkcs7_sha1_refused` / `x509_rsa_sha1_refused` / `doc_timestamp` / `unknown` |
| `integrity` | `intact` / `broken` / `could_not_check(reason)` |
| `coverage` | `whole_file` / `whole_revision(later_updates: n)` / `nonstandard` |
| `later_changes` | `none` / `validation_data_only` / `form_fill` / `annotations` / `later_signature` / `other` / `not_classified` |
| `docmdp` | `none` / `p1` / `p2` / `p3`, and `respected` / `exceeded` / `not_checked` |
| `identity` | certificate name, plus `qualified_per_eu_list(as_of)` / `chains_to_os_roots` / `self_signed` / `not_checked` |
| `time` | `claimed_only` / `trusted(tsa, time)` / `timestamp_broken` |
| `revocation` | `not_checked` / `embedded_good(at)` / `online_good(at)` / `revoked(at)` |
| `parsers` | `agree` / `disagree(reason)` / `recovered` |

### 5.2 Known attacks and what each one requires

| Attack | How it works | Scale then | Design rule |
|---|---|---|---|
| **USF** (Mladenov et al., CCS 2019) | Signature dictionary present, but `/Contents` or `/ByteRange` invalid or unreachable, so the check is skipped and the UI still shows a signer [P-s] | 21 of 22 desktop viewers and 5 of 7 online services hit by at least one of the three 2019 classes; CVE-2018-16042 | **A signature that can't be checked is a failure state, never "skipped".** Every field in `/AcroForm` of type `/Sig` is listed, including no `/V` |
| **ISA** | Bytes appended after the signed range. Variant 1 is a legal update; 2 to 4 omit xref or trailer and rely on reader tolerance [P-s]. CVE-2018-18688 | | **Any byte after the signed range is reported.** No recovery on the verify path |
| **SWA** | Rewrite `/ByteRange` third value, move the second signed part (wrapped in a stream or dictionary), plant a new xref at the original offset; can eat the zero padding in `/Contents` for space [P-s]. CVE-2018-18689 | | **Strict shape:** `[0 a c d]`, `a + hole = c`, the hole is exactly the hex string of *this* dictionary, `c + d` ≤ file length, file ends where the revision ends. pyHanko's check: `pdf_embedded.py:447-508` [P] |
| **Shadow: Hide** | Visible overlay signed, hidden content under it. Later update drops the overlay by new page object or by re-typing the object in xref [P-s] | 16 of 29 viewers (NDSS 2021) [P]; CVE-2020-9592, -9596 | **Compare resolved objects per revision**, not just appended bytes |
| **Shadow: Replace** | Form field's `/V` differs from `/BBox` appearance; or appended font redefinition changes glyphs [P-s] | | **Form fill is not automatically harmless:** check `/AP` against `/V`; a font or resource change is `other` |
| **Shadow: Hide-and-Replace** | Signed file has two objects with the same id. The update is **only a new xref and trailer** pointing to the other one. "The most powerful": whole document changes [P-s] | Paper: Hide and Hide-and-Replace "are always applicable as long as the viewers allow Incremental Update" [P] | **An xref-only update is a content change.** Compare the location each revision resolves to. Warn at signing on duplicate or unreferenced objects |
| **Certification: EAA** | At P3, FreeText, Stamp or Redact annotation paints over content; can hide its own UI entry [P] | 15 of 26 viewers [P] | **Allowed is not harmless.** Show new annotations by default. Classify those three as high risk, even at P3 |

**Why Recto is not exempt by caution.** The Shadow authors excluded viewers with no signature validation at all (sibling §6.4).
Once we claim anything, we are in scope. So rule 1 below is that we only claim what we checked.

**Whole-file coverage is a clean line.** If a signature covers the entire file, no update exists after it, so ISA, SWA's
appended parts, Shadow and EAA or SSA have nothing to work with. That is why v1 can safely distinguish "nothing has been added since"
from every other state, without a full classifier. [E]

### 5.3 The renderer and the signature code seeing different files

This is the core risk, and it is real here: sibling report picks PDFium (own parser) with `IndexedReader` for structure, and
the fork has two internal readers with documented differences (`docs/indexed-reader-contract.md:18-26`). Hide-and-Replace and ISA
exist exactly because "what was hashed" and "what is drawn" need not match.

Rules:

1. **Verification runs on the bytes, and only on `IndexedReader`, in strict mode.** Never the eager reader. No recovery.
   `recovered()` true (`stats.rs:166`), an xref loop (`open.rs:122`), a non-zero header offset or lenient offset correction means:
   no positive status.
2. **"View as signed" hands the renderer a truncated byte view** ending at `c + d`. PDFium then parses exactly the signed bytes.
   Hash is checked on those same bytes (sibling §6.4).
3. **The agreement gate covers signatures.** PDFium's `FPDFSignatureObj_GetByteRange` must match our walk; page count and page
   object ids must match (sibling §6.3). Disagreement: document viewable, no positive status, signing off.
4. **Later: pixel comparison** of signed against final revision, per page (sibling §6.4). Only a detector, never proof of safety.
5. **Fixed order of evaluation.** Bytes, then structure, then CMS, then identity. A later step can't repair an earlier one.
6. **Differential fuzz:** every attack fixture goes through both parsers and both readers.

### 5.4 A real example: signatures that don't match are ordinary

Four signed World Bank documents in the local corpus (`distillPDF/benchmarking/bench100/policy_worldbank_wbD34442276`, `...277`, `...284`,
`...285`) carry DocuSign `adbe.pkcs7.detached` signatures from January 2025. **`pdfsig` reports "Digest Mismatch" on all four; pyHanko on the two I
ran reports not intact, `CONTIGUOUS_BLOCK_FROM_START`, modification level `OTHER`, and a certificate since expired** [M]. Almost certainly a publisher's post-processing,
not forgery, though I did not investigate.

**What this teaches:** "Broken" must not read as an accusation. Say "This file was changed after it was signed, so this signature no longer covers what you see. That can be
innocent, such as a publisher re-saving it." They also make good permanent fixtures, because outside validators agree on the result.

### 5.5 Other verify rules

- **Never fetch on open.** AIA, OCSP and CRL URLs are attacker text in an unverified file; fetching them is a read receipt and an SSRF
  vector. Use embedded data; go online on explicit user action. [E]
- Time-of-signing logic: validate at the timestamp's time, not today. BankID certificates live about 15 minutes, by design, so
  "expired" must not be the result (Stø signature-validation page) [P-s].
- Timestamp checks: imprint matches, TSA cert has critical `id-kp-timeStamping` (RFC 3161 §2.3) [P], chain checked separately.
- Weak hashes: refuse positive status for MD2, MD5, SHA-1. pyHanko's set: `sign/validation/utils.py:151` [P].
- Signature dictionary values come from **original bytes** with exemption for `/Contents` in encrypted files.
- Resource limits on DER, chain length and DSS size. Parser fuzz target.

### 7.2 Where the seam goes

The guide (§2.2) puts secrets at a **host seam**. Signing is different, because the **`recto` CLI has no host** and must sign too.
So:

```
recto-core (no OS names)
  sign::prepare(doc, field, appearance, signer_info) -> Prepared { digest_to_sign, ... }   // bytes, DER, policy
  sign::finish(prepared, raw_signature, timestamp?) -> SignedFile

trait KeyProvider {                          // the one seam
  fn identities(&self) -> Vec<Identity>;     // cert DER, chain, storage kind, hardware?, label
  fn sign_digest(&self, id, alg, digest: &[u8], consent: ConsentContext) -> Result<Vec<u8>, SignError>;
}

recto-platform (cfg-split, only place that names an OS)
  macos.rs   security-framework            windows.rs  windows-rs CNG
  pkcs11.rs  cryptoki (Windows, Linux)     p12.rs      Linux only
  csc.rs     HTTP (later)
```

**The host's part is one thin thing:** a parent window handle (`NSWindow`, `HWND`) so OS prompts attach to the right window, and
the file and picker UI. Rust holds every rule: which identities are offered, algorithm choice, what the sheet says, error
sentences (built from typed errors, never OS text, per §2.1). firma-cli shows this is practical in Rust, with `security-framework` and
`windows` in about 300 lines [P].

**Rules for the seam:**

- **Digest in, raw signature out.** A private key handle never crosses it, and neither does a password in a log.
- `sign_digest` may take minutes. It runs off the UI thread with a cancel path.
- Normalise signature output in Rust: X9.62 from Apple and CNG's raw `r || s` to DER; CSC's raw `r || s` to DER (Stø says exactly this) [P-s].
- **Agents have no route to `sign_digest`** (sibling agent-integration §5.2). `recto sign` needs a real human gesture: OS prompt, or a password read from
  the TTY, never argv or env ([DECIDE] S8).

## 9. Legal and compliance

Not legal advice. **The legal research server disconnected mid-session**, so Norwegian statute text below is identified by title and URL only.

**Law in force** [P for EU consolidated text of 18.10.2024]:

- **Art. 3(11), 3(12), 26:** advanced signature means uniquely linked to and capable of identifying the signatory, under sole control, changes detectable. Qualified is advanced plus a QSCD plus a qualified certificate.
- **Art. 25:** can't be denied effect solely for being electronic; **qualified has the effect of a handwritten signature.**
- **Art. 32, 33:** what validating a qualified signature must confirm, including QSCD use; "qualified validation service" is a regulated service.
- **Art. 23:** only qualified providers may use the EU trust mark.
- **Norway:** `lov om elektroniske tillitstjenester` (LOV-2018-06-15-44, lovdata.no/dokument/NL/lov/2018-06-15-44) implements the 2014 regulation; Nkom supervises. Whether the 2024 revision applies in Norway through the EEA: **not confirmed** [U].

**What this means for keys:** software keys in Keychain or a `.p12` are not a QSCD. **A software key can never give a qualified signature, whatever the certificate says.** Only a token or remote service certified as a QSCD can. Recto must not imply otherwise, and detecting QcSSCD in a certificate is how it can say so.

### 9.1 Wording rules

Rust owns these strings (§2.1).

| Never say | Why | Say instead |
|---|---|---|
| "Legally binding" | Depends on law and facts | Nothing. Or a link to neutral help |
| "Qualified", unless the check in §5 proved it | Regulated term | "On the EU trusted list as qualified at signing time, according to the list dated …" |
| "Valid signature" alone, or green tick alone | Means many things; attack class | "Unchanged since this signature" with who and when as separate facts |
| "Verified" or "Signed by Tor Haugen" for an unchecked certificate | Anyone can make a certificate with that name | "Certificate name: Tor Haugen. Not checked" |
| "Proves who signed" | Self-signed proves nothing about who | "Links the file to your certificate and shows any later change" |
| "Secure", "tamper-proof" | Absolute claims | Specific facts |
| "eIDAS compliant", "PAdES certified", EU trust mark | Not certified, not a QTSP | "Creates PAdES B-T format signatures" in technical details |
| "Signature" for an image | Folio's own docs concede this | **"Image of a signature"** |

### 9.3 Export of cryptography

| Item | Finding | Source |
|---|---|---|
| Digital signature, authentication, integrity, non-repudiation | **Excluded** from "cryptography for data confidentiality" under 5A002.a | BIS page [P-s] |
| So signing code | Not controlled by itself in Cat. 5 Part 2 | Same; my reading [E] |
| But Recto also decrypts and encrypts PDFs (fork's AES) | That is confidentiality, so it is in scope | Fork `Cargo.toml` `aes`, `cbc` |
| Publicly available open-source code | Not subject to the EAR once 742.15(b) is met; notification applies to non-standard cryptography per a BIS node; another BIS page words it generally | [P-s], and the two differ. Have someone confirm |
| Binaries with public source | Follow the source | BIS [P-s] |
| Norway | `lov om kontroll med eksport av strategiske varer` (1987-12-18-93), forskrift 2013-06-19-718, DEKSA is the authority (title and URL confirmed). Text not read [U] | Graph lookup before the server dropped |

**Practical:** low risk for an open-source tool using standard algorithms, but do a one-hour confirmation before the first public binary. Not a reason to change any design. Part of R13.

### 9.4 Privacy

- NNIN (fødselsnummer) can be in a certificate (Stø OID 2.16.578.1.61.2.4) [P-s]. Mask it by default in UI, never log it, never pass it to an agent.
- Certificates hold names and emails. They stay in the file, and in a local trust cache only if the user asks.
- TSA gets a hash; OCSP tells the CA which certificate you're looking at. Both only on user action.
- Signing logs: time and file hash only, no document names in anything leaving the machine. No telemetry.

## 11. Design rules (numbered for the spec)

1. **Say only what was checked.** Every status field has a "not checked" value and it's used.
2. **No positive status on any uncertain structure.** Recovered, disagreeing parsers, non-zero header offset, xref loop.
3. **Bytes first.** Fixed order: bytes, structure, CMS, identity. No later step repairs an earlier one.
4. **Append only.** Prefix byte-identical, proved by test and re-checked before the rename.
5. **The writer returns offsets.** No sentinel search in production.
6. **A signature that can't be evaluated is reported as such**, never hidden or "skipped".
7. **Whole-file coverage is the only v1 condition for "nothing added since".**
8. **Compare by resolved object, per revision.** An xref-only update counts.
9. **Allowed is not harmless.** Show new annotations and signature fields after a signature. High-risk: FreeText, Stamp, Redact.
10. **Fields added after certification, or `/V` missing: certified status lost.**
11. **Every sub-filter fully verified or explicitly refused.** Never pass through.
12. **Validate at signing time.** Short-lived certificates; trust list history.
13. **No network on open.** User action only.
14. **Rust owns the sentence**, and the words "valid", "qualified" and "verified" appear only through one function.
15. **Software keys are never called qualified.**
16. **`sign_digest` is the only seam**; no key handle or password crosses it; no route from agents.
17. **Refuse rather than corrupt:** W8 in plain words, offering "Save a copy" where it helps.
18. **Reader and writer agree:** every signed output re-opened by our verifier and, in CI, by two outside validators.
19. **Never overwrite the input** until the output has verified.
20. **Recompute reserve, never truncate.** Overflow means restart with a larger hole and a clear reason for the second PIN prompt.

## 14. [DECIDE]

**S1. What does v1 do with signatures?** (Replaces sibling RD7.)
- A) Report only. Smallest. But then "support signing" isn't met, and Folio's gap remains.
- B) **Create B-B and B-T, plus report with a cryptographic check, no "valid".**
- C) Create and fully validate, with classifier and trust list. About 25 to 40 more days before release.
- **Recommendation: B.** Meets the owner's request and stays honest. Trust follows soon after as the first post-v1 work.
- **Cost to change later:** low to add. Very high if a wrong "valid" ships.

**S2. When may the UI show a green mark in v1?**
- A) Never. Neutral icon and facts.
- B) **Green only for "nothing added since this signature, math checks", with certificate name still labelled unchecked**. Never on the sidebar.
- C) As in the concept: tick for every intact signature.
- **Recommendation: A for v1**, then B once trust is in. A green tick means "trusted" to everybody, whatever text sits beside it. Changes the concept render.
- **Cost to change later:** low going from A up. High going down.

**S3. Default level and timestamp authority?**
- A) Default B-B, opt-in B-T, no default TSA.
- B) **Default B-T, one preselected public TSA, changeable, with a clear "sends only a fingerprint".**
- C) Require user to pick before first use.
- **Recommendation: B, subject to reading that TSA's terms.** I did not verify any TSA's terms [U]; candidates need a read. If none suits, A.
- **Cost to change later:** low. Depends on an outside service: the file stays valid if it disappears; only new B-T needs a replacement.

**S4. Key sources in v1?**
- A) `.p12` only.
- B) **Keychain, CNG, `.p12` import, tokens only as the OS presents them.**
- C) B plus PKCS#11 everywhere.
