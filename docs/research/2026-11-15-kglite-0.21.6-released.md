# KGLite 0.21.6 is released: reader hardening and in-file full-text search

- **To:** rectopdf

Everything the reply of 2026-11-14 described as "on `main`" or "in progress" is in `kglite` 0.21.6 on crates.io and PyPI. Claims are marked *measured* (run on our side, release build) or *read* (from source). Real-data figures come from a 158k-node graph with 31 MB of text in one property over 57,798 nodes; your corpus was not measured.

## 1. What to do on your side

1. Move to `kglite = "0.21.6"`. The `.kgl` container is unchanged (v9); files written by 0.21.5 open as before, and 0.21.5 opens files written by 0.21.6 (*measured*).
2. Open any file you did not build with `verify="eager"` and a `max_load_mb` ceiling. A default open never panics or reads out of bounds, but does not prove a checksum-valid file is internally consistent.
3. Keep page text as a plain string property on nodes of one type. Nothing is declared and nothing extra is stored: search scans the property's column inside the single file.

## 2. Reader hardening (K6, K7, K2)

Unchanged from the reply, now released: the four panics are gone, `verify="eager"` and `verify_integrity()` check structure as well as checksums, `max_load_mb` bounds real decompressed size, `save()` errors instead of dropping an edge with a bad endpoint, and `docs/rust/kgl-container.md` specifies the container. A mapped open of a file without edge properties no longer walks the edge array: 67.3 ms to 22.5 ms and +189 MB to +51.5 MB resident at 1M nodes / 12M edges (*measured*).

## 3. Full-text search (K5a)

There is no text store and no index to declare. A string property of 256 KB or more is already a contiguous mapped column; the engine scans it in place.

| Surface | What it does |
|---|---|
| `text_match(n.p, query [, {mode, ignore_case}])` | Predicate. `mode` is `'literal'` (default), `'phrase'` (whitespace in the query matches any whitespace run, newlines included) or `'regex'`. |
| `text_hits(n.p, query [, options])` | List of `{offset, length, char_offset, snippet}` for one value. `offset` and `length` are bytes into the property value; `char_offset` counts characters. Options add `snippet_chars` (default 40) and `max`. |
| `CALL db.text.search({type, property, query, mode?, ignore_case?, within?, \`limit\`?, snippet_chars?}) YIELD node, property, offset, length, char_offset, snippet` | One row per occurrence, in node order. `limit` must be backticked. |
| `CALL db.text.rank({type, property, query, within?, \`limit\`?}) YIELD node, score` | BM25 with no index. The scope is the corpus: document count, average length and document frequencies come from the scope's own text. |
| `CONTAINS`, `toLower(n.p) CONTAINS`, `=~`, `text_match_regex` | Same meaning as before; they use the same scan with no change to the query. |

Searching inside a part of the graph (one PDF, a section, a tag, a region):

- Inline, in the pattern's `WHERE`: `MATCH (doc:Document {id: $d})-[:HAS_PARAGRAPH]->(p:Paragraph) WHERE text_match(p.text, $q) RETURN p.id, text_hits(p.text, $q)`. Cost follows the scope, not the corpus.
- Through a procedure: `MATCH … WITH collect(p) AS ps CALL db.text.search({type: 'Paragraph', property: 'text', query: $q, within: ps}) YIELD node, offset, length`. Use this form for `db.text.rank`, which has no inline equivalent.

Measured on the real graph, minimum of 15 runs, against 0.21.5 where a comparison exists:

| Query | 0.21.5 | 0.21.6 |
|---|---|---|
| Whole type, `toLower(p) CONTAINS`, term in 34 / 741 values | 37.2 / 35.5 ms | 1.25 / 3.40 ms |
| Whole type, `text_match` with `ignore_case`, same terms | n/a | 1.4–1.6 / 2.5–2.6 ms |
| Whole type, `CONTAINS`, term in 34 values | 3.26 ms | 0.78 ms |
| Whole type, `=~ '(?s).*\bword\b.*'`, 15 / 399 values | 503.5 / 503.9 ms | 0.98 / 5.34 ms |
| `db.text.search`, first 100 hits, phrase mode | n/a (16 ms fetching and searching in Python) | 1.2 ms |
| Scope of 4,907 nodes, `db.text.search … within`, 220 hits | n/a | 0.77 ms |
| Scope of 4,907 nodes, inline `text_hits`, all occurrences | n/a | 0.90 ms |
| Scope of 4,907 nodes, `db.text.rank … within`, top 10 | n/a | 2.1 ms |
| Scope of 300 nodes, `db.text.search … within` / `db.text.rank` | n/a | 0.085 / 0.22 ms |
| `db.index.fulltext.queryNodes … LIMIT 10` (existing BM25 index) | 11.9–21.8 ms | 0.014–0.94 ms |

Limits that matter for your design:

- The scan serves a single-label `MATCH` on a plain string property in memory and mapped modes. Other shapes fall back to per-row evaluation with identical results: disk mode, a property under 256 KB in a mapped file, `id`/`title`/`name` aliases, secondary labels, mixed-type or list columns.
- Regex: a pattern starting with `(?i)` or `(?x)` is not served by the scan; use `text_match(…, {ignore_case: true})` instead.
- Offsets are byte offsets into the property value. Map them to your rectangles on your side; nothing page- or layout-aware exists in the engine.
- No stemming, no positional index, no term dictionary, no relationship text, no line-per-record file for the `rg` binary. Whole-corpus ranked search still uses the existing BM25 index (`build_text_index`, `text_bm25`), which lives on the heap.
- Embeddings over the same property are possible later; nothing is planned for them in this cycle.

## 4. Unchanged answers

K1 (format crate) and K3 (segment updates) remain declined, K4 (nothing on the heap) remains "partly, on trigger", and K5b (application sections carried through save) is not started. The question from the reply is still open: do your rectangles and page numbers sit on edges or on nodes? A graph with more than 262,144 property-carrying relationships writes no mapped topology.

The file extension stays free: `library.recto` opens and saves like a `.kgl`.
