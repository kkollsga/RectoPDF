# Releasing RectoPDF

A release is **Developer ID signed and notarized**: a zip for people to download and for the in-app updater (SPEC decision 24). Nothing here publishes anything until a tag is pushed and its draft is published. It has run once: **0.1.0**, tagged on `dea9f10e` at 2026-11-11 23:29 UTC, release run 43120258114 (gate 14 s, build 7 min 38 s, signing 1 min 2 s, draft 10 s), published at 23:41 UTC. Each step is marked: **scripted, tested** (a script or workflow that has run for a real release, or is held by tests); **scripted, not run since 0.1.0**; **manual** (a person or the coordinator types it; no script); **missing** (nothing exists yet).

## Releasing

`.github/workflows/release.yml` runs when a `vX.Y.Z` tag is pushed, **all or nothing**:

1. *Tag and CI*: the tag matches `Cargo.toml`, the release notes are ready (`tools/release/notes.sh --check`), the tagged commit is on `main`, and CI passed on `main` on its code (`tools/release/ci-gate.sh`).
2. *Mac build*, a job with no secrets in it at all: `app/release-zip.sh --built-only` compiles everything, checks it reads no override, and runs it in a quiet run that opens a PDF and has to draw it.
3. *Mac signing*, in the `release` Environment, a job that compiles nothing and runs nothing of the product while a key is there: `--signed --already-built` signs what was built, notarizes, staples and zips it. The keychain and every file of a secret are removed, and then `--check-signed` runs the stapled app drawing a PDF, and checks the zip with the updater's own reader and Gatekeeper. The certificate's password reaches `openssl` by the environment, never a command line. The keychain's own throwaway password, made in the job, is on one.
4. *Draft release*: `RectoPDF-X.Y.Z.zip`, `SHA256SUMS` and `latest.json`, not published.
5. *Withdraw the tag* if anything failed or was cancelled, so a fix can tag the same version again. Never a release that's been published: run again after that, this fails and leaves it alone.

CI runs on pushes to `main` and `build/**` and skips a push that changes only `docs/**` and `*.md`, and runs once on a push's newest commit. So the gate asks about the tagged commit back to the newest on `main`'s own line that changes anything else: a green run on any of them checked the tag's code. (Until 2026-11-16 it asked about one commit, the newest that changed code on any line of history. For `v0.1.1` that was a branch's commit under a merge, no push had ended on it, and the gate waited its hour and withdrew the tag.)

**The gate's rules, since 0.1.2** (`tools/release/ci-gate.sh`, which says them at its top; `tools/release/ci-gate-test.sh` holds each with made runs and a made repository, and `release-test.sh` runs it, so `tools/check.sh --full` does when `tools/release/` changes). Until then the gate was shell inside `release.yml`, run only by a tag's push.
- **The tagged commit is on `main`'s own line**, or the tag is refused at once with words that say so: one `main` doesn't have (`git merge-base --is-ancestor`), and one `main` has only as a branch's commit under a merge, which no run on `main` was ever on. Either would otherwise have waited ten minutes for a run that couldn't come.
- **Only `ci.yml`'s runs on `main` from a push count.** A branch's green run doesn't: what's released is `main`, and a `build/*` branch's run checked the branch before its merge.
- **The newest run that wasn't cancelled decides**, among those on the commits asked about (up to 20 a commit). A run a newer push cancelled says nothing either way, so the gate looks past it to an older run on the same commit or the next commit down. A red run is refused, even with an older green one under it.
- **A run that went green on a re-run counts as a pass. That's meant:** a run is listed once, as its latest attempt is, and that attempt passed on this very code. On 2026-11-16 two of `main`'s runs never got a runner on their first attempt and went green on a re-run (`97f37dcef734`'s, 43844245994, on its third attempt); a gate that refused those would refuse for the runner, not the code.
- **How long:** a run queued or going is waited for, an hour in all; with no run on `main` for these commits, or only cancelled ones, ten minutes, as CI starts within seconds of a push. It then gives up, naming what it saw (a cancelled run's address, with "re-run it"), and *Withdraw the tag* deletes the tag.
- **Run as written against `main` before a tag** (the lesson of 0.1.1's first tag, `docs/PROCESS.md`), read-only: `git fetch origin main && tools/release/ci-gate.sh <commit> --repo kkollsga/RectoPDF`. On 2026-11-16 it passed on `main`'s head `78b77b71` (by run 43881731728 on `40f36f3f`, as `78b77b71` changes only documents) in 3 s, and on `97f37dcef734` (its re-run) in 1 s.

**What the gate doesn't see: a push that cancels an earlier push's run.** CI's `concurrency` cancels a run on `main` when a newer push arrives, and the newer run checks what's in its own push against the commit it came after (`tools/check-scope.sh`'s `ci_base`, the push's `before`). So the tools' own tests that the earlier push's changes would have run, and that the newer push's don't call for, are run by no CI on `main` at all. That's a hole in CI's scope, not the gate's: the tag's code still had a full green run, but not every test its changes call for. In the plan as a follow-up.

**A known limit: several commits pushed at once.** CI runs on what a push leaves at the head, not on each commit in it, so a tag on an earlier commit of the same push has no run of its own, and the gate waits ten minutes and withdraws it. Tag the head of a push, or push the commit to be tagged on its own first. The converting of the certificate by `openssl` has run since (the preflight of 2026-11-11 and 0.1.0's signing job): Keychain Access's `.p12` needed repacking, which `tools/release/keychain.sh` does.

The draft's body is `NOTES.md`, made by `tools/release/notes.sh` from `docs/releases/X.Y.Z.md`: the notes with an Install part if they have none (0.1.0's) and their Checksums block filled from `SHA256SUMS`. It refuses a missing file, one whose first line or links name another version, a placeholder (the marker is a line `<!-- PLACEHOLDER: what is to be put right -->`), and a body over 100,000 characters: GitHub refuses one over 125,000 by its API's message ("body is too long (maximum is 125000 characters)", as reported in github.com/intuit/auto/issues/2418), and its REST reference states no limit, so the number isn't from GitHub's own documentation. The release gate runs `notes.sh --check` before anything is built, and the signing job makes the body; a local ad hoc `release-zip.sh` warns and goes on without it. Until 2026-11-15 the body was every commit subject since the previous tag: 1,660 subjects for 0.1.1, about 241 KB, some describing the security faults in detail. For 0.1.0 the list was "- First release." and the published body was replaced by hand.

Publishing the draft is the moment every installed copy is offered the update, within a day. A draft or a pre-release never resolves as `latest`. For pulling one back, see [A bad release](#a-bad-release).

### What only publishing shows

None of these can be seen before the feed names 0.1.1: 0.1.0 is a release build, so it reads only the public `latest.json` (no override, checked by `release-zip.sh` and `check-draft.sh`), a draft or a pre-release never resolves as latest, its installer refuses a plan on any state folder but the user's real one (`not_the_users_state`), and `recto update install <zip>` takes only development builds. Each is listed with the smallest way to see it after publishing **without touching the owner's own copy or state, and each needs the owner** (a login, or a machine set up):
- **0.1.0 fetching the real `latest.json` and offering 0.1.1** (the menu's *Update to 0.1.1…*, Settings): a copy of the published 0.1.0 on a user state that isn't the owner's. Smallest: a second macOS user account on this Mac, or a macOS 15 virtual machine with a snapshot (Apple's Virtualization framework, as Tart or UTM use it), with `RectoPDF-0.1.0.zip` from the release put in `/Applications` there and opened once. A copy that has never checked checks a minute after launch, so this shows within minutes, not a day.
- **0.1.0's installer swapping in the notarized 0.1.1 on that user's real state**, and `launch-ok` across the versions (0.1.1 reading the record, a first frame, a page drawn by the real renderer, no fewer tabs than handed over): the same account or machine, with a few PDFs open and an edit unsaved, *Update automatically* on, and the app left untouched for 30 minutes; then `recto update status` (`updated`), its `update.log`, and `recto tabs`, `where`, `session show` against what was there before.
- **The background reopen on a real desktop** (behind other windows, `open -g`; full screen; a locked screen or a dark wake mid-install): the same, watched on that account's screen; the on-screen pass can show the reopen of a development build, not of a release swapped by 0.1.0.
- **Gatekeeper on a downloaded copy's first launch** (the quarantine prompt for the zip from the browser, and how long that first launch takes): the same account, with the zip downloaded by a browser, not by `gh`. A copy updated by 0.1.0 carries no quarantine, as the updater's own reader writes the files.
- **App Management's prompt, if any,** when a team-signed copy in `/Applications` replaces itself: the same account, at the swap. If it is refused, the old copy reopens and `recto update status` says `not_permitted`.
- **What a copy that goes back meets for real** (no `launch-ok`, or three early ends in the first week): only on a failure; `check-carry.sh` shows the same state transitions in quiet runs with the real binaries.

## What a person on 0.1.0 sees

All of this is 0.1.0's own code, which is what runs until the swap.
- **When:** 0.1.0 reads `https://github.com/kkollsga/RectoPDF/releases/latest/download/latest.json` once a day (a day after the last check, never within a minute of launch, an hour doubling to a day after a failure), always, whether *Update automatically* is on or off. So every running copy hears of 0.1.1 within about a day of publishing, and a copy that's closed hears at its next launch plus a minute.
- **The menu:** *Check for Updates…* in the RectoPDF menu becomes *Update to 0.1.1…*. A check by hand says "RectoPDF 0.1.1 is available. Choose Update to 0.1.1… in the RectoPDF menu." (with no window, in an alert).
- **With *Update automatically* on** (the default for a release): it downloads and checks the zip in the background (checksum, its own zip reader, bundle id, version, `codesign --verify --deep --strict`, the team's Developer ID requirement, Gatekeeper), waits until the app hasn't been touched for 30 minutes, quits, swaps, and reopens 0.1.1 behind other windows (`open -g`), with the session as it was. An install reads `latest.json` again before it starts. Note 0.1.0's fault: a Settings choice in the first moments after launch could have turned this switch back on.
- **With it off:** only the menu item; nothing is downloaded until it's chosen. 0.1.0's Settings has no *Update now* button (0.1.1 has).
- **The swap is 0.1.0's installer** (`Contents/MacOS/recto-updater` of the running 0.1.0): it waits for 0.1.0 to end, clones the record aside, swaps the bundles, opens 0.1.1, and waits for 0.1.1 to say `launch-ok` (it has read the record, shown a first frame and drawn a page of its own through the real renderer) with no fewer tabs than were handed over. If 0.1.1 doesn't, the installer puts 0.1.0 and its record back and reopens it, and that launch says so. The plan and `launch-ok` formats (`crates/recto-update/src/plan.rs`) are unchanged since 0.1.0.
- **What 0.1.1 does with 0.1.0's files**, seen with the published 0.1.0 and a 0.1.1 build by `tools/release/check-carry.sh` (2026-11-15, runs A and B): the record is the same version (1) and read as is; every tab, its place, its zoom, the unsaved turn, Find's text, the recent files and the view came back, and the whole of `qa state` matched but for the restore tests' own exceptions and this pair's (the menu bar, which gains Mark Up; the window's buttons a point lower; the time a quiet run set its level; and, seen again on the bump commit on 2026-11-16, Find's rows starting on a word, `left_picture_bytes` gone with the pictures, and `edits` saying what followed, each held to what its line says); old sleep files (0.1.0's, with pictures of pages) are removed by the pass after 0.1.1's first launch, in the record's `journals/` and in the copy of the record the update keeps for a week (`update/before/journals/`), and at any read before then, so each idle tab wakes once from its PDF (`from_sleep` false, for each); a going back to 0.1.0 writes pictures again, which 0.1.1's next launch removes; journals are read as before.
- **For a week after,** 0.1.1 is on probation: three early ends in a row (not a quit or a kill) send it back to 0.1.0 by itself, with the record as it is.

## A bad release

**Before it's published:** a failed or cancelled workflow deletes its draft and its tag by itself (*Withdraw the tag*), and a fix tags the same version again. A draft that passed but is wrong is deleted with its tag (`gh release delete v0.1.1 --repo kkollsga/RectoPDF --yes --cleanup-tag`): outward, so the owner's word, as tagging is. Nothing has reached anyone.

**Once the feed names 0.1.1, what can be undone:**
- **Copies that haven't installed it yet:** mark 0.1.0 as Latest again (`gh release edit v0.1.0 --latest`) or delete 0.1.1's release. `latest/download/latest.json` then answers 0.1.0's line, and a copy waiting to install reads the feed again before it starts and takes the offer off its menu (0.1.0's `updater.rs`: "an install looks again before it does anything"). The withdraw job never touches a published release.
- **A copy where 0.1.1 doesn't come up,** misreads the record, or ends early three times in its first week, goes back to 0.1.0 by itself (above), and holds 0.1.1 against the version so it isn't offered again.

**What can't be undone:**
- **A copy on 0.1.1 stays on 0.1.1.** A release copy is only ever offered a newer version, so there's no way to send it back to 0.1.0 from here: a bad 0.1.1 is fixed forward, by 0.1.2.
- **Never publish different bytes as 0.1.1.** A copy that took 0.1.1 is never offered it again, and one where it failed holds that version against it, so a second 0.1.1 reaches nobody who needs it. A version number, once published, is spent.
- **What a copy that went back meets,** seen with 0.1.0's own binaries on 0.1.1's state by `tools/release/check-carry.sh` (2026-11-15): 0.1.0 comes up with every tab, in order, on its place; reads the record (same version; fields 0.1.1 added are ignored); leaves a version-2 journal (one holding a highlight) alone byte for byte, so that tab shows the file without its edits and says `edits_unreadable`; and refuses 0.1.1's sleep files (format 4, facts only, with no `pictures` key), so a tab 0.1.1 put to sleep wakes in 0.1.0 from its PDF: run C taps tab #1, which 0.1.1 put to sleep, and 0.1.0's `qa state` says `reader.last_wake.from_sleep: false`, with the app still running after. Then, forward again (a copy that went back holds 0.1.1 against the version, so at 0.1.2): the tab with highlights wrongly says some edits couldn't be read back; and if the person edited that tab in 0.1.0, 0.1.0 wrote a journal of its own beside the version-2 one, and the highlights aren't shown: 0.1.1 keeps 0.1.0's list and sets the version-2 journal aside in the state folder as `journals/journal-….not-merged`, byte for byte (since `build/page-matcher-2`'s crash rule; before, it stayed under its own name), and the tab says `edits_set_aside_after_quit`, which is so of the lists but names an unexpected quit there wasn't (before, the wrong words "open in two tabs"). Nothing is lost from disk; nothing in the app brings the highlights back. Both are to be fixed before 0.1.2 is published (`docs/PLAN.md`, phase 7), and the 0.1.1 notes say it in *Known limits*.
- **What was downloaded** stays downloaded; the zip is public once published.

## The version

One source: `version` under `[workspace.package]` in `Cargo.toml`. `app/build.sh` writes it to the app's `CFBundleShortVersionString` (and `render-helper.sh` copies it into the helper's), which is what the updater compares. **`tools/release/bump.sh X.Y.Z`** moves every file that names it, from one table, and commits nothing; `bump.sh --check [X.Y.Z]` says whether the tree is at one version and which files disagree, and `release-test.sh` holds it on a made tree and on this one. The nine files:
- `Cargo.toml` (`[workspace.package]`), and `crates/recto-headings/Cargo.toml` (`[package]`, its own workspace's, which nothing compares; kept with the rest so the rule is simple);
- the four lockfiles' own packages (no `source`, named by a `crates/*/Cargo.toml`): `Cargo.lock` (19), `crates/recto-headings/Cargo.lock` (8: the 7 workspace crates and `recto-headings`; built `--locked` by `app/build.sh` and read `--locked` by `tools/notices.py`, so a stale one fails the release build), `fuzz/Cargo.lock` (15), `spikes/sandbox/Cargo.lock` (5). Third-party packages of the same version (`byteorder-lite` 0.1.0) and the fuzz and spike workspaces' own packages (0.0.0) are left alone. After rewriting, `bump.sh` asks cargo to take the main and the headings lockfile `--locked --offline`;
- `THIRD-PARTY-NOTICES.txt`'s first line, "RectoPDF X.Y.Z: third-party software notices", which ships as the app's `Licenses.txt` (`check-draft.sh` reads it in the bundle);
- `PRIVACY.md`'s "This describes RectoPDF X.Y.Z." and `README.md`'s zip name, `RectoPDF-X.Y.Z.zip`.

## How updates work

The app reads `<repo>/releases/latest/download/latest.json` once a day: `version`, `tag`, `minimum_macos`, `zip`, `sha256`, all written by `release-zip.sh`. See `docs/engineering/updates.md`, for the rest.

**A release build is whatever `RECTO_RELEASE=1` compiled.** `app/build.sh` on its own makes a local build, for tests and QA, which checks only when asked and never replaces itself. `app/release-zip.sh` and `tools/dev-build.sh` are the only two that set it. Don't set it by hand.

## Development builds

SPEC decision 28, with Seedwell's as the model. The owner's one RectoPDF is `/Applications/RectoPDF.app`, and it runs development builds between releases: `X.Y.Z.N`, Cargo.toml's version and a number counted from 1 for each, so `0.1.0` < `0.1.0.1` < `0.1.1`. A release never has a fourth part.

```sh
tools/sysguard/heavy.sh tools/dev-build.sh --first-install     # once, to start: builds and puts it in /Applications
tools/sysguard/heavy.sh tools/dev-build.sh                     # each time: app/build.noindex/dev/RectoPDF-X.Y.Z.N.zip
recto update install app/build.noindex/dev/RectoPDF-X.Y.Z.N.zip          # goes in once the app hasn't been used for 5 minutes
recto update install app/build.noindex/dev/RectoPDF-X.Y.Z.N.zip --now    # at once
recto update status                                            # build_ready, installing, updated, went_back
```

- **The owner's switch:** Settings › Allow development builds, off until they turn it on (`recto update dev-builds on|off` needs Full). Settings shows it only on a development build, or while it's on: the owner sees it from the first install on. Off, only releases go in, and a development build goes back to the latest release by itself once there is one, after 30 quiet minutes. **`update install <zip>` needs agent access Full** whatever the switch says, as anyone can sign a build ad hoc (a coordinator's default, fail closed, awaiting the owner).
- **Never the keychain.** Owner, 2026-11-11: "I need to approve the use of the keychain, that in some cases takes hours." A dev build is ad hoc, with no Developer ID, `security`, timestamp or notarizing, and its designated requirement is its identifier alone (`designated => identifier "io.github.kkollsga.RectoPDF"`; the helper's is its own), so macOS takes each build as the same app and keeps the folders it was given. `codesign -d -r- /Applications/RectoPDF.app` shows it. Developer ID and notarizing are for a release, in CI, on a pushed tag.
- **What's checked before it goes in:** the switch, an `X.Y.Z.N` named and inside, the bundle id, `codesign --verify --deep --strict`, ad hoc or not, and the signature's identifiers, the app's and the helper's. At the swap the installer reads the switch again, from the user's own state folder only.
- **Only over an ad-hoc copy:** a copy signed by the team, every release, never takes a dev build (`recto update install` answers `release_copy`). Where `/Applications` holds a release, the first dev build goes in by `tools/sysguard/heavy.sh tools/dev-build.sh --first-install --replace-release`, which waits for 5 idle minutes if it's running and keeps the release aside as `/Applications/.RectoPDF-update/previous/RectoPDF.kept`. **What's left, by the owner's signing decision:** an ad-hoc signature can claim any identifier, so a dev copy is only as safe as the user's account (SPEC decision 28).
- **App Management:** the first in-place update of an ad-hoc copy in `/Applications` may raise macOS's "modify apps" prompt once (System Settings › Privacy & Security › App Management). If the swap is refused (EPERM), nothing's replaced, the old copy reopens, and the status says where to allow it (`not_permitted`). Untested here, as it can't happen in temp folders: the refusal path is tested with an injected EPERM.
- **Numbering:** one count for every worktree, the next after the larger of the installed app's `RectoDevVersion` and the count kept in the repository's git folder (`tools/dev-build.sh --next-version` says it). It goes through the same hand-off as a release: the whole state, the old app kept beside it, and back to that if the build doesn't come up.
- **Builds:** the `dev-release` profile where `app/build.sh --dev-release` exists, else `--release`, into `app/build.noindex/dev/app`, so the tests' own build (a local one, in `app/build.noindex`) is left as it is. `tools/dev-build.sh --package <app>` is the last step alone, seconds, on an app already built.
- **One install:** build folders end in `.noindex`, so Spotlight doesn't index them; a quiet run forgets its own copy with Launch Services when it ends, and the tests forget every copy they made; `tools/check.sh --full` ends with a check that nothing of this tree's is left registered.

**What 0.1.0 proved, and what's still unproven.** 0.1.0's run showed a real Developer ID build passing the team and Gatekeeper checks, the `--signed` and workflow steps, and its zip surviving the updater's own unpacking with its ticket and signature (`--check-signed`, and the downloaded zip checked by hand: `docs/PLAN.md`, phase 7). Still unproven, as no update from a release has happened yet: the swap of a notarized bundle by a release's installer, what a background reopen does to a real screen (the code sends the window behind everything and waits to go into full screen, and nothing here has seen it on a desktop), and how long a first launch takes under Gatekeeper. `docs/PLAN.md` carries the item (phase 7, "A real signed update end to end"), and [Gaps](#gaps-before-011-can-be-run) item 1 says what stands in its way; steps 9 and 10 of the sequence are the part that can be had before publishing. The refusal side is tested.

**Hardened runtime:** a signed build runs under it, and the renderer loading `libpdfium.dylib` needs that dylib signed by the same team, which `build.sh` does. Tried on this Mac with the owner's Developer ID on 2026-11-08, not notarized: the sandboxed helper loaded the library under library validation and drew.

**The renderer helper.** PDFium's worker is in `Contents/Helpers/RectoRender.app`, sandboxed, laid out and signed by `app/render-helper.sh`, from the inside out and never with `--deep`. `release-zip.sh` runs `render-helper.sh --check` on the built app, the signed one and the one in the zip, and fails if the worker isn't sandboxed with exactly its one entitlement, isn't signed by the app's team with the hardened runtime, or anything could run in its place unsandboxed. A Developer ID build's helper is `io.github.kkollsga.RectoPDF.Render`, and an ad hoc one `...Render.adhoc`, so no container a development build left behind meets a release.

**The identity goes to codesign by its SHA-1.** codesign reads a name on its command line as Mac Roman whatever the locale, so a name with an "å" in it is never found. `RECTO_SIGN_IDENTITY` stays the name, matched against the keychain search list byte for byte, the same list the workflow looks in. Two valid certificates of one name are refused, naming both hashes, and an expired one says it has expired. Only `build.sh --sign-only` reads `RECTO_SIGN_IDENTITY`: every other build, `tools/check.sh` and the tests sign ad hoc whatever the shell has set, so none of them raises a keychain prompt.
