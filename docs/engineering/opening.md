# Opening: recent files, files that change, passwords

> Part of the engineering notes: [`README.md`](README.md).

**Encrypted files.** `facts` says when a file is encrypted and opened with no password, because `encrypted` alone reads as though its contents are protected from whoever has the file. Checked on `un_report_un_sdg2023` and an AES-128 fixture.

**Recent files** are a list of at most 20 paths in the session, newest first, in the state record as `recent` (read up to 256, held to 20, relative paths dropped), moved to the front on every open and every return to an open file. File > Open Recent is a submenu Rust lists (`MenuEntry::parent`), and the UI thread reads the list from what the session thread last published, never the session. The published list is built again only when the session's `recent_version` or the tabs' version has moved, not at every reconcile. Each item's id is `recent.<key>`, sixteen hex digits from the path (`menus::recent_key`), and `AppCore::open_recent` takes that key: the item opens the file it showed however the list has moved since, and nothing if that file has left the list. `recto recent` needs Control, names and paths alike (coordinator, review O7): the names of files someone's closed say what they've been reading. A palette that lists menu entries skips those with a `parent`, so a recent file called "Close" can't stand in for the Close command.

**Files that change while open.** Before this a tab's file was looked at on restore, before it's shown and when it wakes from its sleep file, and a worker that saw its file replaced said so. Coming back to the app from another now looks at each file showing too (`CoreCall::LookAtShown`), since that's when a person has been elsewhere changing it. Each look is a stat on a thread of its own, as a wake's is, and `sleeper::LookSlots` holds them to one per tab and 8 in all, so ⌘Tab over and over with a hung SMB volume adds no threads past those; a look that's skipped happens at the next of those moments. No watch is kept. A file that's changed says "This file changed on disk since it was last read here", which blames nobody: a headless `recto` session saving it is RectoPDF too.

**A file the structure reader refuses at a limit opens to be read through PDFium alone.** `recto_core::agreement::refusal_of` turns the fork's caps (revisions, entries, structure windows, object and stream sizes, resolution depth, page count, page-tree depth) into `OpenError::TooComplex`; `recto_agent::loader` then asks the renderer as it does for `NotPdf`, and the tab opens renderer-only, edits refused and so nothing to save (coordinator's decision, review round 1). The indexer and `recto signatures` treat it as they treat `NotPdf`. `TooComplex` is what's said when PDFium can't read it either. Each worker start pays PDFium's own cost of reading such a file: a chain of 100,000 `/Prev` sections took 3.4 s to load where the fork refused it in about 3 ms, which is accepted. Opening itself runs on a read thread, never the UI thread (`40be99e`): `opening_a_slow_hostile_file_never_holds_the_window` opens three sections relisting about a million numbers each (`recto_testpdf::relisted_xref`), 3.5 s of lopdf's time in the debug app, by `recto open` and by Open Recent, and the window's worst wait was 15 ms.

**Passwords.** `recto_platform::Password` (re-exported as `recto_core::Password`) is the one place a typed password lives: no `Clone`, no `Serialize`, a `Debug` that hides it, overwritten on drop. It's in `recto-platform` so the renderer's host holds the same one: `DocRenderer` keeps an `Arc<Password>` shared with the keyring, not a copy. `inspect_with_password` opens with it; `checked_reader` tells the reader's `PasswordRequired` and `InvalidPassword` apart, which before read a user-password file as "not a PDF". The page views share a `Keyring`, keyed by the file's device and inode rather than its path, so a file moved while open keeps its password and another file put at its path doesn't get it; the renderer looks its key up by the open file's own identity (`fstat`). The session thread lets go of any key whose file no tab has open, at most 64 are held, and reads of a protected tab that went cold use its key, so it doesn't ask again. If a renderer finds a file needs a password it has none for (a file moved to another volume or replaced while open), it tells the app (`Engine::take_keyless`), the tab's facts are let go and it's marked as needing its password (`Session::needs_password_again`), and the sheet asks again.

**A password is for the tab it was typed for** (review round 1 of the measured faults, 2026-11-14). A file that needs a password can't be added to another document, as the loader that adds pages is given none; but a crafted file lopdf reads with no password while PDFium asks for one (a different `/Encrypt` seen through an update chain) is added as plain. So the page view's workers use a key only for a job of the tab whose own file it is (`added_needs_password` in `recto-reader`'s run loop): a page added from such a file says "This page comes from a PDF that needs a password, so it isn't shown here. Open that PDF to see it." and draws nothing, whether the key's held or not, its document isn't asked for a password, its text isn't read and its links aren't followed; workers are shared by path, so it's the job's tab that decides. The person's own Find reads only the document's own file with a password (`search::Reader::key_of`). A page from another file that needs one is, to Find and to an agent's `find`, `search` and `text`, a page that couldn't be read, as the page view draws it: skipped and counted, and the search goes on (Find's line says "1 page couldn't be read", `search` lists it in `failed_pages`, `text` of it is `page_unreadable`); before the second review it ended the whole search as "This PDF needs a password." on a document that needs none. So what a password protects is never shown in, pictured in the sleep file of, or read by an agent from a document it wasn't typed for. An added file that needs no password draws as ever. **A key ends with the tab it was typed for** (the second review, 2026-11-14): the keyring keeps it only while a tab has that file open, cold ones included, and a renderer given it (`OpenDoc::keyed`) is kept only while its path is the own file of a tab the page view holds, hot or warm (`let_go_of_unwanted`), not as long as any tab wants the path, as a document with a page added from the file does. Dropping the renderer kills its worker, whose copy of the password and PDFium's key schedule go with the process, and lets go of its share of the `Arc<Password>`, which is overwritten when the last holder lets go. Before, with the own tab closed, the renderer stayed for the document that added the file and kept the key, and a tab opened on the file again, not marked protected as no key was held to read its facts with, drew on it with nobody asked; now it meets a worker with no key, asks for its password, and is withheld from agents meanwhile (`core::headless::encrypted_sleep`). `keyed` goes by the opened file's identity and `own` by path, so a hard link or symlink to the file used as an added file's path is refused too: its renderer finds the key by identity and the job isn't its tab's own path (the safe side).

The sheet is the system's `NSAlert` with an `NSSecureTextField`, in Rust's words (`passwords::prompt_for`). Several files can want a password at once: each is an `Ask` with its own id, waiting in turn in `passwords::Asks` (at most 8), and the prompt carries its id to Swift and back with the answer (`AppCore::password_answered(id, password)`), so a password always goes to the file the sheet named. What's typed is tried on a thread of its own, and the field is emptied. A restored protected tab has `password_needed` as its problem, and is asked about when it's showing; Cancel leaves it saying it needs its password until the person goes to another tab and back. Wrong tries are kept per file until it's opened again (File > Open, Open Recent, a drop), whichever tabs are visited meanwhile, and five stop the asking for that file.

**The copies of a password that remain.** Rust overwrites what it holds: `Password` on drop, the `String` UniFFI hands over (`Password::take`), and the open frame sent to the renderer's worker once it's sent (`secret::wipe`). Others aren't ours to overwrite: the Swift `String` from the secure field and the UniFFI buffer it crossed in, as Swift strings can't be zeroed; the copy lopdf takes out of `IndexedReaderOptions.password` and drops once it has derived the file's key, inside `IndexedReader::open_with_options`, since the options are moved in (a fix would be in the lopdf fork); the worker's copy of the open frame, and PDFium's own C string and key schedule inside the walled worker process, which go with the worker. None is ever written, logged or put in the record.

**Agents and protected documents.** A tab opened with a password the person typed is marked (`TabRecord::password`, kept in the record as `password`), and `Session::withheld_from_agents` is true for it, and for any tab that needs a password. `encrypted` isn't the gate: a file anyone may open can be encrypted too. Every agent command about such a tab, and `find` while it's the document being read, is refused with exit 8, `protected`, before the tab is touched (`recto_agent::execute`), except `where`, `tap` and `close`, which read nothing of it; and everything that lists tabs leaves out what was read with the password: `where`, `tabs`, `session show` and `compare` give no page or length and say `protected`, `sidebar` gives its tab row and none of its contents, and of the events leaving for watchers, one rule for every event however it comes (`recto_control::server::outlet`, by `recto_agent::withheld`: a command's, the person's on the session thread, a page drawn, the Finder's news, the helpers'), exactly these go for a protected tab: `tab_opened`, `tab_activated` and `tab_closed` (its tab and its file's name, as `tabs` gives), and a comparison's `view_changed`, which names it among the panes by its tab as `compare` does; nothing of its place, drawing, layout, saving or edits (whether one of the person's took can turn on its length), nothing of Find while it searches or is being read, nothing of the helpers' work on its file (the person can set one going; it stops before anything's decrypted, but its time, peak and key would tell), and nothing about a tab after it has closed (news is judged when it's sent, so a draw told after the close is held back; a plain tab's late news too). `tabs`, `where`, `session show` and `sidebar` give it no `edited`, undo or redo, and `session show` no zoom, layout, notice or Find query while it's read. **Comparisons** (security reviews of phase R, S2 and its round): `compare` gives no `note` (both lengths) and no `sync_from` while a pane is withheld, and an agent can't make a synced comparison with a protected pane (refused as `protected`, decided on the comparison as it would be after the change, in the same hold of the session as the change; separate scroll is allowed). A plain tab synced beside a protected one follows its place and stops where it ends, so its place is withheld too, by one statement, `recto_session::compare::place_withheld` (`place_withheld_of` for a tab in hand): while it follows; and after sync is off or the comparison ends if any move of it, to another page or down its page, was made while it followed, until the person next sets it themselves by an absolute move (their `goto` or page field, a contents row they click, a link with an absolute target they click, a Find hit they choose by its row; to the page it's on too, so a jump there says nothing a jump elsewhere wouldn't). **Nothing an agent sends lets it go** (the third review, the coordinator's D-A, 2026-11-14): an agent's jump of any kind (`goto` by page, label or entry, `open --page`, a link it follows, a Find hit chosen by its index, a contents or palette row or menu id it runs) moves the tab as ever and leaves its place withheld, and what it leaves on the trail is marked as any stop made from a withheld place is. The rule is stated once, where `Session::jump_as` decides by the actor, and `no_agent_command_lets_a_withheld_place_go` (every command of the walks in sequence, on twins) and `no_menu_id_an_agent_runs_lets_a_withheld_place_go` (every menu id) hold it. So for an agent a withheld tab stays withheld however it moves it: its answer says `place_withheld` and no place, alike for twins, no guess can be checked against where following left the tab, no draw of it is heard, and nothing derived from its place is shown, for as long as the flag is set. For the person one thing is better: an agent's `goto` on a withheld tab in the background no longer drops that tab's remembered zoom and place. The person's own scroll, page keys, ⌘G, Back and Forward, zoom and layout keep it withheld, as where they land is a function of the place, and so do the page view's reports that aren't a move (the second review, D-1). **Withholding carries through syncing** (S-1): the comparison's rules ask one root, a tab withheld on its own account (its document, or the flag), so a tab synced beside one left by following follows it withheld, `compare` gives no note or `sync_from` while any pane is such a root, and an agent can't make a synced comparison with one (`place_withheld`). Its length and words are its own and still given. The flag is in padding the tab's record already had (`TabFile`, 72 bytes with 1 of padding left; `TabRecord` 224), and is kept in the state record as the session's `withheld_places`, the ids of such tabs as `active` and the comparison name them, left out when empty, so a restart or an update's hand-off keeps it (S-4; a field with a default, no new version: an older app ignores it, and a record with nothing withheld is byte for byte as before). It's read capped at the record's tab count, an id that names no tab is ignored and a repeated one is one, and anything else fails the record as damaged. It's part of the bare record (`record::without_what_deltas_carry` keeps it), so a change to it is a whole write, never only a line of places, and what's read back after a crash withholds what the last write did (fail closed). It was a field of each tab entry, flattened from a group of two (the third review, D-C): a flattened field makes serde keep every key of the entry it doesn't know, so a forged record grew by what it said before any cap; the entry's fields are plain again, `password` where it always was. **Letting it go drops what came of it** (S-2, `compare::let_go_of_place`; the person's jump alone does it): the tab's draw notes and a jump on its way, the exact place the page view last said (on the page the jump goes to it would give how far down and the zoom only then), and every draw of the tab asked of the page view before the jump's send (S-3): a draw carries the place clock it was planned at (`Job::asked`), the mail keeps the jump's send as the tab's cutoff (`ViewWord::released`, 56 bytes, one per hot or warm tab, at most 3), and the session thread, the draw's one source of news, notes and announces none asked before it, for `wait page-drawn` and every watcher alike; a tab never withheld costs one compare a draw. **The cutoff is in effect the view's arrival** (the third review, D-B): until the host arrives where the jump sent it the view is where it was, so a draw planned in that gap is stamped 0, before every cutoff (`recto_reader::tiles::place::asked_now`, one branch a plan), and dropped for that tab while every other tab's is told as before. **Nothing a view says of before the release is taken in** (D-B): while the jump waits to be sent, and once it's sent for a read stamped before the send, what a page view says of the tab's place is skipped (`mail::view_told_of`), so a view holding it warm in the background, or a read taken in between the person's jump and the look that sends it, can't put the old place back on the page the person went to. No new state: the cutoff's own word. A cold tab gets no word in the mail by a release, and the mail stops looking for cutoffs once no tab has one. Find's hit gone to last stays marked if it was stepped to from the place, as a step goes on from it. **One way to a tab's place:** every answer an agent gets has a tab's place only through `recto_agent::place::place_for(session, actor, &TabRecord)`, `None` to an agent while it's withheld and always the person's own: `where`, `tabs`, `session show`, `sidebar` (a withheld tab's contents rows left out, as which are open follows where the reader is), `compare`'s panes, `edits` and every edit's, undo's, redo's and save's answer and its note of a page removed, `follow`, `back`, `forward`, `goto`, and Find's `current` and `went_to`; a scan of the crate (`every_read_of_a_tabs_place_goes_through_place_for`) fails on any other read of one not on its reviewed list. Of the events leaving for watchers, the plain tab's place, drawing, saving and edits news, and Find's news while it or the document being read has its place withheld, are dropped. **What starts from the place:** each command says it (`Cmd::starts_from`, no default): `back` and `forward` (to the trail's stop), Find's steps (from the place or the hit gone to last) and `--hit`, and `contents fold`; `recto_agent::execute` refuses an agent's with `place_withheld` (exit 8, next: "Its place is given again once the user has gone to a page in that tab themselves. Nothing an agent does gives it back.") while the tab's place is withheld, the stop was made from a withheld place, or Find's hit gone to last was stepped to from one; a link that goes Back or Forward the same, and the palette's or a menu's Rotate of this page in edit mode. A stop on the trail made from a withheld place is marked (`Stop::from_withheld`, in the stop's padding, kept in the record as `withheld`, left out when false), and the person's Back or Forward onto one lands where it always did with the place withheld again. A jump from a withheld place to the place it's on leaves a mark only (`Stop::mark_only`, D-2), so the trail says the same whether or not it went where following left the tab: the person's Back goes past it, landing where it would have with none and withholding where it lands, Back is offered to the person only for real stops, a mark isn't counted against the cap, and an agent's stop from a withheld place that would give way at the cap stays as a mark; an agent is offered Back and Forward (`where`, `tabs`, the palette) by the gate's own rule (`place::trail_offers`); the person's ⌘G from a withheld place goes to the hit it always did, and the place, and that hit, stay withheld. `session restore` by an agent is refused (`place_withheld`) while any tab's place is withheld by the flag or any trail holds a marked stop, as a record from before this build has neither and keeps the place (the record now keeps both: S-4). As no agent can let a place go, that lasts until the person moves in the tab themselves (and the marks on its trail go as stops do, by the person's jumps and the cap) or closes it. While any tab's place is withheld, `session show` and `session save` give an agent none of the record's sizes and counts (`record_bytes`, `journal_bytes`, `writes`, `appends`, `wrote_bytes`, `edited_tabs`), which move with what the record holds. **What remains, and why:** the person's own action on the page they're reading in a tab whose place is withheld (an edit of this page, a highlight) says which page it is through what it made; the record's counters (`writes`, `appends`, `wrote_bytes`) count from launch and are nulled only while a place is withheld, so their change across the stretch says how much the person moved (low bandwidth; PLAN); after the person's own jump in a tab whose place was withheld (the one release there is), how many of the page they went to's tiles are drawn again follows what the page view had already, so the draw news for that page (how many `page_drawn`, and in the limit whether any and so whether `wait page-drawn p` meets) says whether following had left them on or beside the page they chose: one membership test a release, driven only by the person (the second review's S-3 residual; announcing the settled view's pages once instead would need the view's arrival told to the session, which it isn't: PLAN); the same follows a later jump in a tab once released, whose draws planned while that jump is on its way are dropped too, so `wait page-drawn` on a page the view had on screen before it can miss; the person's choice of a Find hit by its row lets the place go with no jump sent, as the app brings the hit into view itself, so the cutoff is the first read of the views after it: a read by another thread (the saver's, a command's) in the moment between the choice and the hit brought into view puts it before the view moves, and a draw planned at the old place then is told, a race the person's own click opens and no agent drives; a record written before this build has neither the flag nor the marks, so restoring one gives the place following left; and `session restore` by an agent stays refused while any place is withheld or any trail holds a mark. **Accepted, and why:** an agent's `close #N` and `session stop` answer differently for a protected tab with the person's unsaved edits (refused, naming the tab) than for one without: that's the person's activity, one bit, and saying nothing would let an agent close over unsaved edits or leave it unable to act; and Find's news about a plain tab is held back while the tab being read is protected, as Find goes with the document being read; and `wait` on its pages, index or contents fails as protected. `find`'s answer gives no hits from such a document, whichever tab is being read by then. The person's own Find does search it: the app hands `SessionHost` a lookup into the keyring (`set_persons_keys`, `recto_agent::keys::PersonsKeys`), which only the person's own door puts in an access (`SessionHost::run_for_person`, and `AppHost::run_for_person` over it; what the server calls, `Host::run` and `Host::check`, never has it, whatever actor it's given, and the access gives it only to the person's actor), and a plan with it (`FindPlan::with_keys`) reads that file page by page through a worker opened with the password, never reading, building or asking for a corpus, so its text is never written. An agent's `find` and `search` plan without it. Find still looks a file's key up by the identity of the file at its path when it reads it; Print looks it up by the file it has open. **The person's print of it** (2026-11-14; at v0.1.0 and before this, File > Print said "This PDF needs a password."): the window's print is the person's `print` with no file named, run through their door, so it gets their keys; `print.rs`'s `key_for` alone asks them, for a page of the tab's own file and by the file it opened, so a page added from another protected file stays unreadable (the print says it needs a password) and a file put at the path after the password was typed gets none. Its copy flag is read with the key (`copy_restricted_with_password`; without it the read failed open). It's written to a file with no name: made 0600 and unlinked before its first byte (`OwnTemp::create_unnamed`), handed to the window as its descriptor (`/dev/fd/N`, which CoreGraphics opens and maps), and freed when the window lets it go, on Stop, the tab closing, a quit, or however the app ends. Only a print with no name gets the keys, so a document opened with its password never lies on disk as a plain copy with a name. An agent's `print` of it is refused before it runs, as before; the server's route, whatever actor it names, carries neither the keys nor the window's watch. **Accepted:** `session check` says `busy: printing` for as long as the person's print takes, and an agent's exports wait behind it for the heavy slot when a page needs it (timing only, the same for any document); `qa print-to-pdf` on a protected tab shown drives the person's own print, as `qa as-person` does: QA is the harness's, in a quiet run and refused in a release. The print job's name in the system's queue is the file's name, never the title read with the password, and the print's own PDF has no `/Info`. `links`, `follow`, `back`, `forward` and `goto label` are refused like the rest, page labels go with `where`'s place, and the page view's own link reading (`DocRenderer::read_structure`) uses the shared `Arc<Password>` and never reaches an agent. Reading a protected document needs the person's consent per document (agent report §5.5), which isn't built, so until then nothing gets through. `qa state` and `qa shot` read the window, but a quiet run's `qa password` only types into the sheet for a file in its state folder or a temp folder, and reads the password from stdin, so a quiet run can't open one of the person's own protected files.
