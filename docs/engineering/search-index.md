# The search index

> Part of the engineering notes: [`README.md`](README.md).

**The corpus.** A document's pages as text on disk, one folder per version of a file, under `~/Library/Caches/RectoPDF/corpus.noindex/<key>/v3/`, or the state folder's `corpus.noindex/` with `RECTO_STATE_DIR`, so a QA run leaves nothing anywhere else. `app/` holds what the search reads: `text.pack`, each page's exact normalised text in turn, and `pages.bin`, a fixed record per page. **The text is kept once.** `agent/` holds every page again, as `manifest.json` and `pages/0001.md` onwards, the way the agent report's §6.1 has it for Phase 6's `Read` and `Grep`. Nothing reads that yet, so a build doesn't make it: `recto index --agent` does, from the pack alone, with no PDF involved (owner, 2026-11-07: "Feels a bit inefficient?"). No page's text is in memory past that page, and the session holds no state about any of it. `crates/recto-index/src/corpus.rs` has the layout.

**A page's file** starts with a line a page can't write, `<!-- recto page=12 cite="PDF p. 12" text=native hidden=clean untrusted=document_text -->`, and line `n` of the page is line `n + 1`. It's the page's text as it is, so a plain `rg` works and a phrase over two lines is a plain multi-line search, which a `| ` on every line, as `text` prints them, would break. A line holding text that looks hidden starts `! `, with the words inside `[hidden: ...]`, by the same code as `text`. A page's own line that would read as one of those marks gets a `\` first, so `! ` at the start of a line means what it says, and no page can write the first line's comment. The other spellings of hyphen decisions go last, so `Grep` can find those too. Pages that couldn't be read or have no text say so in words. `cite` is only `PDF p. N` until page labels exist.

**Keyed to what the file is.** The key hashes the device, inode, size, modification and change times and first and last 64 KiB. A file replaced with its size and time put back has another inode, or another change time if written in place, so its old text can't answer for it. It takes one `fstat` and two small reads, because every search asks for it, which is why it isn't the agent report's hash of the whole file: 2 GB takes seconds. So a copy gets its own corpus, and a moved or touched file is built again. That costs time and is never wrong. A build checks the key every 64 pages and at the end, and throws away what it's read if the file changed. Reading a finished corpus only ever answers for the version just looked at. Its name and path aren't in the key or in the folder. **Only a file on APFS is indexed.** Its nanoseconds and a change time nothing can set are what make a same-size rewrite show. exFAT has no change time, and at best 10 ms on its modification time, HFS+ has whole seconds, and a network volume says what its server says. Reading more of a file wouldn't settle it short of the whole of it, per search, so a search of a file on those reads its pages, as it always has, slower and never wrong, and `index.note` says why. Checked on this Mac: `/Volumes/EksternalHome` is APFS, and a file on an exFAT disk image was refused with exit 1 and its search read pages, with nothing written. A volume's device number can change when it's mounted again, and that costs a rebuild.

**A folder from an earlier build.** Before it was named `corpus.noindex` it was `corpus`, with plain text that nothing here would otherwise look at. A session's start removes that one folder, and not a link there or anything named like it.

**An old version's text goes.** Each key stands alone, so a saved edit, a redaction or a file since encrypted would otherwise leave the old version's plain text. `by-file/` holds a small file per hash of a file's path, of where that really leads, and of its inode, each with the keys it's had, so a new version at that path, or the same file renamed, is connected. None holds a path. A key is noted before a page is written, so a build stopped partway can be found too: that's the redaction case. When a build for a new key finishes, or the new version is refused, the other noted keys' folders go, and one that can't be removed stays noted. `recto index clear` takes every version on record, even if the file's gone. Until then the old text stays: an edit nobody has searched or cleared since hasn't told this anything.

**What makes it build.** Someone asking: a `search`, `recto index`, or `recto wait indexing-done`, which would otherwise wait out its time on something nobody started. **Never opening a tab or switching to one,** so 200 open tabs cost nothing here, and a tab holds nothing about its index. One helper runs at a time for the whole session, and at most 16 files wait, the newest ask first and the oldest giving way. Whoever still wants one asks again, so nothing's lost. `crates/recto-control/src/indexing.rs` has the rest.

**What stops one.** `recto index clear` takes a file off the queue and stops its build before clearing, so the queue can't write it all back, and it gives the helper up to 3 s to go. Lowering access to Off stops whatever's running and empties the queue, since those are agents' asks, and the user has said no. What's written stays until something clears it. Nothing starts again until someone asks.

**The helper.** `recto-indexer` is a process of its own at QoS utility, set as it starts (`recto_platform::helper`, `posix_spawnattr_set_qos_class_np`), a clamp that every thread of it and its render worker inherit (`ps -M` shows them at priority 20, against 31 for an ordinary process), and it exits when done, as `SPEC.md` §2 has it. So what it uses ends when it does: a page of two million characters takes tens of megabytes to read, and the session's footprint stays where it was. It takes its job on stdin, so a file's name stays out of `ps`, and it ends as soon as stdin closes, so it can't outlive whoever started it however they ended. The session's one thread for it exists only while there's something to build. `stop` closes that pipe. Anything that stops it leaves a usable state.

**Its level, and the headings helper's** (2026-11-11, `recto_control::helpers::HELPER_PRIORITY`). Both helpers ran at Darwin background until GitHub's virtual Macs starved them: `wait indexing-done` timed out at 60 s on a four-page file in three CI runs in one day, and generated contents didn't come. Every job either does is one someone asked for and is waiting on, so both run at utility, set by the session as it starts them. Darwin background isn't only a lower share of the processor: its disk reads wait behind anyone else's. Here, reading 64 MiB uncached from the external SSD while two other processes read from it took 1.1 and 1.3 s at the default level, 3.7 and 3.4 s at utility, and 12.1 and 12.1 s at Darwin background; the kernel's own throttle periods are 5, 15 and 25 ms an I/O on an SSD and 40, 85 and 200 ms on a disk it doesn't take for one (`debug.lowpri_throttle_*`), which a virtual Mac's may be. With every core running three `yes` and four uncached readers, `the_sidebar_offers_generated_contents_and_labels_them` took 25.4 s at Darwin background and 16.4 s at utility, against 2.1 s on this Mac as it was, and `a_search_in_the_app_gets_its_index` 3.5 s and 3.2 s, against 0.9 s; the 60 s timeout wasn't reproduced here, as this Mac's scheduler still gives a background process a share. **The window while they work,** a debug build's quiet run with NASA's 383-page report generating and USGS's 28 MiB report indexing, scrolled at 6 pages a second in 5 s sweeps, before and after in turn, under other agents' builds (load 3 to 20): no UI stall of 1 s or more in any of six runs, the worst 63, 94 and 58 ms at background and 45, 40 and 113 ms at utility; a sweep's p99 step 1.3, 2.8 and 1.2 ms at most at background, 6.2, 2.7 and 3.5 ms at utility, the median sweep's p99 1.3 and 0.6 ms against 0.4 and 1.2 ms, as much from the load as from the level. The index was built in 13.4, 20.9 and 13.4 s at background and 6.1, 14.0 and 14.1 s at utility; the debug headings helper didn't finish NASA's report in 10 minutes at background and did in 434 s at utility.

**Killed at any moment, it's sound.** A page's text is written, then its record, and only a record counts. Starting again checks every record against what's there, cuts off anything past the last that holds up, and goes on from there, coming out byte for byte the same as a build never stopped. `ready.json` goes last, after a sync of the pack and table, and nothing is used without it. An agent's folder has its `manifest.json` written last. **Page files aren't synced:** on this disk an `F_FULLFSYNC` costs 5 ms a file against 0.09 ms with none (load 12 to 17), so 383 pages would be 2 s and 10,000 pages 50 s, for a cache. Asking for the folder checks each file's size against what it should be and rewrites any that's wrong, so an empty or missing page after a power cut is mended when it's next handed out.

**Its limits,** from outside. 256 MiB for its worker, half a reader's, with no heavy step: only the hidden-text check draws, and by the numbers above 17 of 5,872 real pages need more at 2x. Such a page reads as `hidden=not_checked`, and a search draws it if it ever finds something on it, under a reader's limits. After 16 such failures in a document the rest go unchecked, because kills are capped per document, and spending them all on a check would leave pages unread. 10 s a page, twice a reader's, since this is on the slower cores. 512 MiB a document, past which it's refused and its text removed. 200,000 pages. An hour for a build, after which the next ask goes on from there. All corpora together 2 GiB, the least recently used going first, and anything unused for 90 days (agent report, D6). That's looked at when a build ends, however it ended, and on the first ask of each session, on the indexer's thread, so a deleted PDF's text goes at 90 days without any build. It doesn't go sooner: nothing here can see that a PDF was deleted, and `recto index clear` is how to say so. A full disk gets at least 64 MiB back, however far under its cap the folder is. Only folders named as keys are ever looked at or removed. A file that needs a password has nothing written, and `refused.json` holds only that. A file readable with no password is indexed, as `text` reads it: `aes_128` and the like. The real `form_bomb` fails its page in 2.4 s, where a reader's limit sequence takes 3.1.

**A page that fails.** What goes down depends on whether it's about the page. A worker that can't be started, or a failure remembered for only a moment (`Unavailable`), writes nothing: the build stops where it is, and goes on from that page after a pause. A worker lost to a deadline or for no stated reason may be the moment, not the page, so the page goes down as failed, the rest carry on, and it's read again at once, and up to 3 times in all, 10 minutes apart if someone's still searching, 64 pages a go. Past its memory limit or breaking the protocol is the page's own doing, and it isn't retried in a build. A failed page in a corpus is only what happened when it was built, so **a search reads it live, like `--scan`**, and `route` says `mixed`, up to 5 s of that per search. A worker's deadline is 5 s a page and 128 kills a document, so 10,000 bad pages would otherwise use up every search on its first few. Past the 5 s they're listed as failed with no worker, counted in `failed_pages_not_read_again`, and the clean pages behind them are still read. So answers from the index and `--scan` differ on a file like that, since `--scan` stops at its 30 s. Drawing to check for hidden text stops at the deadline too: a page past it says `checked: false`, and a ranked search leaves out top pages past 5 s more, in `top_pages_left_out_for_time`. The agent's folder and the manifest say what the build found.

**Not trusted when read back.** Lengths are checked against the file, text as UTF-8, and a corpus that doesn't add up is thrown away and built again, which only costs time. The search goes on by reading pages, in the same answer.

**Spotlight and backups.** The folder is named `.noindex` and carries the attribute `tmutil addexclusion` sets, byte for byte. Checked on this Mac, 2026-11-07: a test file with a unique word in a folder under the home showed up in `mdfind` within 25 s, and its twin under a `.noindex` folder beside it didn't, which the name alone explains, though one try on one Mac isn't a promise. `tmutil isexcluded` says `[Excluded]`, and a test holds that. No Time Machine destination is set up here, so no real backup was tried. `~/Library/Caches` is left out of backups by default anyway.

**What 0700 doesn't stop.** It keeps other users out. It doesn't stop an agent running as this user: one with a shell of its own, even with access at Off, can `rg` this folder, as it could read the PDFs themselves, since levels govern `recto` and not the file system. The difference is that **this folder also holds closed and deleted documents**, up to its limits: 90 days from their last use and 2 GiB in all, unless cleared. Phase 6's locked-down run reaches only one document's `agent/` folder, and that's what's meant to contain it. A user's own agent with wide tools isn't contained.

**No index in front of the text, because it isn't needed yet.** A search is one pass over `text.pack`, folding each page with no map back to the text, and placing hits with the normal code only on a page with one. So the same code that reads a live page makes each hit, which is what makes the answers the same. A trigram or word index would shorten a pass that's already this quick, take more room on disk, and need its results checked against the text anyway. **Measured** below: 37 MB of text takes 42 ms, and that's the largest tested. By arithmetic, the 200,000 pages a document may have would take about a second, which wasn't tried. If documents that large turn out to be common, that's the next step, behind the same command.

**The same answers, proven.** `real_pages_answer_the_same_from_the_index` holds every field of an answer from the index to `--scan`, apart from how it was read, for 8 plain searches at 2 limits each, 7 patterns and 6 ranked searches on each file. Set `RECTO_BENCH100`, and `RECTO_INDEX_ALL` for every file. On all 141 PDFs of bench100, 5,872 pages, release build, 2026-11-07: 2,256 plain searches, 987 patterns and 846 ranked searches compared, and none differed, with no page failing to read. That needs a folder of PDFs, so it's `RECTO_BENCH100=<folder> tools/check.sh --corpus`, about a quarter of an hour, and not part of `--full`, where `the_hard_cases_answer_the_same_every_way` always runs the same comparison over a page with a word drawn late, words broken at line ends, hidden text and no text. `the_same_answer` leaves out `route`, `index` and the counts, and `totals_agree` holds the counts wherever a page-by-page read can know them. It covers line-order repair, hidden text and hyphen spellings because `read_page` is the one way both get a page's text. `an_edited_tab_keeps_its_page_numbers_and_marks_added_files` holds the same through moves, deletes, inserts and undo.

**All 141 PDFs of bench100,** one at a time at normal priority, by `budget index`: 5,872 pages in 71 s, about 12 ms a page with the check for hidden text. No page failed. Worker peak p50 28 MiB, p95 151 MiB and at most 286 MiB, on the USGS map, killed at its limit. So a file like `ntrs20220005969` takes the slow road on 14 pages, and a search draws them on a hit. 128 pages are flagged, where `examples/hidden_corpus.rs` flags 129, and the other should be among those 17, though that wasn't confirmed.

**What the crates cost.** `recto` is 2.87 MB without `grep-regex` and 4.44 MB with it, 1.57 MB more, most of it Unicode's tables, so `\w` means what it should. `recto-indexer` and the worker don't link it. Linked and used, `grep-searcher` would add only another 40 KB, and it's left out because nothing needs it: pages are in memory, and a pattern here crosses lines. The session's footprint at the start goes up with it, by `recto budget` over 20 starts each, taken in turn: 1.438 MiB (s.d. 0.013) to 1.563 (s.d. 0.018), so 0.125 MiB, and that's real. It's `__DATA_CONST`, 64 KiB to 192 KiB, 128 KiB exactly: pointer tables in the engine's Unicode data, which the loader writes to at start. It's once per process, and nothing per tab.

The session itself, NASA, by `recto budget`: 1.55 MiB at the start, 4.81 once it's open, **4.94 after indexing all 383 pages**, 5.86 after 20 searches of all kinds. The build before any of this: 1.44, 4.77, and 6.88 after 10 plain searches, with a worker on top of that during each. Handles are the same before and after, and a test holds that, and one thread once it's done. `recto budget index --file F` reports all of a build's numbers and times each kind of search both ways.
