# The renderer sandbox

> Part of the engineering notes: [`README.md`](README.md).

**Sandbox.** In the app the worker runs in the App Sandbox, in a helper app of its own, as the spike recommended (`docs/research/2026-11-07-sandbox-spike.md`): not XPC, which allows one process per app and delays a restart by 10 s, but the same child process, socket pair and shared memory as before, from an executable signed with `com.apple.security.app-sandbox` and nothing else (`app/RectoRender.entitlements`).

```
RectoPDF.app/Contents/
  MacOS/RectoPDF, recto, recto-indexer, recto-headings, recto-updater     Not sandboxed (SPEC decision 3). No worker or PDFium here.
  Helpers/RectoRender.app/Contents/
    Info.plist                       io.github.kkollsga.RectoPDF.Render, LSBackgroundOnly. The sandbox takes its identity and container from it.
    MacOS/recto-render-service       The one entitlement. Hardened runtime when signed by a team.
    Frameworks/libpdfium.dylib       Signed by the same team, so library validation passes with no exception.
```

- **Its walls, from inside** (`recto_platform::wall`). After PDFium has loaded and before the hello, so before any document reaches it, a worker that's in an app bundle, or is a release build wherever it is, puts up two walls and checks both.
  - **The App Sandbox is on**, asked positively: the kernel says this process is sandboxed (`sandbox_check(getpid(), NULL, 0)`, libsandbox's documented-in-practice way, as Chromium and WebKit ask), and the App Sandbox gave it a container, which it says in `APP_SANDBOX_CONTAINER_ID`. The host starts a worker with an empty environment, so only the App Sandbox can have set that, and an inherited seatbelt, sandboxed but with no container, reads as no. Nothing is denied or logged, and nothing depends on where the home folder is. (The first build listed `/Users` and wanted `EPERM`: proven only on this Mac, whose home isn't under `/Users`, and a sandbox violation logged on every start.)
  - **The Mach drop:** every send right to another process goes, and launchd's whatever the kernel says of it. Each right is described by `mach_port_kobject`, then the older `mach_port_kernel_object`; a kernel object is kept, and so is any right neither call will describe, since dropping one a library still uses could crash it later, and so is a send right to a port the worker itself receives on, which reaches only itself. Each name let go of is left behind as a dead name with as many references: a library that held the right, `libxpc` for one, later releases it, and with the name gone the kernel raised a Mach port guard exception (`kGUARD_EXC_INVALID_NAME`), about three a worker on this Mac, logged as non-fatal, 15,816 in a morning of tests (2026-11-08). With dead names, none in 40 workers on a blank page and on `rfc9110`. A bare worker with no sandbox and no drop still raised them on some runs (27 in 10 workers once, none the next), from system libraries, not from anything here. Then launchd must not answer a lookup. The drop is there because the sandbox alone still lets a process launch any app through LaunchServices, and the app runs outside the sandbox; no entitlement takes that away. Receive rights stay, so the surface link made before it keeps working.
  - Each failure exits with its own code, and the host names it: `renderer_not_sandboxed` (77, the only one that says the app is signed wrong), `renderer_mach_drop_failed` (78) and `renderer_launchd_reachable` (79), which are about the OS. The hello carries a `walled` bit. A release host, and any host given a worker from a helper, kills a worker that says its walls aren't up. A bare worker in `target/` runs without the sandbox and says so, as development and most tests need.
  - **Inside another sandbox**, an agent's seatbelt round `recto` for one, the system ends the helper before its first line (SIGTRAP, measured under `sandbox-exec`), as it won't start an app's sandbox inside another. The host, sandboxed itself, says `renderer_inside_another_sandbox`: run `recto` outside it, nothing to reinstall. A spawn the system refuses with `EPERM` or `EACCES` is `renderer_start_refused`.
  - **An agent sees it:** `qa state` has `memory.workers_walled` beside `memory.workers`, and `budget render` has `walled`, from the hello.
- **What it can reach.** The document and shared memory come as descriptors, which the sandbox doesn't need to allow. It can't open the document, or any file of the user's, by its path, nor reach the network, start a process, signal the app, or ask launchd, LaunchServices, the window server or the pasteboard for anything. It can still read its own bundle, system libraries and fonts, and world-readable system files, `stat` a path it can guess, open the IOSurface user client it draws through, and draw a wrong picture. Writing into its own container is stopped by `RLIMIT_FSIZE`.
- **Finding it.** `ServiceConfig::discover` follows the program's path through links, so `recto` linked onto `PATH` uses the app's helper, then looks in `../Helpers/RectoRender.app`. A release looks nowhere else; a development build then looks beside the program, then one folder up for a test binary. PDFium is beside the worker, in `../Frameworks`, or in `target/pdfium`.
- **Signing.** `app/render-helper.sh` is the one place the layout, the signing and its check live: `app/build.sh`, the release and the tests all use it. Signed from the inside out, never `--deep`, which would sign the helper again without its sandbox. Its `--check` fails unless the worker has exactly that one entitlement, the bundle verifies, the library is signed by the worker's team, a team-signed worker has the hardened runtime, and no worker or PDFium sits in the app's own `MacOS` where it could run unsandboxed. `app/build.sh` runs it after every build, so CI's full check does, and `release-zip.sh` on the built, the signed and the zipped app.
- **An ad hoc build is `io.github.kkollsga.RectoPDF.Render.adhoc`.** Every development build and test uses that container, and a Developer ID build `io.github.kkollsga.RectoPDF.Render`, so the container a development build leaves on a Mac is never the one a signed release then finds: whether the system hands a container over to another signer, or asks the user first, wasn't tested.
- **Proven** on the built, ad hoc signed helper: `recto-render-service/tests/sandbox.rs` asks the kernel about the live worker (`sandbox_check`, with this process and the helper's own library as controls), checks the hello said walled, has a helper signed without the sandbox refuse with `renderer_not_sandboxed`, has a stand-in in a helper's place that says it isn't walled killed, runs itself again under `sandbox-exec` to get `renderer_inside_another_sandbox`, draws a tile into an IOSurface over the link after the drop, compares drawing, text and the hidden-text check with a bare worker, kills a worker mid-page and between pages and checks its successor is sandboxed too, and runs a file that reaches for a canary file and a listener every way PDF offers. `recto-platform/tests/walls.rs` signs a stand-in for a compromised worker, `recto-sandbox-probe`, into the same layout: with the worker's walls up it can't read, list or write outside, connect, bind, use the DNS socket, spawn, fork, signal the app, look up a system service, launch an app, or write to its container, and every attempt works with no sandbox. With only the sandbox it launches an app that runs outside it, which is why the drop stays. Whether a fetched-back right reaches launchd is tested by a real lookup through it, not by how the kernel describes it: on macOS 15 CI (2026-11-08) `mach_port_kernel_object` didn't call launchd's right "unknown" as macOS 27 does, so the first version of that test, which only looked through rights so described, found nothing to look through. The product's drop doesn't depend on that description for launchd, whose right it drops by name; CI prints every right's description by both calls on each version. Each wall attempt runs in a probe of its own, after a CI runner with macOS 26 killed the probe once partway through its attempts (run 42473719129): the probe says each attempt before trying it, and a kill during one counts as that attempt stopped and is printed. The app test `the_app_draws_with_walled_workers_over_the_surface_link` and `release-zip.sh`'s run check that every live worker is walled and a surface tile arrived. `RECTO_TEST_WORKER` runs this crate's whole suite against any built worker, and CI does that, with the two files above, on `macos-15` and `macos-26`, where the home folder is under `/Users`.

**Cost**, release builds, this Mac under load (load average 9 to 12, other agents building), 5 rounds taking turns, medians, after review round 1's walls (2026-11-08). The bare worker beside `recto` against the same worker in the helper, with `recto` in the app's `MacOS`. The same commands as the spike; `budget render` said `walled` false and true.

| | Bare | In the helper |
|---|---:|---:|
| Idle worker footprint | 2.17 MiB | 2.41 MiB |
| `rfc9110` whole pages p50 / p95 | 1.80 / 2.27 ms | 1.73 / 2.26 ms |
| `rfc9110` peak | 29.95 MiB | 29.69 MiB |
| Fresh worker, open, first page, p50 / p95 | 12.96 / 14.38 ms | 16.01 / 16.67 ms |
| USGS map first view / scroll / zoom | 522 / 100 / 362 ms | 515 / 98 / 363 ms |
| USGS map peak, first view / zoom | 394 / 452 MiB | 394 / 451 MiB |
| `form_bomb`, every step / kills, heavy retries, pages failed / peak | 2344 ms / 2, 1, 1 / 1025 MiB | 2351 ms / 2, 1, 1 / 1028 MiB |

About 3 ms more per worker start and 0.24 MiB per worker; the rest is within the noise (`form_bomb`'s rounds ran 2.2 to 2.5 s either way). The first build, with the `/Users` probe, measured 2.27 against 2.39 MiB and 20.8 against 26.6 ms on a busier Mac. The first start after the app moves or changes costs about 80 ms more, once, while the system rebuilds the sandbox's profile (spike, not measured again).

**Not tested:** notarization of the nested helper, Gatekeeper and quarantine on a downloaded copy, App Translocation, and any macOS but 27 until the `sandbox` CI job has run on `macos-15` and `macos-26`. User-installed fonts in `~/Library/Fonts` (spike §1). Many workers starting at once. A real exploit: the stand-in calls the APIs, it isn't memory corruption.
