# The renderer sandbox

> Part of the engineering notes: [`README.md`](README.md).

**Sandbox.** In the app the worker runs in the App Sandbox, in a helper app of its own, as the spike recommended (`docs/research/2026-11-07-sandbox-spike.md`): not XPC, which allows one process per app and delays a restart by 10 s, but the same child process, socket pair and shared memory as before, from an executable signed with `com.apple.security.app-sandbox` and nothing else (`app/RectoRender.entitlements`).

```
RectoPDF.app/Contents/
  MacOS/RectoPDF, recto, recto-indexer, recto-updater     Not sandboxed (SPEC decision 3). No worker or PDFium here.
  Helpers/RectoRender.app/Contents/
    Info.plist                       io.github.kkollsga.RectoPDF.Render, LSBackgroundOnly. The sandbox takes its identity and container from it.
    MacOS/recto-render-service       The one entitlement. Hardened runtime when signed by a team.
    Frameworks/libpdfium.dylib       Signed by the same team, so library validation passes with no exception.
  Helpers/RectoStructure.app/Contents/MacOS/recto-headings   The structure helper (S6b): the renderer's walls, no library. Not in `MacOS`.
```

- **Its walls, from inside** (`recto_platform::wall`). After PDFium has loaded and before the hello, so before any document reaches it, a worker that's in an app bundle, or is a release build wherever it is, puts up two walls and checks both.
  - **The App Sandbox is on**, asked positively: the kernel says this process is sandboxed (`sandbox_check(getpid(), NULL, 0)`, libsandbox's documented-in-practice way, as Chromium and WebKit ask), and the App Sandbox gave it a container, which it says in `APP_SANDBOX_CONTAINER_ID`. The host starts a worker with an environment empty but for one allocator setting (`MallocLargeCache=0`), so only the App Sandbox can have set that, and an inherited seatbelt, sandboxed but with no container, reads as no. Nothing is denied or logged, and nothing depends on where the home folder is. (The first build listed `/Users` and wanted `EPERM`: proven only on this Mac, whose home isn't under `/Users`, and a sandbox violation logged on every start.)
  - **The Mach drop:** every send right to another process goes, and launchd's whatever the kernel says of it. Each right is described by `mach_port_kobject`, then the older `mach_port_kernel_object`; a kernel object is kept, and so is any right neither call will describe, since dropping one a library still uses could crash it later, and so is a send right to a port the worker itself receives on, which reaches only itself. Each name let go of is left behind as a dead name with as many references: a library that held the right, `libxpc` for one, later releases it, and with the name gone the kernel raised a Mach port guard exception (`kGUARD_EXC_INVALID_NAME`), about three a worker on this Mac, logged as non-fatal, 15,816 in a morning of tests (2026-11-08). With dead names, none in 40 workers on a blank page and on `rfc9110`. A bare worker with no sandbox and no drop still raised them on some runs (27 in 10 workers once, none the next), from system libraries, not from anything here. Then launchd must not answer a lookup. The drop is there because the sandbox alone still lets a process launch any app through LaunchServices, and the app runs outside the sandbox; no entitlement takes that away. Receive rights stay, so the surface link made before it keeps working.
  - Each failure exits with its own code, and the host names it: `renderer_not_sandboxed` (77, the only one that says the app is signed wrong), `renderer_mach_drop_failed` (78) and `renderer_launchd_reachable` (79), which are about the OS. The hello carries a `walled` bit. A release host, and any host given a worker from a helper, kills a worker that says its walls aren't up. A bare worker in `target/` runs without the sandbox and says so, as development and most tests need.
  - **Inside another sandbox**, an agent's seatbelt round `recto` for one, the system ends the helper before its first line (SIGTRAP, measured under `sandbox-exec`), as it won't start an app's sandbox inside another. The host, sandboxed itself, says `renderer_inside_another_sandbox`: run `recto` outside it, nothing to reinstall. A spawn the system refuses with `EPERM` or `EACCES` is `renderer_start_refused`.
  - **An agent sees it:** `qa state` has `memory.workers_walled` beside `memory.workers`, and `budget render` has `walled`, from the hello. `memory.workers_too_busy` and `memory.workers_deadline_kills` say how many workers ran out of time with the Mac too busy to give them the processor, and how many were killed at their deadline: counts of the renderers held, so they go to 0 when a tab goes cold.
- **What it can reach.** The document and shared memory come as descriptors, which the sandbox doesn't need to allow. It can't open the document, or any file of the user's, by its path, nor reach the network, start a process, signal the app, or ask launchd, LaunchServices, the window server or the pasteboard for anything. It can still read its own bundle, system libraries and fonts, and world-readable system files, `stat` a path it can guess, open the IOSurface user client it draws through, and draw a wrong picture. Writing into its own container is stopped by `RLIMIT_FSIZE`.
- **Finding it.** `ServiceConfig::discover` follows the program's path through links, so `recto` linked onto `PATH` uses the app's helper, then looks in `../Helpers/RectoRender.app`. A release looks nowhere else; a development build then looks beside the program, then one folder up for a test binary. PDFium is beside the worker, in `../Frameworks`, or in `target/pdfium`.
- **Signing.** `app/render-helper.sh` is the one place the layout, the signing and its check live: `app/build.sh`, the release and the tests all use it. Signed from the inside out, never `--deep`, which would sign the helper again without its sandbox. Its `--check` fails unless the worker has exactly that one entitlement, the bundle verifies, the library is signed by the worker's team, a team-signed worker has the hardened runtime, and no worker or PDFium sits in the app's own `MacOS` where it could run unsandboxed. On a whole app it also requires `Helpers/RectoStructure.app` (checked the same way, with `.Structure` and `.Structure.adhoc` as its identifiers) and fails a bare `MacOS/recto-headings`, which the app could start with no walls (S6b-2; a test holds each). `app/build.sh` runs it after every build, so CI's full check does, and `release-zip.sh` on the built, the signed and the zipped app.
- **An ad hoc build is `io.github.kkollsga.RectoPDF.Render.adhoc`.** Every development build and test uses that container, and a Developer ID build `io.github.kkollsga.RectoPDF.Render`, so the container a development build leaves on a Mac is never the one a signed release then finds: whether the system hands a container over to another signer, or asks the user first, wasn't tested.
- **Proven** on the built, ad hoc signed helper: `recto-render-service/tests/sandbox.rs` asks the kernel about the live worker (`sandbox_check`, with this process and the helper's own library as controls), checks the hello said walled, has a helper signed without the sandbox refuse with `renderer_not_sandboxed`, has a stand-in in a helper's place that says it isn't walled killed, runs itself again under `sandbox-exec` to get `renderer_inside_another_sandbox`, draws a tile into an IOSurface over the link after the drop, compares drawing, text and the hidden-text check with a bare worker, kills a worker mid-page and between pages and checks its successor is sandboxed too, and runs a file that reaches for a canary file and a listener every way PDF offers. `recto-platform/tests/walls.rs` signs a stand-in for a compromised worker, `recto-sandbox-probe`, into the same layout: with the worker's walls up it can't read, list or write outside, connect, bind, use the DNS socket, spawn, fork, signal the app, look up a system service, launch an app, or write to its container, and every attempt works with no sandbox. With only the sandbox it launches an app that runs outside it, which is why the drop stays. Whether a fetched-back right reaches launchd is tested by a real lookup through it, not by how the kernel describes it: on macOS 15 CI (2026-11-08) `mach_port_kernel_object` didn't call launchd's right "unknown" as macOS 27 does, so the first version of that test, which only looked through rights so described, found nothing to look through. The product's drop doesn't depend on that description for launchd, whose right it drops by name; CI prints every right's description by both calls on each version. Each wall attempt runs in a probe of its own, after a CI runner with macOS 26 killed the probe once partway through its attempts (run 42473719129): the probe says each attempt before trying it, and a kill during one counts as that attempt stopped and is printed. The app test `the_app_draws_with_walled_workers_over_the_surface_link` and `release-zip.sh`'s run check that every live worker is walled and a surface tile arrived. `RECTO_TEST_WORKER` runs this crate's whole suite against any built worker, and CI does that, with the two files above, on `macos-15` and `macos-26`, where the home folder is under `/Users`.

**Not tested:** notarization of the nested helper, Gatekeeper and quarantine on a downloaded copy, App Translocation, and any macOS but 27 until the `sandbox` CI job has run on `macos-15` and `macos-26`. User-installed fonts in `~/Library/Fonts` (spike §1). Many workers starting at once. A real exploit: the stand-in calls the APIs, it isn't memory corruption.

## Structure helper (S6a)

`recto-headings` can run in a sandboxed helper of its own, `RectoStructure.app`, with the renderer's walls: the same App Sandbox with exactly the one entitlement (`app/RectoStructure.entitlements`), the same Mach drop, and `RLIMIT_CORE`, `RLIMIT_FSIZE` and `RLIMIT_NPROC` at 0. The app's build lays it out (S6b-1) and the session starts it, only walled (below). `app/render-helper.sh --layout-structure <Contents> <exe>` lays it out, `--sign` and `--sign-dev` sign it with the renderer's rules (inside out, never `--deep`), and `--check` verifies it, on the helper or on the whole app, where the structure helper is required. The release carries it through: `release-zip.sh` checks its architecture and its team (the same as the renderer's), its quiet run makes generated contents (`recto contents --generated`, then `recto wait contents-generated`; every build refuses an unwalled helper, so a zero exit shows it started walled under the release's signature and hardened runtime), `check-draft.sh` checks it is Developer ID signed with the hardened runtime from 0.1.4, and `recto-update` refuses a kept copy whose structure helper is another program's identifier (one with none, from before S6b, is still one to go back to). Notarization of the nested helper is covered by the preflight and not yet tried: it needs the owner's keys. It has no PDFium and no library, so no library-validation rule.

**The document comes as a descriptor.** The sandbox lets the helper read no file by name, so the host opens the document and gives it as descriptor 3 (`recto_platform::helper::spawn_with_document`, which first copies it to a number of 4 or more, so a pipe that landed on 3 is moved before the document is put there). In the helper, `inherited_document()` takes 3 once, marks it close-on-exec and refuses unless it's a regular file, and distillPDF opens `/dev/fd/3`. Nothing else is open in the helper but 0, 1 and 2 (`a_helper_given_a_document_gets_it_at_3_and_nothing_else`).

**When it puts its walls up.** Only when its own path ends `Helpers/RectoStructure.app/Contents/MacOS/recto-headings`, or when it can't tell where it is (`helper_app::in_structure_helper`); a bare helper in `target/` has no walls to put up and isn't hardened, since `RLIMIT_NPROC=0` would stop it starting its render worker. A walled helper that can't put them up exits 77, 78 or 79 (the renderer's codes) before it reads a job. It then says `{"state":"hello","walled":true}` and takes one job, `{"kind":"count"}`, which answers `{"state":"counted","pages":N,"helper_peak_bytes":…}` from the descriptor; any other job gets `{"state":"failed","code":"unsupported_job"}` and reads nothing. A bare helper says `walled:false` and still does its headings job, with the hello as a first line the session skips.

## The session starts it (S6b-1)

Generated contents now runs only through `RectoStructure.app`. `recto_control::structure` is the runner for any structure-helper job, and `structure::headings` the first job (`docs/engineering/generated-contents.md` has the line protocol and the limits).

- **Where it is.** `Structure::installed` is the one finder: `Helpers/RectoStructure.app/Contents/MacOS/recto-headings` beside the `MacOS` folder of the running program, through any link to it. A development tree has it at `target/Helpers/…`, which `tools/check.sh` lays out (and `recto` in `target/debug` finds, as `app/build.sh`'s app finds its own). A test binary in `target/debug/deps` finds nothing there, so a headless test that makes generated contents has no helper (`helper_missing`); the tests that need one name it (`Walled::at`, `Structure::at`, `test-seams`). `app/build.sh` no longer copies `recto-headings` into `MacOS`.
- **Checked from outside before it sees its job.** After the hello, and before a byte of the job is written: `sandbox_check` says the helper's pid is in a sandbox, the sandbox refuses its path-filtered read of the document (by the name given and the real one), and the hello says `walled:true`. Anything else is `structure_not_sandboxed` and the helper is killed. The pid is not collected until this has run, so it can't be another process's.
- **Why the codes.** `structure_not_sandboxed` (signed wrong, or a bare helper: exit 77, or the kernel shows it in no sandbox), `structure_unconfirmed` (the walls couldn't be confirmed: a hello that isn't one, a probe that couldn't tell, or a document its sandbox lets it read by name; ask again, not a reason to reinstall), `structure_inside_another_sandbox` (the helper was killed on starting while this process is itself sandboxed: run `recto` outside), `structure_walls_failed` (exit 78 or 79: this macOS gave it no rights to drop, or launchd still answers) and `structure_start_refused` (the system refused to start it). Each has its own words for a person and its own next step for an agent. None falls back.
- **The environment is `MallocLargeCache=0` and nothing else.** Not `spawn_helper`'s pass-through of the render worker's and PDFium's locations, never `APP_SANDBOX_CONTAINER_ID`; the helper starts no worker.
- **The check for hidden text moved to the session** (`generating/ink.rs`, `recto_index::generated::visible`): the walled helper has no way to start a render worker, so it only finds headings, and the session's render worker, at the renderer's own level, draws the pages that have some. A walled and a bare helper find the same (`the_walled_helper_finds_what_the_bare_one_does`: plain, bold and a hidden-heading document, every line the same but for two numbers that are a run's own).
- **Proven** in `recto-control/tests/structure.rs` (macOS): the 15 ways of hiding a heading and the bold and moved-media-box documents through the walled helper and the session's check; a bare helper refused as `structure_not_sandboxed` in every build; the run again under `sandbox-exec` giving `structure_inside_another_sandbox`; a cancelled job writing nothing and leaving no child. In `src/structure/tests.rs`: the admit table, a stand-in that lies `walled:true` and is never given its job (a stand-in that writes what it reads, never written), a stand-in that sends 70,000 bytes in a line killed as `bad_answer` and gone, a 64 KiB line of `[` refused on the reader's own 256 KiB stack, and the environment exactly `MallocLargeCache=0`.
