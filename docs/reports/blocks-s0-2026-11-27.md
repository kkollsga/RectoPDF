# 8.3 blocks, slice S0: measurements (2026-11-27)

Tool: `crates/recto-headings/examples/blocks_sample.rs` (release, `MallocLargeCache=0`, one file a run, each run through `tools/sysguard/heavy.sh`; USGS with `HEAVY_SOLO=1`). It runs distillPDF 0.1.7 (`scan_document` = Full or `scan_typography`, then `page_stream`, page by page, keeping counts only) and maps each block onto the page's characters read through the render worker (`page_characters`, no hidden-text check). Source: `docs/design/blocks.md` §7.

**Method notes, so the numbers aren't over-read.**
- Machine under load throughout (the `uptime` 1-minute load is in each row, 4 to 8 on this 16 GB Mac, other agents running). Each number is one run. Wall times and CPU are therefore upper-ish and noisy.
- Peak is `phys_footprint` of the example's process (`recto_platform::isolate::process_memory`, peak). It holds distillPDF only: the render worker is a separate process and is not in it. CPU is this process's `ps` cputime, also without the worker. A real helper adds the worker's own cost for the text reads (the "text reads" column is wall time of those).
- **Mapping rule measured.** A block's letters (alphanumerics lowercased, ligatures spelled out, after `recto_headings::plain` strips the inline markup that `Block::text` carries) must be one unbroken run in the page's letters. *strict* = also found after the previous mapped block's end (the design's rule); *anywhere* = found anywhere on the page. The text is the raw character stream the renderer gives, not `recto text`'s final cleaning (hidden spans, running heads), so a pass here is an upper bound by a little. Blocks with no letters (figures, tables: distillPDF gives tables as cells, not text) are counted separately and can't be mapped by this rule.
- My first pass compared distillPDF's HTML (`<a href=...>`) without stripping it and showed 30% on RFC 9110; it was my error, found by printing the misses, and every number below is the rerun.
- Cold file cache inflates first runs: NASA `ntrs20220005969` Full scan was 34 s on its first run and 3.4 s on the rerun; USGS Full scan 8.4 s then 0.4 s. The tables use the warm rerun; the cold figures are in the last section.
- Not measured: the 10,000-page remade PDF (none exists in the repo or the distillPDF checkout), the `get` timing, the sandbox (`/dev/fd`) question. Not run: the German and French GDPR.

## What a record costs

Per mapped block: 1 byte (kind, level, continues bit) + 3 + 3 (start, end; a page has at most 2^21 characters) + 8 (box in whole points) = 15 bytes, plus 8 bytes a page (count and digest). Totals for the blocks that mapped (Full), per page in brackets:

|---|---|---|---|
| NASA 2628 | 1736 | 29,104 (28 KiB) | 76 |

| math_AG | 1387 | 21,469 | 259 |

If every block with letters were stored it would be about 15 bytes times 4,000 blocks = 60 KB for NASA 2628, so the design's 190 KiB for NASA (0.5 KiB a page) was an overestimate by six to seven times: 76 to 260 bytes a page here. 10,000 pages at 100 to 260 bytes is 1 to 2.6 MB, not 5 MB. (An estimate, from these files and my fixed field widths, not a built codec.)

## What the numbers decide

1. **Typography, not Full, as the default scan.** Full costs 2 to 10 times the scan wall time and 2.6 times the CPU (NASA 2628: 14.4 s against 6.5 s; the first-run scan alone was 34 s on the cold NASA 22). The mapping pass rate is the same or within a few points on every file, and Typography finds many more headings that map (NASA 2628 headings that map anywhere: 99% of 1119). The one thing Full may buy is fewer false paragraphs/headings; this wasn't measured against ground truth. Recommend Typography for the first ask, Full only if a quality check later shows a need.
2. **"On first ask" fits a wait for most documents, and with Typography for a 383-page report (about 6.5 s plus the queue) too, with `recto wait blocks-ready`. A 1,000+ page book is likely a minute; the 10,000-page case wasn't run and the 30-minute limit isn't tested.** Peak memory of 20 to 44 MiB means the 512 MiB limit has ten times headroom here. Caps: the largest block was 2,774 letters and the busiest page 92 blocks (USGS), 83 (NASA 22), so 512 blocks a page and 64 Ki letters a block are far above anything seen; the 512 KiB a line holds too.
3. **The strict "after the previous block" rule costs a lot.** On multi-column or magazine layouts the blocks are in reading order but the text isn't (NASA 2628 paragraphs: 42% strict, 73% anywhere; NASA 22: 28% and 44%; UN: 31% and 54%). On single-flow law and RFCs it is nearly free (GDPR 97%, AI Act 87% against 100% anywhere). Decide before S1: let the cursor restart for a block that fails it (anywhere on the page, unique) or accept page fallback on those documents. "Paragraph" honestly promises about 9 in 10 on law and standards, about 5 in 10 on RFC-like text and about 2 to 4 in 10 on reports with interleaved columns and sidebars; the owner's answer C (page fallback, said) is needed as designed.
4. **Footnotes, and any block on a map or poster page, mostly don't map** (USGS: 2% of paragraphs; footnotes 11% on NASA 2628), and tables and figures have no text at all. Promise paragraph, heading, list item and code only; others answer with the page.
5. A `form_bomb` page's text is refused by the render worker (a bounded 0.7 s), so a blocks job must treat "page text unavailable" as a page that maps nothing, not as a failure.
