# UI wait follow-through — 2026-11-18

This is the next responsiveness increment after prepared SVG, based on `124eecb0`. It removes a confirmed lock coupling and moves native print document reads off the UI thread. It does **not** close the historical one-second print finding, the CPU-busy 35–44 ms observations, or SPEC's 16 ms target.

## Changes and proofs

- **QA answers:** `core/qa/mod.rs` removes the answer slot and releases its mutex before decoding JSON. The UI's answer delivery needs that same mutex; the server permits eight jobs, so another answer must not wait for the first job's decoding. The real ask/answer regression holds the first decoder and requires the second answer to finish. It failed on the old lock scope, then passed after the explicit unlock. Malformed success remains `null`, explicit errors keep their code/message, and late answers do not recreate slots. Synchronization used to force this ordering exists only in tests; production gains no state or allocation.
- **Print ownership:** Rust refuses another print while one is preparing, ready or handed to the host, matching the menu and the documented one-print rule. QA cannot retarget that print's output. The ready-to-handing transition has no observable idle gap; the unnamed descriptor remains owned through output publication. A completion for a currently unowned path cannot publish another print's output. Five small tests failed before their fixes, then passed. This is not a claim that a path-only completion API distinguishes an old descriptor number after reuse.
- **Refused print settings:** both native entry points retain only the newest admitted `NSPrintInfo`. Two refused requests previously kept two entries; the existing restricted-print test saw that failure. It now asserts one retained entry before Print Anyway and zero after completion. No native test launch was added.
- **Native document loading:** the existing print command still prepares the PDF in Rust. Swift loads its `CGPDFDocument` and page count on a background queue, then transfers the immutable result to the main thread to create the view and print operation. The view uses the cached count. Rust's single-print ownership bounds the pending load and keeps the unnamed descriptor alive. A missing delegate, failed load, or closed/replaced original window releases that exact held file; it cannot start printing in a replacement window. Host state lives in `Print.swift`, with one `AppDelegate` registration and one QA report registration. The existing page-fidelity launch asserts the loader ran off-main; moving that same loader onto main made the assertion fail (`true`, expected `false`).

One existing headless test expected a second command to replace an unconsumed ready file. After enforcing the whole busy lifecycle, its original descriptor-cleanup concern is tested through the actual defensive `PrintWatch::ready` replacement callback instead. A temporary seed leaked the replaced file and the rewritten test failed with two held descriptors instead of one. The seed was dropped. No test was deleted and no app-launch count increased.

## Measurements and limits

Release builds on this 16 GB Mac; quiet windows, temporary files and no posted events. The baseline ordinary-file probe made 60 sequential state requests: median 9.79 ms and maximum 20.32 ms **round trip**, including CLI/server work. No additional over-budget UI stretch appeared during those requests. The four-second sampler attached too late to attribute their short work: its main-thread samples were idle, so that sample is not evidence about the startup stalls. The same run had earlier stretches of 68.7 ms wall/46.5 ms CPU and 32.3/19.8 ms; the last `scroll` label does not identify which work caused them.

Separate temporary phase instrumentation measured opening the generated three-page RFC print at 116–117 µs on main, with the initial page count at 1 µs. For the USGS map it was 316 µs plus 1 µs. Those small reads do not explain a historical one-second stall; moving file/parser work off-main prevents a larger or delayed read from holding input. Actual draw callbacks in these runs were off-main: about 9.8–10.1 ms per RFC page and 225 ms for the map. `canSpawnSeparateThread` alone was not treated as proof. All temporary phase instrumentation was removed.

**Input to frame:** the unchanged release harness ran before at 07:00–07:02 and after at 07:31–07:33, at 1, 100 and 1,000 tabs. All four reported quantiles in each of 54 action cases stayed within `after ≤ 1.1 × before + 200 µs` (`input-comparison.json`). The before run shared the machine with the small probe; the after run held the local heavy queue alone. The 1,000-tab p50 differences above 10 µs were decreases: tap 195.3→177.5, typed page 111.8→93.6, pane focus 173.0→159.3, Undo 98.9→87.1 µs. Those ordinary action implementations did not change; different test-binary layout, scheduling and load are uncontrolled in this pair, so these decreases are not attributed to the fix or reported as an optimization.

**Native print resources:** one release pair per case, local heavy queue held alone. A separate `clang -O2` sampler reads each process's `phys_footprint` and sums the native app and its own bundled helpers simultaneously. It sleeps 5 ms between scans; enumeration and reads brought the observed cadence to about 8 ms, so shorter peaks may be missed. Shared OS printing services and the CLI controller are outside that total: the controller was `target/release/recto`, outside the unique app-bundle prefix used to select processes. The sampler reported no overflow. An initial child-only sampler missed helpers and was discarded; its files are explicitly marked `child-only.invalid`. The executed compile and invocation parameters are recorded in `memory-invocations.json` (reconstructed from the commands after the run).

The final loader reported `main_thread=false`, 165 µs/three pages and 267 µs/one page; refused settings were released (`answers_kept=0`). The map's sampled total changed by about 1.5 MiB; the single-pair RFC peak/time differences are not evidence of a causal speedup or memory saving. Loading adds one bounded active dispatch job, transfers the existing document without copying PDF bytes, and adds no per-idle-tab state, handle or thread. Retaining one refused settings object replaces the old unbounded accumulation.

The resource table uses `memory-before-rfc-corrected`, `memory-after-rfc`, `memory-before-map` and `memory-after-map`; the input harness logs and comparison are beside them. No claim is made about a visible window, a physical printer, or 120 Hz drawing.

## Remaining work

The historical print stall remains unconfirmed by these runs. QA's final publication still runs synchronously through `printFinished`; its `qa_target` guard still spans filesystem publication, including the fallback copy. Keep that separate from the fixed answer-decoding mutex and the moved Core Graphics reads. Measure and move publication through a bounded asynchronous completion path next, preserving the busy/ownership interval until the output is actually published.

The remaining startup and short-stall work needs samples covering the actual interval, with CPU time, layout/report phases and platform drawing separated. A queued QA verb and the last action label are leads, not attribution. The horizontal-scrollbar report remains open separately.
