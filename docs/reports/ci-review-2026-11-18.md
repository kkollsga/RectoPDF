## What changed against the morning

Morning run 43830180421's printed stages: compile gate 38 seconds, doc links 2, workers 11, headings 20, combined test stages 291, app build 103, bundle 22, app tests 347, registrations 10. Latest: 41, 4, 13, 23, 366, 136, 22, 308, 9. Test-stage wall increased 75 seconds and app build 33, while app tests fell 39. The latest job also saved a new cache, costing 85 seconds; the other four did not. Cache restore alone ranges from 85 to 130 seconds.

Parsing unique passing test names in the morning/latest logs finds 3,162 shared names, 86 names only in the latest and two only in the morning. The new names total **21.475 test-seconds** on the latest runner; the shared names total **2025.364 before and 2003.043 after**. Test-seconds are summed elapsed test durations, not critical-path wall time or CPU time. They do not prove that code changes added only 21 seconds to CI: workloads can change inside an existing test, features and scheduling differ, and building more code costs time too.

The common tests do not uniformly slow down: summed `recto-agent` times rise about 90.3 to 132.4 seconds, `recto-app` 198.4 to 231.0, while the real app and restore test groups fall about 504.1 to 418.4 and 677.8 to 612.6. Therefore "all the extra time is a slower runner" is not supported by this comparison. It also does not identify a removable redundant suite.

## Decision and next checks

- Do not delete tests, raise the CI budget, restore the retired ten-minute goal or change cache policy on this evidence. Coverage removal needs the seeded-bug proof; a cache change needs a cold/warm comparison, not the cost of one save alone.
- Keep new locator tests pure and small; add no app-launching test. Report each slice's added test time. The copy fix uses the existing in-process chrome tests. SVG preparation must be measured because moving work ahead of paste can charge every snapshot and its tests.
- The next CI investigation is a targeted profile of the existing actor/app policy walks and their build costs if the next five green runs keep the margin thin. Their increase is a lead, not a declared product regression. Avoid another whole-suite run merely to investigate it.
- Existing local timings (`check.sh --slow`, retained run 636ff38d) are 105 seconds wall for core/process, 143 for app tiers and 46 for the deliberate slow stage; they are not substitutes for CI's slower runner.

This completes the bounded initial attribution. It permits the agreed small feature slices to proceed under the existing no-regression rules; it does not claim CI has been made faster. The next pushed code runs provide the before/after evidence for actual changes.
