# Testing as a worker

Paste this into a worker's brief. Name the exact check the work needs, because "run the gate" gets the whole gate.

The whole suite decides a hand-back. It's never how you find out why something changed. Agents under pressure reach for the biggest test, so ask the smallest question that answers yours first.

## Which check answers which question

| The question | The check |
|---|---|
| Does this one behaviour work? | One named test: `HEAVY_CLASS=quick tools/sysguard/heavy.sh cargo nextest run --locked -p <crate> -E 'test(=<name>)'` |
| Did my fix work? | `tools/check.sh --failed`: only what failed last time |
| Does it compile, and does what I changed still pass? | `tools/check.sh --quick`: the compile gate, the tests of crates changed since the branch left `main` (committed or not), and the registration guards |
| Why did these inputs change? | Just those inputs, not the whole corpus |
| Is this ready to hand back? | `tools/check.sh --full`, once, last. On a branch it runs what the change can affect (below) |
| How many full runs has this branch had? | `tools/check.sh --runs` |
| Which tests are slow, and is a tier over its time budget? | `tools/check.sh --slow` |

## How to work

0. **Start from a warm build.** Make your worktree with `tools/worktree.sh new <branch> .worktrees/<name>`, which seeds its `target/` from the main checkout's as an APFS clone: no extra disk, and the first build compiles only the workspace. A worktree made with plain `git worktree add` starts cold.
1. **Settle what you're testing first.** No final run on a dependency pin, a merge or a set of findings that's about to change. Fix all of a review's findings, then run once.
2. **Fix before rerunning.** A failure names its test. Read it, fix it, then run that test or `--failed`. The queue refuses a command that failed on code that hasn't changed.
3. **Run the whole suite once, last,** on the commit you're handing back, and again only if code changed.
4. **Commit before the full run.** A dirty tree runs, but it's never recorded, so its pass is worth nothing later.
5. **A test waits for what it checks.** Poll for the condition with a bound (say 10 s) and fail with what it saw. Never sleep a fixed time and then count threads, files or events, and never assume which of two queued jobs a background thread takes first. Four of five failed full runs in one stretch were tests like these, not product bugs. Fix them like any other bug: find what the test assumed, and check the property instead.

## The ratchet

`tools/ratchet.sh` runs first in every `--quick` and `--full`, in about a second, and builds nothing. It holds structure that may only shrink: production lines per file (budget 1,500), function length (150), struct fields (15), enum variants (40), methods per `impl` (40), the size of `recto-ffi`, fixed `sleep` calls per test file, and the number of tests that launch the real app (the `app`, `restore`, `compare`, `evidence` and `long_session` binaries of `recto-cli`: test what Rust decides in process with the headless app in `recto-app`'s testkit, and add what only the real app shows to a launch that is already there), against `tools/ratchet/baseline.txt`. Today's offenders sit in the baseline at their current size; a new offender or any growth fails the run, naming the file or item, the old and new number and the budget. **When it fails, split the code by concern into a module of its own (guide 2.8); don't raise the number.** A baseline number is raised only by a hand edit that a reviewer sees. When something shrinks the run says so, and `tools/ratchet.sh --update` locks it in (it refuses to raise anything). Code that moves unchanged keeps its entries with `tools/ratchet.sh --moved <old> <new>` (a file's path, or one `path::Item`), which refuses while the old one still holds the offender (a copy) or when a number at the new place is higher; a new small file may take the old path, as when a bridge file keeps a module's name, since it no longer measures as the offender there. `--kind sleep` (or `file`, `fn`, ...) moves only one kind's entries, as when a file's sleeps go to one new file and its functions to others. A struct or enum under `#[uniffi::remote(..)]` restates a type that lives, and is counted, in another crate, so it's left out of the field and variant budgets, while its lines still count toward its file and the bridge crate. A sleep that is the poll interval inside a bounded wait helper takes `// ratchet: poll`; a test that sleeps and then checks gets rewritten to wait for the condition. `tools/ratchet.sh --report <base-ref>` lists the shared hub files a branch touched and the lines added to each. After changing the tool, `tools/ratchet-test.sh`.

## What the tools do

- **The compile gate comes first.** Before any test is queued, `check.sh` runs rustfmt (outside the queue, it builds nothing), then clippy and the Windows compile check as a quick job of their own. A compile, lint or layout error costs seconds, queues no test and counts no full run. `cargo fmt --all` fixes a layout.
- **`--quick` always runs the registration guards** (every command has a row, rows documented, every menu id has an enable rule, the known `qa state` paths sorted, and so on) whichever crate changed, because a change in one crate breaks the list in another. The guards, the app tiers and the rules that select them are in one file, `tools/check-scope.sh`. A name there that no test has any more stops the check before anything is queued, and so does a test file that drives the app and is in no tier. A new guard goes in `GUARD_TESTS`.
- **`--full` on a branch selects by what changed since it left `main`.** The crates changed plus everything that depends on them (from `cargo metadata`) get their tests, and the guards always run. Anything changed outside `crates/` and `app/` that isn't a document (tools, `.config`, `Cargo.*`, fuzz) runs everything. `app/` changes run the app tiers, not the Rust tests. The run prints what it selected, why, and what it skipped.
- **Two tiers of tests that launch the app.** *Window*: drawing, AppKit, the bridge, reading and restoring state; it runs when recto-ffi, recto-reader, recto-session, recto-agent, recto-control, anything they depend on, recto-cli or `app/` changed. *Lifecycle*: updates end to end, Launch Services, long sessions, a thousand tabs, what is left registered; it runs when recto-update, recto-platform, `app/`, the record code (`recto-session/src/record.rs`, `recto-control/src/record_store.rs`, the bridge's updates, sleeper, sleep queue and saver) or the test files changed. A test is in lifecycle if `LIFECYCLE_TESTS` names it, and in window otherwise.
- **The ratchet runs first, then the tools' tests.** `tools/ratchet.sh` (structure that may only shrink) runs before anything is queued, in `--quick` and `--full`. When a change touches `tools/` (the hooks too), `.config/` or `.github/` since the base, a full run also runs `tools/ratchet-test.sh` and `tools/check-test.sh` before the gate (on CI, in core, against CI's base: on `main` the push's previous commit, on a branch where it left `origin/main`, and always when that can't be worked out) (they build nothing, on a throwaway repository), so the tools are held by the tool.
- **Durations are kept.** Every nextest stage of a full run writes JUnit, and the run's per-test times go in one small file under the git common dir (`recto-test-times/`, next to the ledger), the newest 20 runs. `tools/check.sh --slow` prints the 20 slowest tests, each tier's test-seconds and wall time against its budget (core 60 s, process 60 s, window 90 s, lifecycle 240 s; edited in one place, `TIER_BUDGETS` in `tools/check-scope.sh`), the slow stage's total, and the stages of the latest run of everything against the one before. Over budget is reported, not a failure: a process review reads it. A new test file that spawns `recto`, a worker or the installer goes in `PROCESS_BINARIES` there, or its tests count as core.
- **A named part of a full run:** `CHECK_PART=core|window|lifecycle tools/check.sh --full` runs just that part (core: the gate, the workspace tests and the tools' tests; window and lifecycle: the app build and that app tier). CI runs the three as parallel jobs, so what runs there is still what `check.sh` says. A part is never remembered as a pass, counted as a run or stamped for the push guard.
- **`tools/target-hygiene.sh` runs at the start of every check run** and removes the `.o` files cargo leaves in `target/*/deps` once a folder holds over 30,000 entries (`tools/target-hygiene-test.sh` holds it; it never sweeps under a running build). Each test is a process, and the first IOSurface in one lists its executable's folder, so 400,000 entries made 84 tests take 10 s each on 2026-11-12. `[profile.dev] split-debuginfo = "packed"` stops dev builds leaving them. Its line shows the folder's entries and size for the trend.
- **Everything runs on CI, on `main` and with `CHECK_ALL=1`.** `CHECK_BASE=<commit>` selects against that commit instead of `main`.
- **Only a pass of everything lets `main` be pushed.** A selective pass is remembered for the same selection (the same code again runs nothing) but never stamps the push guard, so a merge of a selectively passed branch is checked in full on `main`, as CI checks it. To make a branch's pass count for the push, run it with `CHECK_ALL=1`. The ledger's last field says which kind each run was.

- **A pass on identical code counts.** `--full` on a clean tree whose code has passed before says which commit passed it and when, lets the push guard accept this commit, and runs nothing. That covers reverts, doc-only commits and a merge identical to its branch. Documents are `docs/` and any `.md`. `CHECK_AGAIN=1` runs it for real, to look into a pass you have reason to doubt.
- **A branch gets two full runs:** one for hand-back, one after a review's fixes. The count starts again when the branch takes in new code from `main`. `main` gets two per range of commits not yet pushed, and a push starts its count again. Only runs of commits still in HEAD's history count: a merge taken back off, or commits set aside, no longer do.
- **A third run needs a reason:** `tools/check.sh --full --why "what this run decides"`. It starts at once, and the reason goes in the ledger with the time, branch, commit, result and seconds. It's a speed bump to make the run deliberate and visible, never a lock. If you're asked for one, first ask whether a smaller check would answer it.
- **A failure carries its evidence** (PLAN R0.7a). A failing test that started the app leaves one folder, `target/recto-evidence/<stage>/<binary>--<test>/` (CI: in the `check-logs-<attempt>` artifact, under `evidence/`), made by the harness (`crates/recto-cli/tests/common/evidence.rs`): every launch's messages, `qa state` as each launch was last read (a comparison's before and after), the threads by name and a 3 s `sample` if the app is still there, the slow seams and seed, the system pressure, load, memory and OS, Launch Services for this tree, the runner's command line and settings, and `rerun.txt`, the one command that runs it again here as it ran there. At most 16 MiB a folder; the next run of `check.sh` empties the root. Read it before running anything again. A plain `cargo nextest run` puts it in `target/recto-evidence/adhoc/<run>/`.
- **A failure says how to run it again** (R0.7b). The evidence's `rerun.txt`, printed with the failure and listed at the end of a failed `check.sh`, is one command: the test by binary and name, the profile, the concurrency of its stage, `RECTO_QA_SLOW` with the seams and the seed as the run met them, and `tools/check.sh --like-ci` for CI's limits. The slow stage takes `CHECK_SLOW_SEED=<n>` for its jitter, and is plain `ci` without it.
- **CI measures a failure the first time** (R0.7c). A stage that fails runs its failed tests again 4 times (`CHECK_RERUN`; here 0 unless you set it), each round with its own evidence, and prints `test, failed N of M` counting the first run. The stage still fails. Bounds: 8 tests a stage, no round after 240 s of a stage's rounds or 360 s of the whole run's (`CHECK_RERUN_TESTS`, `CHECK_RERUN_SECONDS`, `CHECK_RERUN_TOTAL_SECONDS`), so a failing run takes at most about 11 minutes more. A failed app tier no longer hides the registrations stage after it, which runs anyway; the run fails with the app tier's name.
- **CI's conditions here** (R0.7d): `tools/check.sh --like-ci <part or filter> [--times N]` runs a CI part, or the tests of a nextest filter N times with their `failed N of M`, with CI's profile and concurrency and the tests and their apps under `taskpolicy -c background`: about CI's speed (the lifecycle tier 1.41 times CI's wall, 2026-11-12, `docs/engineering/failures.md`). It can't give a clean user or a clean Launch Services database, and says so. It holds its queue slot about four times as long as a plain run. Never a pass.
- **`main`'s CI is watched by the tool** (R0.7e, the coordinator's). `tools/push-main.sh` pushes `main` (the hook still decides) and watches that commit's run to its end: green, or red with the failed jobs, the failed tests, their `failed N of M` lines and the artifacts with the command that fetches each; `--watch [sha]` does only the watching. While the last pushed `main` commit's CI is red, `tools/check.sh --full` on `main` remembers a pass but doesn't stamp it for the push guard (exit 4), until CI is green or the red is marked known for at most a week: `tools/push-main.sh --known <sha> --until YYYY-MM-DD --why "what is known"`, the dated-exception idea of `restore/ci_known.rs`. A run that never ran (no part got a runner or a step) is neither: said plainly, run again once, and it doesn't hold the stamp. Every call to `gh` is bounded (20 s); `gh` missing, signed out or offline is a warning and the pass is stamped. Branches never ask GitHub.
- **Stopping at the first failure** means a failed run shows one failure. A run stopped from outside, or refused by the queue, doesn't count against the budget.

## What a pass doesn't cover

An untracked file stops a pass being remembered only if something could read it: one inside a folder, such as a new test file or crate, or a build file at the top (`Cargo.*`, `rust-toolchain*`, `clippy.toml`, `rustfmt.toml`, `.heavy-inputs`). Untracked documents and other files at the top, such as notes, don't. The memory of a pass covers the tracked code, the test tools' versions (nextest, Swift, macOS), whether the Windows target is installed, and settings that change what tests do (`RECTO_*`, `NEXTEST_*`, `RUSTFLAGS`). It doesn't cover the real PDFs in the distillPDF checkout, which `recto-reader`'s `looks_on_real_files` and the fuzz seeds read when they're there. After changing those, use `CHECK_AGAIN=1`.

A test that fails only sometimes can pass once and then be remembered, so a failure you've seen still gets a fix. CI and the reviews still run on everything.

Never `git stash`, which is shared across worktrees. To compare with old code, use a temporary commit or a second worktree.

## Call back at an edge case

Owner, 2026-11-12: "Ask them to call back to you when they are touching edgecases, and you can give clear steer". Send the coordinator a short message as soon as you hit one (what you hit, the options, which you'd pick), and carry on with whatever doesn't depend on the answer. Don't decide these alone, and don't leave them for the hand-back:
- a constraint in the brief you can't meet as written;
- a guard that fails: the ratchet, a budget, the push guard, a refused command or permission. Never edit a baseline upward or go around a guard;
- a test failure you can't explain, or are about to call load or flaky;
- a change in behaviour, a wire format or a host-facing API beyond the brief;
- a design choice with two reasonable answers that later steps will build on;
- anything touching security, the owner's data or the owner's installed app;
- running low on working room.
