## Quality bar

- `unsafe` is forbidden in every crate except the OS seams (`recto-platform`, `recto-ffi`) and the PDFium seam (`recto-render/src/pdfium.rs` and `pdfium/contents.rs`). Every `unsafe` has a SAFETY comment.
- Clippy with `-D warnings`.
- No panics on untrusted input. Collections grown from outside input have a cap.
- A struct held per item documents its size and asserts it in a test.
- Dependencies count: `default-features = false`, few crates, and a line below saying why each one is here.

## Renderer

**The process.** One worker per document, in a plain child process on a socket pair, with shared memory for pixels and one shared word for cancelling. It inherits nothing but its channel (`POSIX_SPAWN_CLOEXEC_DEFAULT`) and an empty environment, gets the document as a descriptor, and never learns a path. No thread in the host: the call blocks its caller, which is never the UI thread, and watches while a job is in flight. A cold tab has no `DocRenderer`, so it pays for none of this.

**Limits**, all held from outside the worker, because it may be compromised:

| What | Default | Why |
|---|---|---|
| Hard memory limit | 512 MiB footprint, read every 5 ms during a job, then the sequence below | The worst real page reaches 493 MiB. macOS has no OS limit for this: `setrlimit` refuses `RLIMIT_AS`, `RLIMIT_DATA` and `RLIMIT_RSS` with `EINVAL` |
| Page deadline, with kill | 5 s | Platform §2.6. The slowest real page at 2x took 939 ms |
| Retirement | 64 MiB after a job, read from outside; the worker goes before its next job for another page. A footprint that can't be read, or reads as nothing, retires it after 8 such jobs in a row rather than never | Only exit returns PDFium's memory (spike §6). Tiles of one page share a worker: retiring between them cost 72 respawns and 14 s on the USGS map. On macOS 15 CI in the sandbox the footprint after each page never crossed the test's fixed 24 MiB though the peak did, so the test now puts its line halfway up the growth it sees, and prints each page's footprint |
| Cancel by generation | Kill 90 ms after a job goes stale, if it hasn't returned | A stale render is gone within 100 ms, by return or kill. PDFium's pause callback runs only between objects |
| Idle exit | 30 s after the last job, 3 s for a heavy worker | |

**The memory sequence** (owner, 2026-11-06), all decided in `DocRenderer`, with only the reading of free memory in `recto-platform`:

1. **512 MiB.** A worker with history gets one more try in a fresh one, because what stopped it may be what earlier pages left behind.
2. **That page alone at up to 1 GiB,** if `kern.memorystatus_level` is at least 30 and no other page has the one heavy slot. 30% is about 4.8 GiB free on 16 GB, and 2.4 GiB on 8 GB, over twice what the retry can use. The slot is per process and goes with the worker, so the worst case stays near 1 GiB. A viewer takes it without waiting. The heavy worker goes before any other page.
3. **On screen only: a lower-resolution version at a quarter of the scale,** under the normal limit, reported in `Tile::low_res` with its scale, rectangle and reason. A page lacking only memory or the slot may go sharp later (`may_clear`); one past 1 GiB won't.
4. **`PageFailed`,** with words saying even that couldn't be drawn, only once every step has really failed. If the larger limit was out of reach and the smaller version didn't fit, the page isn't given up on: `NotDrawableNow` says why, without running the kill again, until the slot or memory comes back.

What's learned holds at that scale and above, since a higher zoom costs more, and a zoom under 70% of it gets its own try (`page_draw_state_at`). Each state keeps the lowest scale it was learned at, and they only move down, so a kill at a lower zoom doesn't take away what a higher zoom learned, and going between two zooms runs no kill twice. A failed open is remembered too, so a search of a bad file doesn't start a process per page, for only as long as it holds: "not a PDF", a password or a worker the file stopped hold until the file is a different one, when it's opened anew, and a failure that isn't about the bytes, such as a failed read of its size, holds for 2 s (`open_retry_pause`). The app needn't remember to call `forget_failures`, which is for the reader's "try again". Failures clear by themselves in those ways, and when the tab closes; `forget_failures` is for the reader's "try again". To stop a file of many bad pages: at most 8 heavy retries per document, then pages go straight to step 3, and at most 128 kills, then `DocumentStopped`, until asked. A cancel between steps ends the sequence, taking no slot and starting no worker.

**Too large at this zoom** names the largest scale that fits, from the page's size and the caps (`largest_scale_that_fits`), to two decimal places, so an agent doesn't try 8, 4, 2 and 1 by hand. It's a statement about size alone: a heavy page can still be refused for memory at that scale, in words of its own. `render --scale max` draws at that scale and says which, and goes down the same limits as any export, so it's sharp or it isn't written.

**A refused export says the limit, and how long it took.** Whether a smaller scale is offered goes by the picture's own size: it must be at least an eighth of the 1 GiB limit, at a scale above the smallest there is. Otherwise it's the page's content using the memory, and the refusal says a smaller scale won't help. `form_bomb` is 625 KiB at 2x, 9.8 KiB at 0.25x and 9.8 MiB at 8x, and fails the same at each in 2.9 s. `render` gives `took_ms`, and says it in plain words too.

**Exports differ** (owner, 2026-11-07). Whole-page drawing (`recto render`, later print and snapshot) goes in strips under the same limits, with `DrawPurpose::Export`. Step 3 doesn't apply: an export is sharp or isn't written. If it needs the larger limit it sleeps for the slot, up to `export_slot_wait` (60 s), ahead of any viewer, and a cancel ends the wait at once. No memory free, the wait running out, or the page passing 1 GiB each refuse plainly with nothing written: `export_memory_tight`, `export_wait_timed_out` (exit 7), `export_page_too_heavy`. It can block for a long time, so it's a call for a job thread, never a UI thread. On-screen tiles still never wait. The slot's ticket lives in the heavy process's end action, so it frees when the process has really gone, however it went, with nobody needing to touch its document. An idle heavy worker leaves after 3 s (`heavy_idle_exit`), and is killed by 8 s if it doesn't. A worker the host doesn't watch would be free to grow, so during a job the worker also runs a small thread of its own that checks its footprint, its deadline and whether the host is still there. That thread starts with the first job and parks between jobs.

**Between jobs and at exit.** One reaper thread in the host, alive only while a worker is, sleeps in `kevent`. It collects a worker the moment it ends, and at most once per `idle_exit + idle_grace` (35 s) per live worker it checks the idle rule: past its time or its memory limit, the worker is killed. That's one wake-up per 35 s per live worker, none with no worker, and no thread or handle left behind. A compromised worker could still grow unseen between those wake-ups: closing that needs the sandbox's memory limit. Killing never blocks: a process stuck in a read from a dead network volume can't die until the read returns, so the host signals it and moves on, and the reaper collects it whenever that happens. This wasn't tested against a real dead volume; the property tested is that nothing waits.

At 256 MiB, 17 are refused, and at 170 MiB, all 28. A kill overshoots by up to about 55 MiB on a large image's single allocation.

**The USGS map, before and after.** Whole page as tiles at 2x went from 3.75 s to 0.70 s, peak 339 to 426 MiB, and at 4x from 10.9 s to 2.95 s, peak 342 to 448 MiB. `recto render` at 2x is 0.83 s; at 4x it was stopped at the limit and is now 2.46 s, peak 468 MiB.

**The first pass's 450 ms** is about half inflating the two images' Flate streams and most of the rest stretching them (sampled at 0.25x). It's the same at any zoom, because every source row must be inflated. Nothing short of a change to PDFium or a preview cached from an earlier run avoids it.

**The renderer is hostile.** Replies go through `recto-proto`'s decoders and validators before anything uses them; any violation kills the worker. A frame's claimed length costs nothing until bytes arrive. Pixels are copied out of shared memory, never referenced in place, and shared memory can't be resized once sized on macOS, so a worker can't make the host fault. A compromised worker can still draw a wrong picture and rewrite a surface it was given earlier; that's the limit of this design until surfaces are per-job IOSurfaces.

**Sandbox.** In the app the worker runs in the App Sandbox, in a helper app of its own, as the spike recommended (`docs/research/2026-11-07-sandbox-spike.md`): not XPC, which allows one process per app and delays a restart by 10 s, but the same child process, socket pair and shared memory as before, from an executable signed with `com.apple.security.app-sandbox` and nothing else (`app/RectoRender.entitlements`).

```
RectoPDF.app/Contents/
  MacOS/RectoPDF, recto, recto-indexer, recto-headings, recto-updater     Not sandboxed (SPEC decision 3). No worker or PDFium here.
  Helpers/RectoRender.app/Contents/
    Info.plist                       io.github.kkollsga.RectoPDF.Render, LSBackgroundOnly. The sandbox takes its identity and container from it.
    MacOS/recto-render-service       The one entitlement. Hardened runtime when signed by a team.
    Frameworks/libpdfium.dylib       Signed by the same team, so library validation passes with no exception.
```

- **Its walls, from inside** (`recto_platform::wall`). After PDFium has loaded and before the hello, so before any document reaches it, a worker that's in an app bundle, or is a release build wherever it is, puts up two walls and checks both.
  - **The App Sandbox is on**, asked positively: the kernel says this process is sandboxed (`sandbox_check(getpid(), NULL, 0)`, libsandbox's documented-in-practice way, as Chromium and WebKit ask), and the App Sandbox gave it a container, which it says in `APP_SANDBOX_CONTAINER_ID`. The host starts a worker with an empty environment, so only the App Sandbox can have set that, and an inherited seatbelt, sandboxed but with no container, reads as no. Nothing is denied or logged, and nothing depends on where the home folder is. (The first build listed `/Users` and wanted `EPERM`: proven only on this Mac, whose home isn't under `/Users`, and a sandbox violation logged on every start.)
  - **The Mach drop:** every send right to another process goes, and launchd's whatever the kernel says of it. Each right is described by `mach_port_kobject`, then the older `mach_port_kernel_object`; a kernel object is kept, and so is any right neither call will describe, since dropping one a library still uses could crash it later, and so is a send right to a port the worker itself receives on, which reaches only itself. Each name let go of is left behind as a dead name with as many references: a library that held the right, `libxpc` for one, later releases it, and with the name gone the kernel raised a Mach port guard exception (`kGUARD_EXC_INVALID_NAME`), about three a worker on this Mac, logged as non-fatal, 15,816 in a morning of tests (2026-11-08). With dead names, none in 40 workers on a blank page and on `rfc9110`. A bare worker with no sandbox and no drop still raised them on some runs (27 in 10 workers once, none the next), from system libraries, not from anything here. Then launchd must not answer a lookup. The drop is there because the sandbox alone still lets a process launch any app through LaunchServices, and the app runs outside the sandbox; no entitlement takes that away. Receive rights stay, so the surface link made before it keeps working.
  - Each failure exits with its own code, and the host names it: `renderer_not_sandboxed` (77, the only one that says the app is signed wrong), `renderer_mach_drop_failed` (78) and `renderer_launchd_reachable` (79), which are about the OS. The hello carries a `walled` bit. A release host, and any host given a worker from a helper, kills a worker that says its walls aren't up. A bare worker in `target/` runs without the sandbox and says so, as development and most tests need.
  - **Inside another sandbox**, an agent's seatbelt round `recto` for one, the system ends the helper before its first line (SIGTRAP, measured under `sandbox-exec`), as it won't start an app's sandbox inside another. The host, sandboxed itself, says `renderer_inside_another_sandbox`: run `recto` outside it, nothing to reinstall. A spawn the system refuses with `EPERM` or `EACCES` is `renderer_start_refused`.
  - **An agent sees it:** `qa state` has `memory.workers_walled` beside `memory.workers`, and `budget render` has `walled`, from the hello.
- **What it can reach.** The document and shared memory come as descriptors, which the sandbox doesn't need to allow. **Search text.** `recto-index::normalize` turns PDFium's characters into text `rg` can search. Its rules and their limits are in that crate's header. In short: at a line-end hyphen it follows the rest of the page if the page shows a form, keeps the hyphen for capitals, one- or two-letter tails and a short closed list of compound words, and otherwise joins. It's a guess, so the other spelling of each decision goes in `also_spelled`. Lines stay lines. On bench100 it joined 12,297 and kept 1,627, with no `simulationbased` or `datadriven` left, and line hits equal to the spike's normaliser on every common word checked but one (`office`, 633 against 634), plus 4 more for `simulation-based`. A hyphen on a page number or a marker doesn't join: a number between hyphens, `-17-`, whatever follows; a real roman numeral or one letter between hyphens, `-iv-`, unless a small letter follows; or a number or one letter alone on its line, `17-`, above a capital. Without that, `wbD34442284` p. 17 read `-17-PBC`. Real tokens still join: `10-` above `year`, `X-` above `ray`, `-civil-` above `ian`, a range of numbers alone on its line, and a number in a sentence, since that's how `21-cm` breaks. Over all 5,872 pages of bench100, compared line by line with the rule switched off, this changes 47 lines, all page numbers in 4 World Bank documents.

**Line order.** A PDF can draw a line's styled words after the rest of the page, and PDFium returns drawing order, as `pdftotext -raw` does. RFC 9110 p. 110 read `A recipient ignore If-Modified-Since`, with `MUST` at the bottom of the page: a dropped `MUST NOT` turns a sentence round, and a search for the real words finds nothing. `recto_index::read_page` is the one place `text` and `search` read a page, so they can't disagree. It uses each character's box. A later run goes into an earlier line if its baseline matches and it fits a word-sized gap, or sits a word's space past either end (`Section` at a line's end, `2.` at its start). Everything else stays in drawing order: no layout sort, since the spike (§10.2) found that right for two-column text on 79 of 84 pages.

The rules that keep it from doing harm: each side of a run with a neighbour must be within 0.8 of a character height, the middle of the line's characters so one tall symbol doesn't widen it. On RFC 9110, 99% of real gaps are under 0.76, with a median of 0.53. A run on the end of a line must not start or end level with the lines drawn around it, since that's what a table's cells do down a column: `wbD34442277` p. 11's gutter is 2.9 pt beside a 3 pt word space, so width alone can't tell them apart, and it read `utilizing at least utilizing at` before this. All of a line moves or none of it, and a run doesn't pass anything drawn since that sits on or against its line, so a fraction or a superscript stays where it is in an equation. Text running backwards, upwards or on a slope is left alone, a line-end hyphen stays at its line's end, and letters touching across the end of a line aren't joined. Only whitespace is ever added or dropped.

**What's left in drawing order:** a whole line drawn late with nothing on its baseline, such as RFC 9110's code samples and page headers. And reference lines whose punctuation is drawn first: `rfc9293` p. 85 reads `, , ,` then `eid1572>.`, because the later run overlaps those gaps rather than fitting them. Mathematics mostly stays as broken up as PDFium makes it, at every raised symbol. Not tested on a real right-to-left PDF: none of the 454 under `distillPDF` has any.

**Hidden text.** The spike's prototype: draw the page at 2x, mark a character with no ink under its box (range under 16, box padded by 2 px). `hidden_text.flagged` means a run of 3 or more such characters; shorter ones are thin glyphs, and stay in the count. It's a flag: every character stays in the text, under `untrusted`. In plain `text` a line holding a flagged run starts with `! ` rather than `| `, and the run is inside `[hidden: ...]`. Every line has one of those marks first, so a page can write `[hidden:` but can't print a line that's marked or unmarked other than it is. `hidden_spans` gives the same places in characters of `text`, and moving words can't help anything hide. The flag is judged in the order the file gave, so a run can't lose it by being scattered into a line's gaps, and in reading order, so pairs of hidden letters can't assemble into a word unflagged. On a line a move has touched, every character with no ink counts, however short its run. On bench100 that adds nothing: of the 2,016 changed pages, 13 are flagged in the file's order, and none only once words moved. Its limits: hidden text next to visible text passes, because the box has ink. An OCR layer over a scan is expected to pass, but this corpus has no scan to prove it on. Annotation text the page draws isn't in page text at all (spike §10.4). If the extra render stops the worker, the text comes back with `checked: false`, which never reads as clean.

**How far the flag can be believed, reviewed 2026-11-07.** `examples/hidden_corpus.rs` flags 129 of bench100's 5,872 pages, with 19,833 characters with no ink. 37 of those pages were drawn and looked at, by a box round the two longest runs of each: 7 arXiv, 8 NASA, 5 USGS, 6 World Bank and 11 UN. On all 37 the text is really not there to see: the box is blank, or off the page. **No false alarms in the sample**, and the check wasn't changed. MuPDF, as a second opinion on all 129 pages: of 19,752 no-ink characters, 10,465 are off the page, 9,081 have no ink in its drawing either, and 206 (1%) do, scattered single characters at the edges of neighbouring ink, and 99.7% of the characters the check passed have ink there. Those two renderers agreeing isn't proof that nobody could ever see these, and the runs not looked at weren't.

What made them look wrong is that **most of it is harmless, and the check can't tell.** `Am[hidden: bient Air]` on `ntrs20220005969` p. 159 looks like a chart label wrongly marked, and it's a second copy of the label. The file has `Ambient Air` twice, at x 386, drawn, and at x 415, not drawn, and pdftotext's boxes show both. The second copy's first letters overlap the first's `Air`, so they have ink, and the mark starts partway through the word. What's in the sample: copies of figure labels left outside a crop (arXiv, NASA), text off the page's edge (the World Bank's `For Official Use Only`, a NASA back cover), designers' notes (the UN's `Two different guide layers for two- and three-line titles`), and white text in a blank margin (the World Bank's `Public Disclosure Authorized`). So the words say what's known and no more: text that looks hidden, in the file, with nothing drawn where it sits, often harmless, sometimes planted, and this can't tell which.

## SVG export

`recto export svg` writes a page, or a box on it, to a new SVG, with the same `O_EXCL` temp file and `link(2)` publish as `render`, at Full. **Nothing is held.** The worker reads PDFium's page objects and answers one frame of records at a time, usually about 1 MiB and at most 16 MiB, only when asked (`recto_proto::contents`). The host checks each record (`StreamCheck`) and passes it straight through `recto-svg` to the temp file. So the host costs one or two frames, one row, one compressor and a small buffer, however large the page: an image's rows go through as they arrive, base64 and PNG included, and a path's numbers are written as they're read. The worker holds the page PDFium has parsed, and the image in hand.

It goes down the same limits as any export (`DocRenderer::read_contents`): 512 MiB, then that page alone at 1 GiB with the wait for the heavy slot, sharp or refused with nothing published. A worker stopped partway means starting again from the top in the larger one, with the temp file emptied first. There's one deadline per frame, and one over the whole page, so a worker can't keep a job alive by always saying there's more. Being asked for one frame at a time is also what holds a hostile page to a pace the host decides.

**What's read, and from where.** PDFium's objects, rather than a content stream parser of our own: paths with their matrices, clips, text, images and forms. Forms are flattened into page coordinates, so the file's nesting isn't its depth: a clip stack is a chain of at most 32 `clipPath`s, and opacity groups nest at most 16. What PDFium's calls can't say, and what's done about each:

| Can't be read | How it's noticed | What comes out |
|---|---|---|
| A shading | Its object type | A picture of just that element |
| A tiling pattern | `FPDFPageObj_GetRenderedFillPattern` is the one call that tells | A picture of just that element |
| A shading pattern, which reads as plain white | The file's structure says the page has one, and that white thing draws in colour on its own | A picture of just that element |
| A blend mode or soft mask on an object | `HasTransparency` at full opacity, or with the structure saying the page uses one | A blend: a picture of it over everything under it, 32 at most. A soft mask: of just it |
| The same on a form | `HasTransparency` can't tell these from a plain transparency group, so the structure decides | The same, with its text kept selectable |
| Anything clipped by text | Text in a clipping mode. There's no call for the clip, so what comes after it in its form goes as pictures, which obey it, a little more than may be needed | A picture of each |
| Stroked text | Its render mode. A pen's width goes by a transform PDFium keeps to itself, so an outline's stroke can't be the right width | A picture of just that text, with its characters kept |
| Annotations and form fields | They aren't page objects | One picture of just them, if they draw anything. A link with no appearance doesn't |
| Whether a layer is on | Asked of every object: its `/OC` marks go on a plain box that always draws, and the box is drawn alone, so PDFium's real rule decides, memberships and usage included. Forms and images, which name a layer where no call reaches, are drawn to see wherever the document has layers or one names any. A layer is remembered by its mark, or by its whole name only if everything the page's `/Properties` can name is a listed layer with a plain name no other has. Past 64 marks on an object, or the limit on looking, it hasn't been shown to be visible, and the page goes as PDFium draws it. | Left out, and counted. Past 1,024 looks, nothing unchecked goes out as itself: the page is drawn whole at the end, which obeys its layers, and any text in what wasn't checked isn't kept |
| A clip's fill rule | There's no call. It only matters to a clip of more than one shape, or that crosses itself, going by its corners | A picture of what it clips, which obeys the real rule |

`FPDFPageObj_SetIsActive` is what makes "just that element" exact: every other object is switched off and the page is drawn, on transparency, clip and all, in strips, at `--scale`. This changes the page in memory, and it's thrown away when the walk ends. The structure comes from `recto_core::page_effects`, a bounded walk of the page's resources through the lazy reader, down through forms and patterns without reading a stream's bytes. If that can't be read it says nothing, and everything's assumed. Past 512 pictures, 4 pages' worth of pixels, 32 blends or 4,000,000 objects, one picture of the whole page goes last, opaque, with the text kept selectable and the pointer let through to it. Each kind is listed in the answer in plain words. Nothing is dropped without saying.

**Text is exact outlines with real characters over them, invisible** (`--text both`, the default). Selectable text alone (`--text selectable`) is the smallest and is what a text editor wants, but it looks like whatever font the reader has. Outlines alone (`--text paths`) are exact and can't be selected. Both together cost about half as much again as outlines alone, and keep what each is for. A glyph's outline is defined once and used by number, so a page costs its letters plus about 30 bytes a character. The trade-off stays open: it's one flag, on the same records.

**A glyph's outline can be the wrong one.** `FPDFFont_GetGlyphPath` goes from Unicode back to a character code, which a font's map doesn't always lead back from, so a math font's `σ` often has no outline, and two codes for one letter can lead to the wrong one. Each outline is checked against PDFium's own box for the character, and if it's off by more than 0.12 em or missing, that text goes as a picture with its characters over it. A ligature's parts share an origin, so they're tried as the ligature's own character. There's no call that gives an outline by character code: this is the most that can be had without parsing the font programs.

**Images.** At their own resolution, and pixels byte for byte as PDFium decodes them (colour conversion is PDFium's). A mask needs PDFium's drawing to apply: it's found by drawing the image small, then drawn at its own size. That isn't byte for byte, and a mask finer than the image is resampled to it, so these count apart, as `images_drawn_with_mask`. That call obeys the object's clip as well, in coordinates that mean nothing once the image is laid flat, and no call takes a clip off, so the clip is blown up around a point inside it for the moment it's drawn, and the real clip goes in the file. PNG uses the `Up` filter and needs one row of memory, and the host holds a row to 8 MiB whatever a worker says. A clip is blown up to clear the image for that drawing, around a point inside it and only as far as it must go: PDFium takes it through where the file placed the image, and its filler bends shapes past 50,000. One that would have to go further stays a picture.

**JPEGs keep their original bytes** (owner, 2026-11-07: "Lets do original bytes"), EXIF, XMP, comments and bytes after the end included, so one in the file is byte-identical to the one in the PDF, where it means what the page means. `recto_proto::jpeg` reads its structure, in the worker to choose and again in the host, which stops a worker that sends anything else, and counts what it carries from the bytes. It goes as PNG if: it isn't sound; it's not one `DCTDecode`; it isn't grey or RGB, or an ICC profile that says sRGB, since a reader would take any other for sRGB; the structure says the page has a `/Decode` or `/ColorTransform` that changes it (`/Decode [1 0 1 0 1 0]` is the inverse in a PDF and plain in an SVG); it has a mask; its EXIF says to turn it, which a page ignores and Chrome was seen obeying inside an SVG; or a box cuts through it, since a JPEG can't be cut losslessly. The answer's notes say what the JPEGs carry, with counts. `--strip-metadata` (owner, 2026-11-07: "Just add it in the cli for now (agent option)") takes out EXIF with its GPS and thumbnail, XMP, comments, other application blocks and bytes after the end. It keeps JFIF without any thumbnail and Adobe's marker, which a decoder reads to know the picture's colours, and a colour profile, which says what they mean, and the compressed picture stays byte for byte. On 161 JPEGs from 12 bench100 pages, 160 of them with metadata to take, PIL decodes the same pixels from each. Such a JPEG counts in `images_jpeg_metadata_removed` rather than as original bytes. It also leaves out the title, as a box always does.

**A JPEG that would look different is corrected around its picture** (owner, 2026-11-07: "Cant we fix the decoding instead?"). Everything from its first scan on stays byte for byte, the result is read back by the same parser, and any doubt goes to PNG. EXIF saying to turn it is set to upright. A profile of its own the page doesn't go by is taken out, and a non-sRGB ICCBased page profile goes in as APP2 segments, up to 1 MiB. On real JPEGs with real Adobe RGB and Display P3 profiles, against `render`: mean difference 0.3 to 0.7 of 255 on every case, in Chrome and in WebKit (`qlmanage`). A JPEG with a soft mask keeps its picture, with the mask beside it as lossless grey through SVG's own `<mask>`; a `/Matte` goes the old way. PDFium has no call for a mask as stored, so one finer than its image is resampled to it, as before. PNG, with a note saying which: a `/Decode` or `/ColorTransform`, a JPEG written in the page's drawing, a colour space like CMYK, a mask blended ahead of time, and one a box cuts. The page's and forms' drawing is read through a chunk at a time for `/DCT` to find the ones written in place, up to 256 MiB or 500 ms, and a protected file's is decrypted a stream at a time up to 8 MiB. Past those, the page's JPEGs go as PNG.

**Hidden text.** `hidden_text` in the answer is the same check `text` gives, from one function, run once the page is known to draw, for the whole page whatever the box. Characters in mode 3 or 7 are counted where all text passes, whichever route it took. Measured, median of 7, under load, against `--text paths`, which has no text to check: `rfc9110` p. 10 30 ms against 20, `math_AG` p. 5 35 against 22, `eu_gdpr` p. 10 30 against 15, `cs_CV_28611` p. 20 283 against 173, and about 10 MiB more in the worker, since it draws the page at 2x.

**A box leaves out what's outside it, and doesn't hide it.** A path not all inside, and a turned image crossing the edge, go as a picture cut to the box. An upright image is cut to the box by its own pixels. A clip that reaches outside and isn't an upright rectangle sends what it clips to a picture, and one that is, is cut to the box. Text goes a character at a time. So what's in the file from outside is at most the rest of a letter that crosses the edge, and the rest of a pixel. Measured on the middle half of the same 274 pages, before and after: 148 pages stay as they were on text, 106 pages all vector becomes 53, 144 have pictures for this (1,928 in all), and paths 8,153 become 6,153. Size doesn't suffer: 109.6 MiB in all becomes 101.3, with p50 130 KiB to 133, and time p50 46 ms to 62, part of which is the hidden-text check.

**What's lost, or can't be known.** A miter limit: no call, so always 10, PDF's default. A form's soft mask or blend on a page whose structure the reader couldn't see through. Text PDFium makes bold itself when it substitutes a font. `/Decode` on an inline JPEG, which isn't an object the structure's walk reaches. A JPEG's embedded profile is kept, and a browser honours it where a page with a plain RGB colour space doesn't. An image mask so slight that a 64 x 64 drawing shows nothing. Hairlines other than zero: PDFium never draws one thinner than a device pixel, and a browser will. A line of no width is one pixel at any zoom (`vector-effect`), which a reader without that can show as one point. Gradients are pictures: `recto-svg` can write them, but PDFium can't read them.

**Hostile.** Text is escaped, and characters XML can't hold or that change how text reads unseen are dropped along with their positions and counted. Attributes hold only numbers, fixed words and a font name cut down to letters and digits. The only hrefs are `#g12` and `data:image/...`. Numbers go through integers, so no `NaN`, no `inf` and no `1e+39` can be written. `recto_svg::verify` reads output back strictly, for tests. Every record is checked for form, and against the stream: ids in order, one image at a time with exactly its bytes, a JPEG starting as one, groups closed. Any violation kills the worker with nothing published.

## Images and snapshots

SPEC section 6, Extraction, and the owner's 2026-11-08 decision on copy-restricted files. `recto_agent::extract` is the one place that says what comes out and where it goes: `recto images`, `recto image` and `recto snapshot` write files or answer, and the app's snapshot tool asks `image_clip` and `snapshot_clip` for the clipboard, with its types and their order.

**Images go through the contents walk, asking only for images.** A `ContentsJob` now says which images it wants (`images`): everything, as `export svg` has it; `IMAGES_LIST`, where each image is as an `ImagePlace` record (its own pixels, whether it's a JPEG stream, its matrix) with no bytes and nothing else of the page; or one number, that image whole and as itself, with no clip, group or blend, a masked one as a single RGBA picture (`MASK_NOT_SEPARABLE`). Both modes count images at the same point of the same walk, so a number from a list is the image it names, and layers still decide: an image in a layer that's off isn't listed and can't be clicked. The host's `StreamCheck::for_images` refuses whatever the job didn't ask for, and a second picture for one number, which kills the worker as any violation does. A list draws nothing, so on the 346 MiB USGS map (66 images) it took 0.82 s, release, at load 10 to 12, with the host at 3.8 MiB peak and the worker at 351 MiB, nearly all PDFium opening that page.

**What an image comes out as.** `.jpg` takes a JPEG's own bytes, or its picture byte for byte with what's around it corrected (`jpeg_header_fixed`, as `export svg` does), and anything else is refused before a byte is written (`not_a_jpeg`), as it would be re-encoded. `.png` takes any image losslessly at its own size, a JPEG decoded as the page decodes it, a mask as alpha. An image PDFium can draw but not hand over is drawn alone at 2x and says `lossless: false`. On the clipboard, a JPEG goes as `public.jpeg` with a `public.png` beside it for apps that can't take a JPEG; anything else as `public.png` alone.

**A snapshot** is a box in points on the page as it's shown. PNG and JPG go through the export's drawing (`draw_page_box`, strips over the box, the page itself held to the caps, so a box can't get past them), sharp at the scale asked or refused. JPG is a small baseline encoder of ours (`render/jpeg.rs`: 4:4:4, quality 90, Annex K tables, the AAN float transform), streaming eight rows at a time, and every answer says it's re-encoded. SVG is `export svg`'s writer cut to the box, now generic over where it writes (`Output`: a temp file, or memory up to a cap). Text is `PageText::text_in_box`: characters whose middle is in the box, a line at a time in reading order, hidden text and chrome left out by a copy's rules, and a box of only chrome gets the chrome. On the clipboard all four go at once, PNG, text, SVG and JPG, each up to 32 MiB and 64 MiB in all: past that one is left off and the notice says which. The PNG is the snapshot, so its failure is the snapshot's.

**A file that asks not to be copied** is refused, exit 8 and `copy_restricted`, unless `--anyway`, for every format and for images, and for every export too: `render`, `export svg` with or without `--rect`, and `print --to-pdf` (owner, 2026-11-08: "Yes, same step"). Each use that gives something goes in `activity-overrides.jsonl`, as `copy --anyway` does, checked end to end through the real `recto`. **The flag is read straight from the file** (`recto_core::copy_restricted`): the encryption dictionary's `/P`, bit 5, which is document-wide and plain, so no page, worker or character is read, and a refusal costs nothing. Only a file the structure reader can't open asks the renderer, and one neither can say is taken as not asking, so an image copy can't fail because a page's characters can't be read (review, 2026-11-08). In the app, every export path offers the notice: the snapshot tool's "Copy anyway", and a print the panel saves or previews as a PDF, which gets "Print anyway". Each button names the notice that offered it, so a stale one takes nothing, and turning the tool or pressing for a new box takes the notice away.

**The clipboard, after review** (2026-11-08):
- **One job at a time.** A release while a snapshot is being taken stops it, through its worker's cancel word (`ClipStop`), and waits in its place, the newest only (`JobSlot`). Ten clicks on the USGS map were ten workers of 350 to 750 MiB at once; now they're one at a time, on the one thread.
- **Every item is made into a buffer capped at the room left** under 32 MiB each and 64 MiB in all, so nothing past the cap is made and then dropped.
- **PNG and JPG come from one drawing**, each row going to both encoders; the JPG is the extra, dropped if it passes its cap.
- **The SVG is promised, not made:** it's declared on the pasteboard and made by `extract::snapshot_svg` only when a paste asks for that type, which on the map is the larger worker's 742 MiB. Another process reading the PNG and the JPEG left it unmade (checked with a second process on the quiet run's named pasteboard); a read in this process resolves the item's promises, which `qa copied` allows for. The system asks on the UI thread and waits: the one wait there, only for a paste of the SVG from another app. On the way out a promise isn't kept.
- **The clipboard's SVG has text as outlines only** (`TextMode::Paths`), so hidden text stays out of it as from the text item; a file's SVG keeps real text, as `export svg` does.
- **One offer.** A text copy and a snapshot reach the host as one `ClipboardOffer` from `take_clipboard`, its types in order and which are promised, and each type's bytes come one at a time from `clipboard_data`, dropped from Rust as they go. So at most one item is across the bridge at once, rather than all of them in one record: the copies are Rust's buffer, UniFFI's, Swift's `Data` and the pasteboard's. Fewer would need a C entry point handing Swift memory it frees itself (phase R).
- **A JPEG on the clipboard ends where its picture does:** bytes a file put after the end are left off. A file written keeps every byte.
- **`image --out` is held to `OutputCaps::max_bytes`,** as `render` is (`LimitedOut`).

## Printing

`recto_agent::print` is the one drawing a print goes through: `recto print --to-pdf` writes its result where it's told, and File > Print… writes it to a file of the app's own that the system's printing then takes. Each page's size is asked of the worker once, and it's drawn by `draw_whole_page_sized` at the dpi asked (300 by default, 72 to 600), the export path, so it's sharp or refused, waits for the heavy slot as any export does, and knows nothing of paper colour. Its rows go straight through a zlib compressor into a PDF of one picture a page, written by a small streaming writer of ours (`/FlateDecode` RGB, an indirect `/Length`, the page tree and the table last). So the host holds one strip, one row and the compressor's buffer, whatever the length, and the PDF it makes is new: it never writes over anything, least of all the file being printed. Only the lopdf writers change a document's bytes; other writers, this one among them, only create new files (AGENTS rule 5). Its cross-reference table is checked by hand in a test, every offset landing on its own object, as the lazy reader and PDFium would both repair a broken one. **A page too large to draw whole at the dpi asked** (A0 at 300 dpi is about 139 Mpx, past the 100 Mpx cap) prints at the most it can be, `largest_scale_that_fits`, and the answer and the app's notice say which page and at what dpi, rather than the whole print failing. **A PDF's flag against printing is ignored** (owner, 2026-11-08: "Ignore the flag"): nothing reads it. A print to a PDF file is an export, so a file that asks not to be copied asks "anyway" (`--anyway`, logged); print to paper never does. **SSD:** the app's print is written once to a temp file and removed when the system's printing is done with it, about 0.3 MB a page of text and 50 MB a map page at 300 dpi, held to 4 GiB in all, which is one write of what's printed, as the system's own spooling would make. A page's unsaved quarter turns go on its page as `/Rotate`; its picture stays as drawn. An edited tab's pages each come from their own file, with at most two workers open. Caps: 10,000 pages, 4 GiB, and a page past the 1 GiB limit is refused with nothing written.

**In the window**, the system's `NSPrintPanel` asks which printer, how many and which pages, with Selection offered when something's selected (`AppCore::print_model`). Its answer goes to Rust (`print_chosen`, `printing::chosen_range`), which prepares those pages on one `recto-print` thread, saying "Preparing pages for printing: 3 of 20." by the page, and sets `print_ready`. The host then hands the file to an `NSPrintOperation` of a view that draws its pages with Core Graphics, fitted to the paper, with no panel since it's been answered, on a thread of its own (`canSpawnSeparateThread`). The file goes when the operation's done (`print_finished`, which removes only a print file of this process's). **Stop** sits beside the progress line (`print.stop`), and closing the tab or quitting stops it too, at the next page, with its file removed; a launch removes the `recto-print-PID-*` files of runs whose process is gone, on a short-lived thread. An update waits for a print being prepared, one ready and one being handed over (`printing` in the hand-off's busy list, as the print's thread is done before the system has the file), and so does `qa wait-settled`. `qa print-to-pdf` has the system write to a new name of Rust's beside the file asked for, published there when it's done, never over anything (`print_qa_target`). At rest there's nothing. `qa print-to-pdf OUT[|FIRST|LAST]` drives the same path with the job saved to a file, on paper the first page's size with no margins, so the result lays page for page over the source; the test compares 8 px blocks, as text edges move a little when a page's picture is drawn again, and dark paper on screen or a wrong page would change most of them.

## The app

`app/` is a Swift package with AppKit and no SwiftUI. `app/build.sh` makes `app/build.noindex/RectoPDF.app`: Rust, then the bindings, then Swift, then an ad-hoc signature, with `recto`, the worker and PDFium beside the app's executable for now (at release they move into the nested helper: `docs/research/2026-11-07-sandbox-spike.md`). `--quick` needs no Xcode. `--full` builds the app and drives it. Where a worker comes from is in one place, `Worker::start`.

**One session.** The app holds a `SessionHost`, runs the same `Server` on a thread blocked in `poll` (started once the state's been read, so nothing's asked of an empty session), and wraps it in a `Host` of its own, so `recto tabs` and `recto goto` act on what's on screen. What the app does itself goes through `with_session`, as the owner's. A socket another session holds doesn't stop a normal run, and a QA run refuses. Things the reader does that aren't commands reach watchers through `Server::announcer`.

**Threads at rest, all parked or asleep:** main, `recto-control` in `poll`, `recto-session` on a condvar, `recto-pages` parked, `recto-watchdog` parked, the reaper while a worker lives, and AppKit's own. The UI thread calls Rust for three things: `set_viewport` on each scroll (a short lock and a few map lookups, at most 8 surfaces reclaimed), `drain_ops` when told there are some, and pulling a published snapshot of the sidebar. Anything that can take time goes on `recto-session`, because waking a cold tab reads its file with the session's lock held. So it can stall the session thread, and `recto status` and the UI thread both still answer. No display link: tiles arriving hop to the UI thread once each, which needs no tick at rest and works off screen.

**How a tile reaches the screen, with no copy.** The host makes the surface, so it's charged to the host and outlives the worker. A socket pair can't carry an IOSurface, since it crosses as a Mach port, so each worker is started with a send right in an exception-port slot that nothing raises, set by `posix_spawn`. It sends back a send right to a port of its own and clears the slot. There's no name in any registry, and after that the host never receives from it. A job's surface goes to that port just ahead of its frame, the worker maps it, draws, and unmaps, and the layer's `contents` is that same surface. Measured with 64 tiles: the host's footprint rises 64 MiB, the worker's by nothing, and creating, sending, looking up, filling and hearing back is 0.13 ms a tile. A copy into a surface would have been 15 µs warm a tile, plus its first touch, so this wasn't for speed: it's so there's one copy of a tile, and so a worker's limit doesn't count tiles. **In the sandbox:** the same two programs in a helper `.app` with the App Sandbox entitlement and the spike's Mach drop run correctly: rendezvous, 64 surfaces round trip, pixels verified, host charged. The drop leaves receive rights alone. The first surface takes 64 ms and adds about 4 MiB to the worker, loading IOSurface after the drop. That's the C test only, with no PDFium in it. **What this gives up:** "pixels are copied out of shared memory" no longer holds on this path. A compromised worker can keep its right and rewrite a tile that's on screen. It could already draw a wrong picture, but it can now change it later. `recto render` and everything else that writes a file keeps the shared-memory path.

**Regions** are one surface and one layer, with no cutting up. Blank tiles get no surface, only a colour, or nothing if they're the paper's colour. Grey tiles are still BGRA: `L008` would take a text page's tiles to a quarter, and it's only known correct in `render(in:)`, not on a real screen, so it waits for the MacBook spike.

**What's kept**, all in `recto_reader::tiles`: what's on a layer stays. Off a layer it goes discardable the moment the host says it's applied, which takes it out of the footprint: 64 tiles go from 66.6 to 2.7 MiB. Kept: 256 MiB and 1,024 surfaces of tiles, least recently used first, and 128 previews, which outlive their tiles. **A surface serves one job.** There is no pool: a worker can read and write a surface it was sent for as long as it lives, so reuse would be a way from one file's worker to another file's pixels. It costs 51 µs more a tile, 67 against 16 p50, nearly all the first touch of its pages. Attached: at most 8 a turn, with every visible page's preview first. A cold tab has no entries and no renderer, and a closed window has neither. The page layout costs nothing per page: pages are taken to be the size of the first one known until asked about, and only pages of another size are stored, so a file claiming 8 million pages costs nothing until it's read.

**A worker past the retirement line goes 3 s into a pause** (`BIG_WORKER_REST`), not the idle rule's 30. It's the only timer in the page view, and it's there only while such a worker is. The USGS map at rest goes from 433 MiB to 36 MiB, and the first move after that pays for the image again.

**Pinch and scroll.** Layers are page-relative in PDF points, under one transform per page, so a pinch moves one transform and a change of fit moves no tile. Tiles stretch during a pinch, and nothing's drawn until it ends. New tiles go on top of old ones, which come off when the page's visible tiles are all there. Pages are snapped to whole device pixels. `NSScrollView` does the scrolling, so rubber-banding, momentum and the scrollers are the system's. **Not checked on a screen:** a quiet run has none.

**Dark paper** is done to the tile's pixels in `recto-reader`, not by a layer filter: a filter makes the compositor take an offscreen pass every frame, and `render(in:)` leaves it out, so a shot wouldn't show it. On a page of text, lightness turns over and each pixel keeps its distance from grey, so a blue link is lighter blue. **Text keeps its weight** (owner, 2026-11-07: "The font in the future competitiveness is not super readible. I think its a bit to skinny"). On white paper the tiles are what Preview draws: PDFium draws glyphs through Core Graphics on a Mac, and part A p10 at 1, 1.25, 2 and 2.5x has the same ink as Core Graphics with font smoothing to four places, the app's tiles at the device scale (2.55 at fit on a 2x screen). On dark paper it was thinner: turning lightness over in sRGB's encoding left a letter's edge giving off less light above the paper than it took from white, 0.71 of it in linear light on that page, and in Helvetica, Helvetica Neue Light and Avenir Light at the same scale 0.86 to 0.89 of what Core Text draws as light text on the same dark paper. Paper-ness now goes through `TURNED_LIGHTNESS_POWER`, 1.8, before it's turned, which brings those to 0.98 to 1.00 and part A's to 0.85. White and black land where they did. **The curve is for text and lines only** (owner, 2026-11-08): a pixel whose channels are within `CURVE_GREY_SPREAD` takes all of it, one past `CURVE_COLOUR_SPREAD` turns straight as before, and between the curve fades, so figure 8's deep blue stays a rich blue rather than going pale lavender, and a coloured letter's edge has no step. **Cost,** release, under load 5 to 6, p50 for a 512 px colour tile: one like a page, white with grey text and a fifth of it a chart's colour, main 505 µs, the curve on everything 531, the curve faded by colour with the last colour remembered 430, as most of a page is runs of its paper; a tile of noise, where nothing repeats, 497, 531 and 560. A table for the fade, where a division a pixel had doubled it. A grey tile goes by a table and costs the same throughout.

**Each image is judged by its own pixels** (owner, 2026-11-07: scans "appear bright white", and "similar with images with white bg"). `PageLook` in `paper.rs` is the whole rule, and there's one for each page, so a tile never decides for itself and a page can't come out in two halves. An image whose background is white or paper-like turns over with the page, off-white landing on `DARK_PAPER` exactly (`NEAR_WHITE_SNAP`, with gains from the image's own background), and coloured lines keep their hue. Anything else stays itself, a little dimmed, from where the renderer says it is. **A page whose images keep their colours over `MOSTLY_PICTURE` of its area isn't turned over at all:** it's dimmed by `PICTURE_PAGE_DIM`, 176 in 256. Uncertain is left alone, dimmed, on purpose: it can't produce a negative, and a bright page is the worse look only when it's a page of text, which is what the rule catches.

**What counts as white.** Paper-like: lightest channel at least `PAPER_LIGHTEST_CHANNEL` and spread at most `PAPER_MOST_SPREAD`, so yellowed, grey and shaded scans count. An image that's `SCAN_LEAST_PAPER` paper with at most `SCAN_MOST_COLOUR` real colour is a scan. Pure white, by `WHITE_LIGHTEST_CHANNEL` and `WHITE_MOST_SPREAD`, over `WHITE_LEAST` of the image with at most `WHITE_MOST_COLOUR` colour is a chart or a diagram on white. **A chart with more colour** (owner, 2026-11-07: "images with a white background should be dark, as a chart with a white background was left light"): figure 8 of part B of the EU competitiveness report is 0.77 white and 0.21 colour, its bars, just past `WHITE_MOST_COLOUR`, so it was kept and dimmed to a grey box. Its colour is flat, though, and a photo's isn't: with at most `FLAT_MOST_COLOUR` colour, `FLAT_LEAST_CLUSTERED` of it in the `FLAT_TOP_BINS` fullest of `COLOUR_BINS` (3 bits a channel), on white as above or on one plain light colour (`PLAIN_LEAST` of it within `PLAIN_NEAR` of its average, so a chart on beige counts and a map on shaded tan doesn't), it's a chart, unless its colour is one colour shaded: the fullest bins, joined where they're neighbours, running through 4 lightnesses or more (`is_shading`), as a ball or a product photographed on white does, where a flat fill's edges and noise reach a bin or two beside it. Only adds flips: nothing that flipped before stays. With no boxes known, the whole page is judged and `WHOLE_PAGE_MOST_COLOUR` is stricter, since its margins are paper whatever it holds. Under `LEAST_PIXELS_TO_JUDGE` an image stays itself.

**When it's decided.** Before the page's first tile is attached, so there's no flash and no second look. From the preview's pixels when the preview job runs, or a picture at 512 px drawn first if it doesn't. It's kept in `OpenDoc.looks`, at most `MAX_LOOKS` pages, cleared when the file changes and when the image places it's decided from are forgotten past their cap. A low-resolution page gets the same answer as a sharp one, since it's the page that was judged, and a failed answer can't leave a negative in the cache, as a job gone stale is thrown away as cancelled.

**A photo in a scan.** A small one flips with the rest, as the owner accepted, and looks like a negative. A big colour one, with over 20% of the image's pixels in real colour, keeps the page from being a scan, so the page is dimmed rather than flipped.

**What a worker can do to it:** a worker emptying a surface it holds, with `IOSurfaceSetPurgeable`, across a real process boundary, leaves the host reading zeros and writing normally, with no fault (`hostile_surface.rs`), so the turn stays in the host.

**Warm paper** is white paper with a tint over it. Each page has one extra layer of a single colour (`WARM_PAPER`, a named constant in `recto-session`, with its reason and a WCAG AA test) and the compositor's multiply filter, so going to it or from it draws no tile and keeps nothing per tile: a test holds to no draw. Black stays black. A multiply is the same sum everywhere, so a photo or map under it takes R×0.96, G×0.93, B×0.86, the same as the paper: a white in a photo goes cream, and no colour turns over. Exports and snapshots never see any paper. With none chosen, paper goes with the window, white or dark. `recto view --paper` sets it, for the app, in the state record.

**Selecting text.** Owner, 2026-11-07: "And select text should work natively". Rust decides and the host draws: the host reports points, in the document view's coordinates, the same at any zoom, and is told rectangles, in the page's. `recto_index::select` is everything about a page and a range, the same code for `recto select`, `recto copy` and the window. `recto_reader::selection` is what the page view holds. Swift has the mouse's events, the layer, the cursor and the clipboard.

**A place is a character of `recto text`.** `PageText::build` runs what `read_page` runs and keeps each character's box, as shown, so a selection's offsets are the ones `recto text` counts in, and what's copied is what an agent reads: late-drawn words back on their lines, a line-end hyphen decided. A word joined over a line end is one word with a piece on each line. A range is a stretch of that order, so a drag from one column into the next takes the rest of the first and the top of the second. There's no layout sort, for the reason `order.rs` has none: drawing order was right on all of the spike's 84 two-column pages with body text, and it's tables a sort breaks. A file that draws its right column first selects that way, as `recto text` reads it. `tests/select.rs` holds this on two-column pages made here, and `select_corpus` over real ones.

**Where a character is.** The worker's boxes are in the page's own coordinates, which aren't what's shown once a page has a crop or a rotation, so each text reply now carries the page's frame: `FPDF_GetPageBoundingBox` and `FPDFPage_GetRotation`, taken through a sum in Rust, and validated like everything else from a worker. `on_a_rotated_or_cropped_page_the_highlight_covers_the_ink` checks that against what's really drawn, for each turn with and without a crop: every dark pixel is under a rectangle, and no rectangle reaches far past the ink. Unsaved rotations don't move anything, as they aren't drawn either. A line's band goes by its baseline and the usual height of the page's lines, so a highlight is the same height whether its letters have ascenders or not. Lines that run up or down the page as shown, as on a page turned by a quarter, go by the other axis, and a place goes the way the line runs, including right to left.

**What can be selected.** Characters that show. Text that looks hidden, by the same check as `recto text`, and printed characters wholly off the page, can't be hit or highlighted and don't get copied, and a quiet notice says how many went. `recto text` keeps them, marked, because it's telling an agent what's in the file, where a clipboard has no way to mark anything. **Not left out:** a character whose font gives it no box. It can't be hit, but a whole-page copy keeps it, since an empty box doesn't make text hidden. A page with no text layer selects nothing, with no error. A page past `MAX_SELECTABLE_CHARS`, 128 Ki characters, over eleven times bench100's busiest, selects nothing and a copy says so.

Sizes are the letters' boxes, and the usual one is the lines', so a table of small figures doesn't pull it down. **A page number** can be found inside a row, as lines are cut into pieces at gaps of 1.5 sizes: one alone in its row, ending it or centred on the page, at least 0.48 of the usual line and under 1.6 of it or 10 points tall, goes when the pages either side have page numbers at its place, down and across or mirrored, that step with the pages, set apart from the body or not. That catches part B's number on the last line's row, and leaves a question's or a heading's number that starts its row, a slide's 24 pt section number and a timeline's 20 pt years. Alone in a file, one set apart and under 1000 is enough. A piece alone repeats only if it's long enough to say so, or is a date. **Whether the pick was only chrome is decided over all of it:** `CopiedText` keeps the chrome beside the copy until anything else lands, and a pick of only chrome, over a page break or not, gets it; so does a page whose every line repeats. `recto copy` and `recto select` say how many characters went, in `chrome_left_out` and the note; `recto text` marks them in `chrome_spans` (owner, 2026-11-08) and still reads everything. **What it costs:** at most 16 pieces a page, 72 B each, with its text; deciding a page took 0 to 2 µs over bench100. **Two points and a small cache.** A `Selection` holds what the pointer did, not what it covers: two ends, worked out against the text whenever that's there, so a press on a page not read yet is picked up when it is, and a whole document selected is two places however long it is. Pages between the ends need nothing read. Text is read when a selection or the pointer reaches a page: a job at a time on `recto-pages`, through the worker that's already there. An end, or a selected page showing, comes before tiles, as it's answering the reader's hand. The pointer, and a selected page's hidden-text check, come after them. The first read has no check, since the check draws the page, and no character moves when it comes, by a test: only an end that was on a hidden word goes to the nearest thing that shows. Kept: 8 pages and about 8 MiB, past what a selection is using now, which is its two ends and at most 12 visible pages, and past 16 MiB of that no more visible pages are read, so a page of tiny hostile pages costs no more. A closed window and another tab drop all of it. No tab holds any, so a cold tab's cost doesn't change, and no thread, handle or timer exists for any of this at rest. **A press never waits.** It looks through a page already here, at most 16,384 lines and then one line, or notes the page is wanted and returns.

**A copy goes a page at a time.** `start_copy` returns at once. `recto-pages` reads each page after whatever's visible has been drawn, adds it, and lets it go, through the same cache. When it's done `copy_ready` hops to the UI thread, which puts it on the clipboard, or a clipboard of a quiet run's own, `com.rectopdf.qa.<pid>`, so the real one is never touched. It stops at `MAX_COPY_BYTES`, 16 MiB, `MAX_COPY_PAGES`, 100,000, or `MAX_COPY_TIME`, 2 minutes, and says at which page. Past 0.3 s it says how far it's got. **It takes what's selected when it's asked for,** as ⌘C does on a Mac, so the drag going on with the button held, or a click, changes nothing about a copy on its way: it was reading the live selection that underflowed and killed `recto-pages`. Only a new copy, another tab, a closed window or the file changing ends one. With nothing selected it doesn't start. **Services can't wait,** so they're offered the text only if every page of it is here and a check has really looked at it, which a selection on screen of up to 8 pages usually is, and otherwise not. A copy can say a page wasn't checked, and Services have no way to. Asking costs a look at those pages, and builds nothing. A file that asks not to be copied answers Services the same way until the reader has said "Copy anyway".

**A failed check is about the check.** It draws the whole page at 2x, on the worker tiles use, so past its deadline or its memory it says nothing about drawing a tile at the zoom on screen. It leaves the page's drawing alone, is remembered as not to be tried again, and doesn't count towards the kills that stop a document: past 16 in a document, pages just go unchecked. Before this, ⌘A ⌘C on a page that draws in 3.2 s at half zoom left it saying "took too long to draw" for the session. **A check can be stopped.** A text job carries its generation to the worker, which stops the draw, and `running_is_wanted` gives one up the moment the view wants a tile or the text under a selection being made. A check stopped this way wasn't tried, and comes round again. A first read isn't given up for a scroll.

**If the thread that draws panics,** `run_guarded` goes round again: what it held goes, workers included, a selection and a copy go too, and pages are asked for again. Four within a minute of each other and it stops trying, and the page says so, so a panic can't leave pages silently undrawn. Tested by panicking on it, from `EngineEvents`.

**A file seen to change** ends a selection, and a copy says it stopped: on a page count that no longer agrees when a worker opens it, or a failed file tried again. `take_file_changed` means only that now. It used to fire when a cache of image places filled up, at 4096 pages on dark paper, which wiped a selection and a running copy with nothing wrong, and never when the file changed.

**A page known to be heavy isn't drawn for the check.** One more draw of a USGS map is hundreds of MiB, for hidden text on a map. A copy says how many pages weren't checked.

**The highlight** is one `CAShapeLayer` on a page with something selected, a sublayer of the page's layer in the page's coordinates, so it scrolls and zooms with it. It's under warm paper's tint, so the tint warms it as it does a white page. **The contents area.** `sidebar_heights` in `recto-session` shares the sidebar's height. The contents never take over `CONTENTS_MAX_SHARE`, 60% of it (owner, 2026-11-07: "The max height of toc does not seem to be working"), so a long outline with one tab leaves the rest empty. Other tabs and the footer stay, and a longer tab list scrolls by itself. **Comparison view** (owner, 2026-11-08: "Ctrl clicking more then one pdf should enable comparison view, right click menu can enable separate scroll (default) and synced scroll. Zoom is always synced."). `recto_session::compare` is every rule: which tabs, two or three (`MAX_PANES`, the live documents' own number, so three panes are three live documents and nothing more), which is read, and synced scroll's page for page from each pane's page when it went on. The session holds a `Comparison`; the active tab is the pane being read; a tab in a pane is on screen and never goes dormant; a plain tap, an open, or going to any tab that isn't a pane ends it; closing a pane's tab takes its pane. It's in the record as `comparison`, with its tabs, synced or not and the starting pages, and each pane's place is its tab's own, so restore and an update carry it, and the whole-state test in `restore.rs` has a comparison in its rich state. `recto compare` is the agent's way in, at Control to change and Read-only to ask.

**A page view per pane.** `recto-ffi::panes` keeps an `Engine` for each pane past the first, made when a comparison needs it and ended (`Engine::shut_down`) when it doesn't, which ends its thread, kills its workers and frees its tiles, so a pane that's gone costs nothing. Pane 0 is the app's own page view and keeps the warm tabs off screen; the others keep none. Each page view's caps on what's kept off screen are its share (`Reader::set_share`), so panes keep no more between them than one view does, and each has a pane's margins (`PANE_MARGIN`, 20 points), with only the pane at the right keeping the corner's 96. The host has a `PageArea` per pane, each calling the same methods with its pane's number. **Synced scroll goes on the UI thread with no session lock:** `Panes` keeps a copy of the comparison and each pane's length from the last reconcile. A pane follows only the reader's own scroll, which both the host (`by_reader`: the clip view moved while no ops were being applied) and the page view (`take_user_scrolled`: no jump arriving, no change of zoom, room or height, no pinch) have to say, so panes arriving where they were sent can't lead back. The others go by `Reader::follow`, a jump to a page and a depth in it. A page view that arrives on another page than it was sent to says so (`moved_page`), which the restore test found: a narrower pane put the next page where the eye is, and the session and the page view disagreed. **One zoom:** a zoom from a key, the menu, the field or an agent goes to the pane being read and then the same magnification to each other; a pinch or ⌘-scroll in any pane is taken once it settles. With pages of different sizes each pane is at its own fit times that, and the level shown is the pane being read's.

**A file on a dead volume.** A file that doesn't answer holds a thread as long as it likes, so neither the session thread nor a page job waits on one. `open` and `Reader` reads go to one-shot `recto-read` threads, at most `MAX_FILE_READS`, 4, with the flush markers held behind them. A worker's file is opened on a one-shot `recto-open` thread, at most `MAX_OPENINGS`, 4, looked at for `OPEN_LOOK` and given `OPEN_PATIENCE`, 3 s, then the page says so (`NOT_ANSWERING`). Past either cap a file doesn't open and says why. Tested with a FIFO, which blocks an open the way a dead volume does: no real dead volume was used.

**Reposition and rest.** Owner, 2026-11-07: "It can whoosh with smooth acceleration at both ends. It can have a \"dead-zone\" so it doesn't react to small scrolls within the window, so basically it repositions, stays still (while user is reading slowly scrolling) then repositions after the user is scrolling a bit." `ContentsFollow` in `recto-session` is the whole rule, and the host only draws where it says. Inside the dead zone, 12% to 75% of the area's height, nothing moves. Leaving it starts one move, to put the place 30% of the way down. Its shape comes from a third-order chain, a lag into a critically damped spring, so speed starts and ends at about zero with no step when the target changes on the way. It takes 0.6 to 1.1 s by distance. While a move runs it's the move's target that counts, so sections going by fast are one long move and not a row of them. The reader's own scroll stops it, right where it is, and following comes back when the pointer's out, 3 s have passed and the section next changes. With Reduce Motion it goes straight there, and only if the place has left the view. Frames come from a display link on a screen and a timer off one, started for a move and stopped when it's over, so nothing runs at rest, and passing a section costs one comparison.

**A chapter closing makes no second move.** As you leave a chapter it closes and the next opens. If its rows were above the place, the place would drop up the list by that many rows, past the dead zone, and the contents would move straight back, opposite to the move before. So Rust works out how far a change carried the place (`place_shift`, from the two lists), and the scroll takes it up in the same transaction: the place doesn't move on screen, and rows going in the view fade over in 0.15 s. Rows that change only below the place still move in view: they fade over, a layer transition over the list, and not by the table's own row animations, which on macOS 27 keep every row view they animate, with its cell, for good (an observer AppKit gives each view holds it; `comparisons_leave_no_views_behind`). With the reader in the contents themselves it's the top of the view that stays, and rows in the view fade over. **Before and after,** `rfc9110` at 6 pages a second, 10 s, by `qa sweep`: before, a move forward at each change of chapter was followed about 0.1 s later by a move back of 196 to 223 points. After, 6 moves all forward, 690 ms each, at least 0.31 s apart.

**Showing a shortened name.** One tracking area on the sidebar. After a short rest over a cut-off row, a label opens in place over it, past the sidebar's edge if it must, and goes on leaving. **What a worker can hold.** A surface costs the host, and the worker that was sent it can keep it as long as it lives, which no limit on its own memory sees. So each worker's surface bytes are counted: past `surface_bytes_cap`, 1 GiB, it's retired before its next page, and at twice that before its next job, so a one-page file can't dodge it. That's about 80 pages of text a tile at a time, for a restart of 17 ms.

**Who quits.** `recto stop` is refused by a normal app, and says only the user quits it. A quiet run stops when told.

**Which version of the contents the host has.** A chapter closing is a change to the list, sent as where it differs from the one before, with a version. The diff stays with its version until the next change. The host applies version + 1, nothing for the same version, and reloads if it's further behind, so a publish twice for one change or two changes in one pull can't leave it wrong.

**Many tabs.** The tabs' rows cross to the UI thread only when their version moves. The active tab's index comes with the model, so a table reload isn't quadratic. A tile drawn doesn't go through the sidebar at all.

**What AppKit calls.** Every other QA verb calls the method behind an event, so a method AppKit can't reach by name passes them all. Full names and hover details never fired on a real window for that reason: the tracking owner isn't a responder, and its handlers weren't Objective-C, and a plain `@objc` would have been `mouseEnteredWith:`. `recto qa entry-points` checks each owner answers the selector AppKit sends, and goes by the selector where an event can be made and handed over, with nothing posted: hover, pointer, wheel, the pinch's notifications, the sidebar button, the zoom level and its field, and Undo and Redo as the window's own chain gives them with the window key (`qa key-action`), since a quiet window isn't key and AppKit's own route would go past it. **Not covered:** a real pinch or click, whose events can't be made, so for rows and buttons it's that the target answers the action.

**Text isn't an `NSTextField`.** On macOS 27 each `-[NSTextField layout]` makes a view, whose `-[NSKeyValueDependencyInfo initWithOwner:]` leaves records in AppKit for good. It came to about 7 KiB for each tab opened and more while reading, and took 1,000 tabs of a drawn PDF to 5.7 MiB. `TextLine` draws an attributed string instead: 0.8 KiB a tab, found with `heap` and `malloc_history`.

**Colours aren't dynamic `NSColor`s:** there's one per appearance, told again when it changes.

**The QA channel.** `recto qa start` runs the app with `--qa` on a state folder set with `RECTO_STATE_DIR`, and the app refuses anything else. It has the activation policy `.prohibited` from before AppKit does anything, so no Dock icon or menu bar and it never activates. Its window is never ordered in, sits off every screen, and draws as key at 2x. No sheet or panel is ever begun on it: AppKit orders a window in to hang a sheet on it and slides one that's off screen onto the nearest screen first, which flashed a quiet run's window up in the lower left each time the print panel or a close prompt came and went (owner, 2026-11-08). Every sheet and panel goes through `SheetPresenter` (`app/Sources/RectoPDF/Sheets.swift`), which in a quiet run makes it and holds it, never shown; `qa sheet-answer` runs the completion a click would, and `qa shot` draws an alert from its own window where it would hang. The print panel, Save As and Open have no window of ours to draw, and About isn't shown. `a_quiet_run_never_puts_a_window_on_screen` samples the window server's list (`recto_platform::screen`) every 2 ms through a run's start, sheets, Settings, a print and shots, and fails on any window of the app's on it. And a quiet run answers the system's reopen, open-documents, print and get-URL events itself, by doing nothing, from before AppKit finishes launching (`QuietRunGuard`, `app/Sources/RectoPDF/QuietRun.swift`): LaunchServices hands an `open` of the same bundle, from anyone, to the running app, and AppKit's own handling turned a quiet run into a regular app with a Dock icon and menu bar, which a full check's restore test saw while another worktree's update tests were opening their copies. Its policy is watched and put back should anything else change it (`a_quiet_run_stays_quiet_when_the_system_opens_it_again`). There's a 10-minute limit, and a run ends sooner with what started it (`qa::end_with_starter`): its owner process (`--qa-owner-pid`, from `recto qa start --owner` or `RECTO_QA_OWNER_PID`, which `State::command`, the QA scripts, the corpus run and the soak set to their own; an update's relaunch passes it on), its state folder going, or its own program being deleted, as a worktree's removal or a rebuild does. One thread asleep in one `kevent` (`local::wait_until_gone`), with no wake-ups. `recto qa state` reports what the app says it's showing. `recto qa shot` draws the window's frame view with `cacheDisplay` into a 2x bitmap, which needs no permission. `recto qa wait-settled` goes through the session thread's queue first, then waits for what's visible to be on layers, then asks the host until no animation that changes what a shot shows is running (`app.animations` in `qa state`: the sidebar contents' fade and slide, their drift, a name about to show, a ⌘-scroll zoom about to go sharp), all within the one timeout. Drive verbs call what the event calls, and answer after that's been through the session thread and laid out, so no script sleeps. `recto qa run` runs a script and gives PASS or FAIL, and a 2 s stall fails it. `recto qa sweep` reports each contents move, with its length and peak, and the rests between. `qa` rows are Read-only or Control, and a session that isn't a quiet app answers `qa_needs_app`. They're in `recto help`, and left out of the skill. **Not covered:** the step from a real event to the method it calls has no unit test, only the method. Run-loop blocks from Rust are in their own autorelease pool, as AppKit only drains its pool after an event.

**The watchdog.** The UI thread says when it wakes and sleeps, from a run-loop observer. One thread watches only while it's awake, looking every 250 ms, and notes 1 s and counts 2 s. `recto qa stall` proves it fires.

## Saving

SPEC section 6 and decisions 16, 25 and 27. `recto_core::save` is the one place that changes a PDF's bytes, `recto_agent::saving` is the one way anything saves (`recto save`, `recto save-as`, ⌘S, the Save icon, Save As's sheet and the close prompt's Save all run the same command), and `Session::begin_save`, `save_prepared`, `saved` and `end_save` are the session's side.

**Two writers, never a third.** Adding things appends with the fork's `append_atomically`, so every byte that was in the file stays, a signature's included. Removing things rewrites with `rewrite_atomically`, so what's removed is gone. `clippy.toml` refuses by name every lopdf call that writes to any `Write`: `Writer::write_object`, the eager `Document` and `IncrementalDocument` saves, `copy_revision_to`, and `RewriteChanges::remove_object`, as nothing reports a kept page still using a removed object. Test fixtures that build encrypted files with lopdf's eager writer say why they're allowed.

| Edit | Writer | Why |
|---|---|---|
| Turn | Append: a new version of the page with its `/Rotate` | An addition |
| Move | Append: a new page tree, each page given what it inherited | An addition; the old tree is in the earlier revision and holds nothing that isn't in the new one |
| Pages from another PDF | Append: the pages and what they draw with, copied under new numbers, streams as their raw bytes 64 KiB at a time | An addition. Another page of that PDF, its page tree and its catalog aren't followed, so a link can't bring the rest along; an annotation's `/P` and `/StructParent`, and the page's `/PieceInfo`, stay behind; its layers join the file's `/OCProperties`, the hidden ones hidden. **Its form fields come along:** a widget keeps its field and the field's parents, a field's `/Kids` keep only what's on added pages, top fields join the document's `/AcroForm /Fields`, renamed `name_2` when the name's taken, and the source form's `/DR` fonts join; signature fields don't, as a signature from another document would only be a broken one here |
| Delete | Rewrite: `remove_page` for each, the file's own tree kept when the rest are in order, otherwise a new tree; with moves, turns and added pages in the same save, one rewrite | Appending a tree without the page would leave its objects readable in the file. The fork drops every reference to the page and corrects the tree, outline, names, form and structure |

**One plan, either writer.** `Plan::write` puts objects through a `Sink`: `AppendSink` writes them into the update as it goes; `RewriteSink` gives them to the rewrite's changes, which hold them until the file is written, counted against `MAX_REWRITE_HELD_BYTES` (256 MiB), and a copied stream goes as a `LazyStream` that opens at its first read, so a million copies hold no reader each. A rewrite's answer has `pages_removed`, `objects_missing` (a warning, as MuPDF and poppler can repair what the copy drops), `signatures_removed`, `resources_left_whole`, and `document_data_kept`, said in words after a delete: attached files, XMP, the document's information and the like can repeat a deleted page. `rewrite_in_memory` is the same plan on bytes, which `save_copy` fuzzes.

**Every claim is checked against the files.** A journal can be forged, so before a byte is written the file's own page count must be the list's, every page asked for must be in its file, each added PDF must have the stamp and length it had when added (none recorded is refused), and the reader saves from has a limit of 1 MiB an object. Before the file is moved into place it's read back: its pages are the objects written, in order.

**The steps.** `begin_save` copies the list out and holds the tab: no edit, undo, redo, discard or close until `end_save`, and it can't go dormant. The file is written beside its target and synced. In the fork's `prepare_replacement`, the file's attributes and ACL are carried over (a Save As carries only quarantine and where it was downloaded from), its pages are read back, its stamp is taken, which the rename keeps, and `save_prepared` notes it; the app writes that to the journal and reads it back from the disk (`RecordStore::journal_says_saving`) before going on. Then the fork's own check of every byte, the rename, `saved`, and the record is asked to follow at once. A failure at any step leaves the file as it was, and `end_save` forgets what `save_prepared` noted. A kill at each step leaves the original or the whole new file (`a_kill_at_every_step_leaves_the_original_or_the_new_file`, by a debug-only pause).

**Refused whole:** a file changed since it was opened, before writing or in the moment before the rename; other hard links, as those names would keep the old version, and for a rewrite what was removed; a read-only file or folder; a new file's name taken; a protected file or added PDF. Each says nothing was written, and where a copy helps, the app's sheet offers Save As.

**The agreement gate** (SPEC section 3). `recto_core::agreement` has the rule and the words, and reads lopdf's half; `recto_agent::agreement` asks a worker of its own for PDFium's half, through the very file descriptor the structure is read from (`DocRenderer::read_structure`), so both read the same bytes. Compared: page count (PDFium takes the root's `/Count` and keeps a slot for a kid that doesn't load, where lopdf leaves it out), each page's shown size in order, which stands for which page is where (a `/Type /Page` with `/Kids` is a page to lopdf and a branch to PDFium; a page object each reads from another place shows another size), and whether either rebuilt the cross-reference data (`FPDF_DocumentHasValidCrossReferenceTable`, carried in the worker's `Opened` reply, against `index_stats().recovered()`). PDFium checks that the first object its table lists is where it says and rebuilds if not; lopdf, reading lazily, never looks there. Counts are compared first, and sizes only when they match: every page up to `MAX_COMPARED_PAGES` (10,000) and that many spread evenly past it; a page one of them can size and the other can't is a difference, and only a page neither can size isn't compared. A file only one of them needs a password for (`/Encrypt` named only by an older trailer: lopdf reads the newest, PDFium honours it) is `Encryption`, and one the renderer can't read at all is `RendererFailed`. **What it couldn't check is `Unchecked`, never agreement:** the descriptor opened isn't the version asked about (`open_file_stamp`), the structure read failed, a worker couldn't start, or the look passed `LOOK_DEADLINE` (30 s); it refuses the save that asked, but doesn't grey Save, Save As or the close prompt's Save (`ffi::saving::greys_save`, the coordinator's decision in review round 2): each click's own look is the retry. lopdf failing to read the very descriptor PDFium opened is `StructureUnreadable`, the file's answer. A renderer-only tab skips the gate, so `begin_save` refuses it as such with no worker started, and a file whose stat fails is `Unchecked` rather than skipped. Every answer, `Unchecked` too, is kept for the version asked, 16 of them, so the window, told a look is done, finds it and starts nothing; a save looks again at an `Unchecked` one. At most 2 window looks run at once, and a save's own look counts toward that while it runs; a save waits for a window look already under way for the same version rather than start a second. `refusal_for` is asked before `begin_save`, so edits aren't held for a look, and `save_refusal` again once the tab's held, answered from what was kept unless pages from another PDF were added meanwhile; a file whose stamp isn't the session's isn't looked at, as the save refuses it itself (`parsers_disagree`). `known_or_start` is what the window asks once there are edits, on a 1 MiB thread like a file read's, through `SaveUi::save_state`, which decides Save off, Save As's note and the tooltip; File > Save As is off too. A look costs a worker's start and a round trip a page: a made 2,000-page file took 206 ms in a debug build under the build queue's load. The window turns Save off with the reason as the icon's tooltip, the close prompt offers Cancel and Don't Save, and `qa save-from` is refused alike. Tests: `recto-core`'s `agreement::tests`, `recto-agent`'s `agreement::tests` (once per version, a changed or missing file kept and not looked at again, `Unchecked` retried by a save, a save joining a look, the deadline) and `tests/agreement.rs` (a kid that doesn't load, a tree walked differently, a broken index PDFium repairs, a password only PDFium needs, a file only lopdf reads, a structure read that fails), `a_file_the_two_readers_see_differently_isnt_saved`, and in the app `a_file_the_two_readers_see_differently_turns_save_off_in_the_window`. Annotation counts and signature ranges, in the research's list, aren't compared: PDFium needs each page loaded for them.

**Signatures** (decision 27). An approval signature is untouched by an append, byte for byte. `SignatureFacts` says whether a signature field has a value (`/FT` inherited), whether the file is certified (`/Perms /DocMDP`) or a signed field locks it, and whether it has usage rights. **Save is off when a Save over the file would break a person's signature:** a rewrite on a signed file, or any change on a certified or locked one (`save_needs_copy`, from facts read once a version on a `recto-signatures` thread of their own: one look per file, at most 4 at once, and a look that panics ends, counting as having found nothing). The Save icon is there and greyed, its tooltip says why, ⌘S is greyed, the Close prompt offers Save As in place of Save, and Save As's sheet says "The new copy won't be signed. The original keeps its signature." Save off and the rewrite's refusal agree, as both ask `signature_facts_of`, which includes the fork's own look through the file's bytes (`persons_signature`); that reads the whole file, so the app reads it on a thread of its own, once a version, and a sleeping tab's summary says whether its edits rewrite. Save As onto a signed file's own name says to choose another name, and its alert offers Save As. `SignatureFacts` counts a field whose `/V` is a dictionary with a `/ByteRange` as signed, whatever its `/FT`. A page added from a signed document leaves its signed signature widget and value behind; a blank signature field, a place to sign, comes along and joins the form, as the fork keeps blank ones through a rewrite. Added fields' names are compared with the document's decoded (PDFDocEncoding, UTF-16), as a reader compares them. Any save that rewrites needs Full, asked through `SaveHooks::may_rewrite` once the writer's decided. A Save As copy of such a file is a rewrite with `RewritePolicy::remove_signatures()`: every field, value, drawn box, `/Perms`, `/SigFlags` and `/DSS` go, and the answer says how many. The fork refuses to rewrite a signed file over itself whatever it's told. Usage rights alone (`/Perms /UR3`) go from an append's new catalog, or a rewrite's with `remove_usage_rights()` in place, with a quiet note, as any page edit ends them (owner, 2026-11-08). Nothing says a signature is valid.

**One backup of the original**, on the first save over a file: an APFS clone where it can be, synced, in `<state>/backups.noindex/`, named by a hash of the file's real path, out of Time Machine and Spotlight, 30 days within 1 GiB, oldest out, looked at as a session starts. A Save As makes none.

**Levels** (the coordinator's default, 2026-11-08). Control saves what's appended, since nothing is lost: every byte stays in the file, the history keeps the saved point, and the first save keeps the original. Control may Save As to a new file. Replacing another file, and a save that rewrites, need Full.

**A delete costs**, release build, under the build queue's load with three other workers, 3 runs each, whole process by `phys_footprint` (`examples/save_delete.rs`): the 346 MiB map with a small page added and then deleted, 1.12 to 1.32 s, a peak of 4.5 to 4.7 MiB from 3.7, and 327.8 MiB written, the new file; a made 1,000-page file with page 500 deleted, 60 to 62 ms, 4.0 to 4.1 MiB, 0.3 MiB written. The map is damaged, and its rewrite reports 240 objects missing; MuPDF draws it and its rewrite identically at 8 and 36 dpi.

**An append costs**, release build, this Mac, under the build queue's load, 3 runs each, whole process by `phys_footprint`: the 346 MiB USGS map with page 1 turned and another file's page added, 375 to 407 ms and a peak of 6.8 to 7.2 MiB for two saves in one process; a made 1,000-page file with every page moved and one turned, 39 to 52 ms and 4.0 to 4.2 MiB. There was no Save before, so there's no before. **A save writes only its update** since the fork's `598e61f`: the temporary file starts as an APFS clone of the original, and a turn on the 346 MiB map wrote 8,192 bytes by the process's own disk-write counter, where it wrote 346,415,104 (the whole file) before, and took 216–221 ms against 372–401 (3 runs each, release, under load). A volume that can't clone gets a copy, as before.

**The corpus**, bench100 copies, by `cargo run --release -p recto-core --example save_corpus`: every PDF saved with page 1 turned, the last page moved to the front and the next file's first page added. 139 saved, 2 refused as protected; each read back with the original bytes as a prefix and one page more. qpdf `--check` found no errors, and warnings only where the originals had them, plus 9 IRS forms whose added form pages' widgets aren't reachable from `/AcroForm` (`docs/PLAN.md`). MuPDF and poppler gave every saved file the right page count, and PDFium drew the first and last page of each.

## The state record

Owner, 2026-11-07: "It's crucial that app state is perfectly recovered before and after update", and "it should recover state so perfectly that it can update while the user is using it." SPEC decisions 23 to 25. `recto-session::record` is the format and every rule about reading one, `recto-control::record_store` is where it lives, and `recto-ffi::saver` is what puts it there.

**What's where,** in `<state>/session/`, every file 0600 and each folder 0700:

| File | Holds | Written |
|---|---|---|
| `record.a.json`, `record.b.json` | Everything else: tabs, order, each tab's file and place, window, sidebar, panel, appearance, paper, Find, edit mode | When something other than a place changed, over the older of the two |
| `places.log` | One line for each move of a place, active tab, contents scroll or focus, for the record of its sequence | At most once a minute, only if it changed, and at once on quit, background or hand-off. Folded into a new record past 256 KiB |
| `journals/journal-<key>.log` | One open PDF's unsaved edits and rolling undo and redo, with who made each step | Appended after 2 s of quiet, or 5 s at most during a burst |
| `journals/closed-<key>.log` | The same, for a PDF closed with history and nothing unsaved | Renamed on closing. Never read at launch, kept 30 days within 1 GiB, oldest out first, and out of backups (owner, 2026-11-07) |

A record's first line is a header: kind, version, sequence, length, CRC-32 over the sequence and body. It's read first, so a newer one is recognised with nothing else looked at. Its body is JSON, read with serde, so `#[serde(default)]` lets a field be added with no new version and an older app ignore it. **Every list is capped as it's read,** at the cap, not after; every number is looked at (`validate_record`, `validate_edits`, which holds a page to what its file has); and a run of pages is counted before it's expanded, as 20 bytes can claim billions. A hostile file gets as far as a refusal. `tests/fixtures` has one record and one journal as they're written today, and `tests/format_v1.rs` reads them, so a change can't quietly break them.

**A crash leaves the old record or the new one, never a broken one.** Two slots, the older overwritten, and the newer that reads whole is what's taken. Nothing depends on the order a drive puts things down in, so an ordinary write is only a plain `fsync`, handing it to the drive. `F_FULLFSYNC`, which makes the drive flush and costs both time and wear, is for a hand-off alone: `force_to_drive` covers the newest slot, the log of places, every journal and their folders, written by this flush or earlier. A kill loses nothing written. A power cut loses at worst the slot being written, or a journal's tail.

**A journal is only appended to.** Each line is a CRC and one operation, about 27 bytes: rotate, move, delete, insert, add a source, undo, redo. Only what was asked, forwards, since replaying through the same checked calls (`PageEdits::replay`) rebuilds the page order and the history with whose each is, and a hostile journal can do no more than an agent could. There's a budget on how much a replay moves, and on how many lines are read. A torn tail ends the reading at the last whole line, and is cut before the next append. Anything past that, more than one torn line, or an operation that won't apply, is copied to `.kept`, what could be used is written as a clean checkpoint, and the tab says `edits_unreadable`, so nothing added later is lost behind a line replay can't pass. Past 1 MiB, a journal's checkpoint moves up, as one line for the list as it stands, if that comes out under half the size. Otherwise nothing rewrites it. **Named per PDF** from its inode, size and modification time, not its path: a moved file keeps its history, and an edited one doesn't get what doesn't apply. Not the device, which comes back different after a remount. What's in it never reaches the writer: it's only ever read by `replay`.

**A journal has one owner.** Its header says whose it is and what file it's about, and at each launch every `journal-` file is matched: a tab that names it, if it's about that tab's file (`journal_named_is_for`: the same size and time); otherwise a tab on the very same file with none, by path or inode as well as size and time, as `cp -p` keeps those (`journal_is_for`), since a first edit's journal goes out seconds before the record next does; otherwise, with real unsaved edits, it's what a crash leaves, and comes back as a tab; otherwise it goes to `closed-`. A tab never applies a journal about another file. A closed tab stays closed. One failing doesn't send the others again: `journal_work` copies, and only what `JournalOutcome` says got there is let go of. **What's there and isn't known is never truncated or overwritten:** a newer app's journal is left as it is, and writes go under another name beside it. Closing a tab takes what hadn't gone out with it.

**A PDF can only be opened once** (SPEC decision 26). `Session::tab_for_file` is the one rule, by path or by device and inode, so a link or a hard link goes to its tab and a copy is another file. A number alone isn't the file: its contents must be what the tab knows, or the tab's own path must lead to that number now, since another volume can have the same one. Otherwise it's another PDF, and a tab's edits don't follow it. A file moved and opened by its new name takes the tab with it. `open_with_facts` is the one way a tab comes to exist, and has to be told what history there is, which every route gets from a `HistorySource`, so the menu, a drop, a launch argument, `recto open` and an agent can't differ. `recto open` answers `already_open`. A PDF added as pages isn't a tab. A record with two tabs on a file comes back as one (`one_tab_per_file`): the one with edits, and if both have them it says it can't merge them and keeps the other's journal to one side. So `budget tabs` and `qa budget` use `clone_file`, APFS clones of a file, which are other files for no disk space, and fail if they didn't get the tabs they asked for.

**History rolls.** Owner: "a rolling save redo history on the system". 1,000 steps or 64 MiB, whichever comes first (`MAX_UNDO`, `MAX_HISTORY_BYTES`), oldest out. Past that, edits go on: a step dropped is only the way back, and what it did stays in the page order, which replays exactly, as the replay applies the same caps. **Below Full, an agent can't push the owner's steps out,** by an edit, an undo or a redo, as an undo of an insert holds that insert's pages. Steps can only go from the oldest end, as each one's way back depends on those after it, so an agent's own oldest go first by being oldest, and the owner's at the bottom stops the edit with `history_full`. That closes the plan's gap. **Not in `/tmp` or Caches,** as it's the only copy of unsaved work. Edits are never refused for history's size, and past 1 MiB compaction holds a journal to its checkpoint and what's come since, so SPEC decision 25's rolling history leaves no disk cap to reach in practice: 256 MiB is what one journal may be read at, as a limit on hostile files.

**A save marks a point, and what a crash at each step does.** Owner: "after a save you might still have regrets and want to make changes. But you definitely don't want history to leak into the pdf file". `Session::saved` replaces what was `save_confirmed`. What was written is the file now, so page `n` of the document is page `n` of the file, and the list starts again from there with every page in its own place. `is_edited` is whether the document differs from the file, so undoing away from that point reads as unsaved and coming back reads as saved, by any steps, with no mark to go stale.

**Steps stay meaningful, which is the hard part.** A turn, a move and a removal go by position, and the document's positions are what they were. The only steps that name pages are those that put pages back, and those aren't in the new file, or the document would have them. An added PDF is still its own file. The tab's own pages go over to a **kept file** in the journals' folder, holding **only the pages the history can put back** (owner, 2026-11-07): `own_pages_needed` lists them, `RecordStore::keep_pages_of` has `recto_core::save::keep_pages` write them by the rewrite, from the file before the save replaces it, synced with its folder, private, its age its own, and named `.keptpages` so Spotlight has no importer for it. `AddedSource::holds` says which old pages it holds, and the rebase moves each step's page onto the copy's numbers. Up to 64 MiB a PDF, the limit a history has, oldest out, so a PDF of any size can undo a delete past a save. A headless session keeps none. **Where there's none, the step rolls off,** with all older ones, as a step's way back depends on those after it: undo stops short rather than undoing wrongly, and the tab says `history_rolled_off`. A kept file's only ever an added source to the reader, drawn by the same worker, and it's checked at a restore and when a closed PDF's opened again. Written once, by whoever saves.

**The steps of a save.** The journal goes by the file's identity, which a save changes, so it starts again under the new name with the whole list, in one step, and the old one goes only once that's there (`JournalAppend::base`, `replaces`).

| A crash | What the next launch finds | What comes of it |
|---|---|---|
| Before `save_prepared` | The journal as it was | The edits stand |
| After it, the file not in place | `Saving` and `Keeping` in the journal, and the file isn't that | The edits stand. The copy kept ages out |
| The file in place, not confirmed | The file is what `Saving` said | `carried_over`: what `saved` would do, the history goes on under the new name, the old one goes |
| Confirmed, both journals there, the record behind | As above | The same, over the new one |
| Confirmed, the old one gone, the record behind | A tab naming what's gone, and a journal about the file now at its path | That tab takes it |
| A journal that says a save happened and didn't | A list of another length than the file, at the file's own stamp | `activate` throws it out when the file's read, and says `edits_unreadable` |

`clear_history(reason)` removes files, not only references: a confirmed redaction or hidden-data removal, a file changed outside with nothing unsaved, on a tab that's open (seen at a restore or on a wake). A file changed while its tab was closed has another identity, so nothing leads to its old `closed-` journal or kept file, which go at 30 days, a discard, and Clear Edit History. With unsaved edits the page order stays, and the journal's replaced in one step by one with nothing that was only history, so an added PDF undone away from goes from it too. A file changed under unsaved edits keeps them and says so, decision 23. **A redaction keeps nothing:** `save_prepared` isn't given a copy, so what it removes isn't held even for the moment before it's cleared. `never_in_pdf.rs` searches a saved file for marks that were only ever in the history, on the real save path, and checks the kept copy holds the removed page alone. The journals' folder is out of backups however it came to be there. Closed histories and kept files go at 30 days or past 1 GiB in all, oldest first, at a launch and when a tab closes with history: no timer. Only a launch knows which kept files are in use.

**Deep sleep** (SPEC decision 25). Owner: "When it's on deep sleep, we want its state to be stored on disk, not on memory. But it needs to be stored in a way that's quick to recover without any delay." A tab goes dormant once it's been left alone for 5 minutes, and sooner if what's off screen is over its 256 MiB, or the system says memory's short (a dispatch source in the host, and `AppCore::memory_pressure`). **There's no timer per tab:** `Session::next_dormant_at` is the soonest of the few tabs that hold anything, kept in an atomic and waited on with the state's own deadline in the session thread's one wait, so a session of cold tabs has no deadline at all. A tab being worked on doesn't go, whatever's asking: `execute` holds the tab a command's about, and a save under way holds it by `saving`.

Going dormant: what's waiting goes in the journal, the sleep file's written if it says anything new, and the journal's compacted, read back and compared. Only then does the list leave memory for a summary (`Session::asleep`), which is what a look at a tab needs: its length, whether it's edited, whether the owner's in it. **Anything about a tab wakes its list first,** through `wake_list`, so nothing can act on a list it can't see: `activate`, every edit and undo, `saved`, `clear_history`, `close`, and `execute` for every command with a tab. If its journal can't be read just now, it stays asleep under its name, the tab says so, an edit's refused with `edits_unreadable`, and whatever's next tries again. Only a discard or a confirmed save gives up on it. That's a read under the session's lock: 0.2 to 0.5 ms for journals of 33 to 65 KB and 500 to 1,000 steps, release. The UI thread's only use of that lock is `ready_to_show`, which doesn't wait for it, so a long one holds up commands and not the window. Restoring puts every list but the active tab's to sleep at once, as it's read them from disk anyway. A hand-off reads back those too, against their summaries.

**A sleep file is what a first frame needs without opening the PDF:** `sleep.rs`. A picture of each page at the place, the sizes of pages known, and the contents, in `journals/sleep-<key>.bin`, private and out of backups, by the identity of the file, up to 256 MiB in all and 30 days. A picture's its preview, or put together from whatever tiles there are, so a heavy page, which has none, has one too. **The pictures are taken as the tab leaves the screen,** and held while it's warm (`DocView::left_pictures`, at most 4 MiB a tab; a letter page at a Retina window's fit is 730 KiB), because what it left on screen is marked discardable, and the system takes that back whenever it needs pages, with no word to the app. Before, a tab put to sleep after that had no picture and woke to bare paper: a full check's sleep file had none, and 3 GB memory spikes beside the run reproduced it in 2 rounds of 8, with the preview counted in `discards_lost`. They go when the tab's shown again, its file's another version, memory's critically short, or the window closes. `qa memory-pressure discard` does what the system does, for tests. No flush: losing one costs only the quick way. **Nothing's written if nothing's changed,** as the bytes are compared first, so a quit with nothing new writes none. It's made as a tab goes dormant, is pushed out of the warm ones, or at a flush for the tab on screen, and only the last of those is on the session's own time: the rest pack on a one-shot thread, as packing a photograph takes long enough to hold up what's asked for next.

**Held down for the drive's sake** (owner: "reduce SSD wear as much as we can"). A picture's at most 100 KiB. A page that's mostly paper packs well under that as it is, and a page that doesn't goes at half the resolution or less, with fewer colours and each row as differences, till it fits. A tab that's only moving about gets a new file at most once a minute, and 1 MiB an hour in all, so about 8 MiB in a heavy day's eight hours. A quit, a hand-off and being asked don't wait for that. Past those, a tab with a file keeps it, whose facts are as good as they were, and a tab with none gets its facts alone. **A picture's never shown for the wrong place,** as each is of one page of one list of one version of a file: if the place has moved on since, the first frame's the page on its paper, at the right place, with the contents there, until it's drawn. **It's hostile, and can always be thrown away:** a checksum, every number held to what's possible before it sizes anything, pictures inflated to exactly what they say, titles cleaned again, and fuzzed. One that doesn't read is removed, and the tab reads its PDF. It's never used if it's not about the list as it is now: `order_mark` is what's on the document's pages, not a count of edits, as a discard and a new edit would start that again. **What it says of a file's length goes only until the worker has the file open:** if that says otherwise, the file goes and the PDF's read, and nothing that hasn't been checked is written on into the next one. **A protected PDF never has one,** and a document with a page from one has no pictures. Nor does one survive what it's a picture of: a close, a file changed, a save, or a redaction. **Another version of a file is a change of what's on its pages:** `PageMap::own` says which it is, so everything drawn of the old one goes, a worker that has it open goes with it, and the page view won't offer a picture for a version it isn't a view of. **An added PDF is drawn only while it's what it was when its pages were added:** `PageMap::expected` holds each one's stamp, and the engine looks before each job; a changed one's page says why and draws nothing.

**Waking.** `Session::wake_for_tap` tries the sleep file first, which is every route. With nothing asked of the PDF, which may be on a disk that's gone away, the session has the contents, the page view's given the pictures as those pages' previews, and sharp tiles replace them as usual. One thread looks at the file on the way past, and if it isn't what it was, the file's read after all. A launch does the same, so the window goes up with the pictures on (`is_showable`) rather than waiting for sharp tiles.

**Every picture and tile is of a version of its file, checked as it goes on a layer.** A worker says which version it opened: the file's length, page count and both halves of its ID, the second of which a writer changes on every save (`version_of`, from what opening it reads anyway). Each thing drawn keeps that, and `attach` won't put anything of another version on a layer, so however a file came to be replaced, and whatever was on its way, an old picture can't be what's showing. When a worker says another version, everything of the old one goes, and a sleep file's pictures with it. A file whose stamp has changed is opened again before the next job, as a worker reads through what it was given (`reopen_if_replaced`). And a tab about to be shown has its file looked at first, for as long as a frame can wait, 30 ms: that's what a warm tab's held pages and a sleep file's pictures were shown without, which is how the review's red frames came about, reproduced here as a warm tab whose file was replaced showing the old pages until something drew. **What isn't covered:** a file rewritten in place with its size, time and number put back, and no new ID, under a tab whose pages are all held; and a disk that doesn't answer the look in time, where what's held is shown as it was.

**What a page view's `last_wake` says.** From being asked to the host having applied a frame with something on every page in view, and to sharp. That's as far as a test off screen can see: whether a real display's next frame has it isn't measured, and needs a real display. A page under 5% of the view isn't counted as bare. See `docs/PLAN.md`.

**Identity.** A file is size, time, device and inode, kept with a tab. `classify_file` is pure, with every case tested. Same size and time at its path is the same file. Otherwise a file of its inode elsewhere with the same size and time is it, moved, found with `fsgetpath`, so nothing's searched. That comes first even if something new took the old name: page numbers in edits are about the original. Otherwise it's changed if something's at the path, or can't be found. Those are said in Rust's words on the tab, in the sidebar and in `session show`, and edits stay. One thread looks at every file once after a restore and then ends, so a dead volume holds it and nothing else.

**One writer, and what's not read isn't touched.** A lock held for the process's life, which a kill lets go of. A launch waits 600 ms for it, as the app it's taking over from may be on its way out. A second app on one folder neither reads nor writes the record, and says so. A session with no window has a folder of its own, and only writes when told, so `recto session save` from one can't overwrite the app's. A newer app's record is never touched: this app works beside it, in `session.v<N>/`, which is also what going forward copies the old folder to, so going back finds it, and what's done there is brought forward when the newer app next starts, by a `went-back` marker. An older record is carried forward through its own decoder. The newer slot not reading, with the older one good, says so (`record_older`). A record that's been read and is wrong goes to `session.damaged/`, three at most, leaving the journals, and what they hold comes back. A record that can't be read just now isn't damage: it's left as it is, nothing's written over it, and it says so.

**Notices are codes.** A record keeps `record_damaged` and the like, and `notices::words` has the words, so nothing in a record reaches the reader or an agent as text, and a code this build doesn't know says nothing. It goes on the reader's first input, and it's carried until then, so one showing when an update lands is still showing after.

**At rest there's nothing.** No thread, no timer and no wake-up. Saying something changed is an atomic store and, the first time, a nudge to the session thread, which is parked anyway, and now keeps the one deadline there is by parking with a timeout. When it comes due a one-shot thread does the writing and ends. So a scroll on the UI thread waits for nothing, and a window left reading has no extra thread for its minute. Nothing is per idle tab but the `place_dirty` byte.

**The first frame.** The window is made and laid out, and held back. The session thread applies the record, looks at the active tab's file (it may have moved), reads its facts and sends the page view to the place; layers are filled behind the hidden window; and it's ordered in once `is_on_place` says the view has arrived and everything visible is on its layers, or 1.2 s has passed. `qa state`'s `record.first_shown` says what was on it. The place's page size is in the record, so no Size job holds up the first frame. Exact `y` is used while the document's height is what it was, and the page and fraction otherwise, as with a document of mixed page sizes, where sizes learned earlier aren't kept. **A cold tab's zoom and offset now live in the session,** which fixes a tab losing them on going cold. **A state read late** (past the second the window waits for it, on a slow disk or a loaded machine) used to leave the window as it went up without it: the default size, no full screen, every pane at the top, the contents with no height on CI. Now the host makes the window again from the state once it's in (`AppDelegate.restoredLate`, `AppCore::window_replaced`), as an on-time read would have made it, and the appearance and Settings with it; what the host chose already about a closed window, the Dock and hiding stays (`updates::out_of_sight_when_restored`). What the first window says about itself after the state comes in isn't kept: the one made again goes by what the state said (`AppState::from_state`), as just past the patience the first one wrote its default size over it. A new window's contents go back to their scroll, following or not. `qa wait-settled` waits first for what's shown to have been made from the state (`shown_with_state`). `everything_comes_back_when_the_state_is_read_late` reads it 1.05 s and 1.5 s late on purpose.

**Quitting.** Rust's rule: a quit asks nothing, as Resume does in a Mac app, because unsaved edits come back (owner, 2026-11-07). Closing a tab with them is where Don't Save, Cancel or Save belongs (SPEC §4). It asks only if they couldn't be written. While it writes, what a person does and agents' commands aren't taken. A hand-off never asks: `hand_off_check` says what would stop it, and `hand_off` refuses until there's nothing: a sheet or panel open, an agent's command, a file being read. A running save joins that list when there is one. It looks again after it's stopped taking things, as a command is counted before it looks at the flag, so none can slip past. What's waiting, the record and the lists are taken in one look at the session, so an edit can't be in one and not the other. `seconds_since_input` is one number, stored by an event monitor, for the 30-minute rule. A scroll in the moments between the read-back and exit isn't carried: that's the one thing a person can still do, and it's milliseconds.

**For the updater:** `AppCore::hand_off_check()`, then `AppCore::hand_off(limit_ms)` from its own thread, then `AppCore::hand_off_quit_now()` on `Ok`, which does nothing unless a good hand-off happened, or `hand_off_cancelled()` if something else stops it. **It must wait for the old process to have ended before starting the new one:** a launch only waits 600 ms for the record's lock, and past that it starts empty beside the record with "another instance". Launch the new version with `open -g` if the app wasn't frontmost: a restored app activates itself only if it was.

**Not carried, by rule:** a password; which warm tabs were warm, as they come back cold; a window closed with the red button comes back open, as launching one does, except across an update, where it stays closed rather than appear behind whatever the user's doing; agent levels, which only the level's file holds. **Held but not drawn yet,** with `qa` verbs and in the comparison: Find's open state, query and draft, edit mode, view rotation. What's selected comes back on the active tab, as a tab off screen holds none.

## Updates

SPEC decision 24, with Seedwell's GitHub-release back end as the model. `recto-update` holds every rule and word. `recto-ffi::updates` joins it to the app. The host sets one timer and draws a menu item and a small window. **What it costs at rest:** a small struct in memory, one `DispatchSourceTimer` armed for a day away, no thread and no handle. A check or an install gets a thread for as long as it runs, and it's gone after.

**What's on offer** (`rules`). `latest.json` is hostile: capped at 64 KiB, parsed by one function, and only a plain `MAJOR.MINOR.PATCH`, its own tag, its own zip name, a well-formed SHA-256 and a met minimum macOS come out of it. Nothing else from that file is kept or shown. Numbers go in the menu, and only numbers.

**When** (`rules`, `updater`). `next_wake` names one time: a day after the last check, an hour doubling to a day after failures, never within a minute of launch or the last try. It changes only when something happens, and the host re-arms only when it changes, so nothing's done per input. The timer's by the wall clock, so a sleeping Mac looks when it wakes. An automatic install looks when the 30 minutes could be up, reads `seconds_since_input` then, and if it isn't time, sets the next look for when it could be: at most one wake-up per half hour while one's waiting, and none otherwise.

**Fetching** (`fetch`). `/usr/bin/curl` with `-q`, no environment, `--proto =https`, `--proto-redir =https` and a time limit, supervised from outside too, reading into a capped buffer that stops it. The memory it costs is another process's, and only for as long as it runs. Nothing a server says reaches a message or the log.

**Everything slow first** (`stage`, `zip`). All while the app's in use, on a thread: download, SHA-256 as it's written, then unpacking into a private hidden folder beside the app, so the swap's on one volume, and then the bundle id, the version the app itself says, `codesign --verify --deep --strict`, the Developer ID requirement and Gatekeeper. **The unpacking is our own reader.** A zip says everything twice, and `unzip` lists one copy while `ditto` unpacks the other, so a check with the one said nothing about the other: a review got names past it that weren't listed, and a zip saying 1 KiB unpacked 50 MiB. `zip.rs` holds the headers to the list, leaves no room between entries for anything unlisted, takes only plain-character names inside the app, makes only files and folders with modes of its own, and counts what comes out as it comes. Fuzzed as `update`. Before anything's downloaded `check_place` asks of the real bundle and its real folder whether they can be replaced: write access for this user, and not locked. Only a bad release is held against the version. A 404, a full disk or a tool that takes too long backs off and tries again.

**The hand-off** (`updater`). Waits for what's in flight, telling the user if they asked for this, then `hand_off`, then the plan, then the installer, then `hand_off_quit_now`. Past a good hand-off every way out calls `hand_off_cancelled`, or the app would stay frozen. An automatic install looks once more at the time since input, after the freeze, in case the user came back. The plan going away is how the app takes it back. A user quitting meanwhile stands the install down, as a quit shouldn't turn into a reopening. A second copy of the app on the same state neither downloads nor tidies: its hand-off would be refused, and what's staged is the first copy's.

**The installer** (`install`, `recto-updater`). Takes an exclusive lock for its whole life, and each plan has a name: two at once did destroy the record in a review, in 3 runs of 4, so one whose plan's been replaced stands down at once, and one that's waiting finds there's nothing left to do. Waits for that one process, without touching it. Refuses if someone's reopened the app in that moment. **Then looks at what it's about to swap in:** sound, and with the signature's hash that was verified, which covers the program, its Info.plist with the version and bundle id, and the seal over every other file, as a by-hand install can wait ten minutes after verifying. Clones the record aside (APFS: no copy of the bytes; a real copy up to 256 MiB elsewhere), `renamex_np(RENAME_SWAP)`, moves the old app to `previous/`, opens the new one with `open` or `open -g`, and waits for `launch-ok`. If the new app ends, runs out of time or says `launch-failed`, it's stopped, the record's copy is put back, the old app's swapped back from wherever it is and opened, and `outcome.json` says so at that launch. With no old app to be found it says that, and leaves what's there. A kill after any step leaves a whole app at the app's path, and `Updater::launched` puts right what's left: `tests/installer.rs` kills it after each one, and inside the record's copy and restore. Should the new version keep failing with no installer around, the launch after three that didn't come up starts one going back. A release that gets as far as quitting the app and reopening it with nothing to show for it says so at that launch, and the third time in a row is the last by itself.

**What "come up" means** (`Updater::first_frame`). What the installer waits for, and what stops a launch counting towards going back. The state's been read, a first frame's showing, and this version has drawn a page through the real renderer: a page of ours, of one colour, that has to come back that colour. Not the first frame alone, which a timer can force and a sleep file can fill with no renderer running. Not one of the user's PDFs, which can be moved, damaged or on a dead volume and says nothing about the version. It's only asked of a version that's new here, so a normal launch costs nothing. **And after it:** `launch-ok` says how many tabs were in the record as the new version read it, and the plan how many were in the record as the hand-off wrote and read it back (entries a restore leaves out on purpose, or a tab closed since, don't count); fewer is a misread, and the installer goes back with the record from before. A version that's come up is then on probation (`Saved::probation`) for as long as that record is kept (`KEEP_RECORD_COPY_MS`, a week): each launch marks its run, which a minute's use (`EARLY_END_MS`, by the one update timer) or a quit someone asked for clears; a launch that finds the last run still marked counts an early end, and the launch after three in a row (`EARLY_ENDS_LIMIT`) starts the installer going back with `keep_record`, so the record stays as it is, holding whatever was done since. The record from before is kept then too, and if the previous version finds the record damaged, or of a newer kind with nothing of its own beside it, it puts that back where it reads and reads it instead (`updates::fall_back_if_unreadable`), once, and says so. Quit Anyway and a SIGTERM, which the host turns into a quit, aren't early ends; Stay is watched again. Going back by itself, the version before comes forward and opens what the launch was asked to open (`Plan::open`). Copies a build before these names left as `RectoPDF.app` are moved to them at a launch with no installer about (`plan::move_to_new_names`), and by the installer. A misread that keeps every tab isn't caught, and the record from before is there to go back to by hand. The real app's misbehaviour for these tests is a file in a test release's `Resources` (`recto_update::test_breakage`), never looked at in a release build.

**Out of sight stays so.** A window in the Dock (`WindowRecord::minimised`) and a hidden app (`AppRecord::app_hidden`) come back so at a launch an update opened, arriving, gone back or not installed, and only then (`updates::stays_out_of_sight`, `Updater::reopened_by_update`), and a state read after the host has decided without it keeps what the host did (`updates::out_of_sight_when_restored`). So that it doesn't have to, a launch an update may have opened, by what the launch was found to be or, before then, by an install's plan or outcome being there, waits for the state up to 20 s rather than the window's usual second (`updates::restore_patience`): a full check under load saw a closed window open and one in the Dock come back shown, the state read after the second was up. Then: `WindowPlacement::minimised`, `app_comes_back_hidden`, then `miniaturize` and `NSApp.hide`, which haven't been seen on a real desktop. `qa minimise` and `qa hide` stand in for AppKit's notices. **A check from the menu with no window showing**, closed or in the Dock, leaves its answer for an app-modal alert (`Updater::take_alert`, `take_update_alert`), through `SheetPresenter.presentAppModal`, which a quiet run holds and `qa sheet-answer` ends; with the window open the margin says it.

**In the background** (`updates`, `MainWindow`). An update arriving while the app wasn't frontmost is sent behind everything with `orderBack`, isn't made key, and doesn't go into full screen, which is another Space, until the user comes to it. `open -g` is what stops it taking the focus. None of that has been seen on a real desktop, as a quiet run has no screen.

**Test and release** (`source`). `RELEASE_BUILD` is compiled in, by `RECTO_RELEASE=1`, which only `app/release-zip.sh` sets. A release takes its repo and its trust from constants, and doesn't look at the environment, and the installer ignores a plan's test fields. `release-zip.sh` runs the real binary with every override set to prove it, asks the app's own library too (`RectoPDF --build-kind`, answered before AppKit starts), and fails on any test's broken-release file (`test-*`) in `Resources`. A build that isn't a release takes `RECTO_UPDATE_REPO`, only on a state folder set on purpose, and only `http://127.0.0.1:PORT`, and then behaves as a release against that server. With neither it's a local build (`Mode::Development`, still `build: development` to an agent): it checks when asked, never replaces itself, and a quiet run reaches no real server at all.

**Development builds** (`version`, `updater::builds`, SPEC decision 28). `X.Y.Z.N`, ordered after `X.Y.Z` and before the next release, and built as a release (`RECTO_RELEASE`), with `RectoDevVersion` in Info.plist beside a plain `CFBundleShortVersionString`; `version::running` is which one a copy runs as, from both. `Updater::install_build` takes a zip named for its version, refuses unless *Allow development builds* (`Saved::dev_builds`) is on, and stages it by our own reader with `stage::prepare_build`: bundle id, version and `codesign --verify --deep --strict`, ad hoc or not, and not the team or Gatekeeper, as a dev build never touches the keychain. Then it's `Status::BuildReady`, held in memory, and `rules::build_step` lets it go after 5 minutes without input (`IDLE_BEFORE_BUILD_MS`) through the release's own `wait_and_hand_off`, or at once with `--now` or the menu. While one waits, the daily check doesn't set the timer, which would otherwise wake it every second. Its plan says `development_build` and `any_version`: the installer then holds the bundle to an intact signature rather than the team, and only once it's read the switch again from `updates.json` itself, and takes an older version. Turning the switch off on a build sets `back_to_release`: a check at once, and the release it finds (`Latest::on_offer_back`) goes in by the 30-minute rule whichever way *Update automatically* is set; a release running clears it. **Full, always:** `update install <zip>` is a Full command like any install, whatever the switch says (review round 1: anyone can sign ad hoc, so the switch alone isn't consent). **At the swap:** a plan saying `development_build` is taken without the team only for an `X.Y.Z.N`, with identifiers that are this app's and its helper's (`stage::has_identifiers`), and the switch read from `real_state_root()`, never the plan's root, in a release build (`install::switch_file`). **Going back by itself** (`start_going_back`, `run_back`) takes a kept copy only if `stage::may_go_back_to` says so: the team's, or ad hoc with the switch on and the identifiers. **Round 2:** only over a copy that's itself ad hoc (`builds::takes_builds_over` in the app, `replacing_is_ad_hoc` in the installer just before the swap); `install::plan_refusal` holds a plan to the app the installer is in, that app's folder beside, and in a release build `real_state_root`; `may_replace` lets a release build go to any other version only for a build over an ad-hoc copy or from a build to a release; `run_back` looks at the kept copy after its wait; `Host::may_take_a_build` drops a build once access is below Full. An EPERM at the swap, as App Management refuses, is `not_permitted`, said in words, and not held against the version. **One install:** `recto_platform::registry` forgets a copy with Launch Services (`lsregister -u`), every bundle under a folder, and lists what's registered; a quiet run forgets its own copy in `shutdown` (`updates::forgets_on_quit`), the tests' harnesses on teardown, and `tests/registrations.rs`, its own stage after the app's tests, fails on this tree's copies left registered, forgets those and the tests' temp copies, and only reports anything else. `tools/dev-build.sh` makes the zip.

**What it costs, measured** on a release build, in quiet runs, under the build queue's load (1 to 2 of 3 slots busy): quit to first correct frame 341 to 384 ms over 7 runs, median 363, on a rich state of three tabs. Of that, the old process ending takes 17 to 20 ms, the last look at what's being swapped in 30 to 46 ms, and the swap 0 to 1 ms. Before the last look it was 292 to 488 over 5 runs, median 305, on a different day's load. Drawing the proof page comes after the first frame, so it isn't in the gap. At rest over 20 s with the timer armed: 3 to 8 wake-ups, against 6 to 7 with nothing armed, 0 to 4 ms of CPU. Footprint at rest in the same plain app: 11.70 MiB with nothing armed, 11.59 to 11.63 with the timer armed, and 11.61 before a check against 11.64 after one that found an offer. `app/release-zip.sh`: a 9.9 MB zip of a 23 MB bundle. **A test's copy of the app costs about 1.8 MiB more at rest, at 13.5 MiB, with nothing armed:** its own bundle id and `LSUIElement`, so numbers from `measure_what_the_updater_costs_at_rest` aren't the real app's. That's the likeliest reading of the 12.39 and 14.47 seen there earlier, which `docs/PLAN.md` still carries, as 14.47 hasn't been seen again.

**Files.** In the state folder: `updates.json`, what's remembered, `update.log`, one older file kept, and `update/`, which has a plan, `launch-ok` and the rest only during an install. Beside the app, private: `.RectoPDF-update/previous/RectoPDF.kept`, and `new/RectoPDF.staged` while one waits. **Not `.app`:** a scan of the app's folder registered a hidden copy with Launch Services (`lsregister -R -f`, 2026-11-11), which puts a second RectoPDF in Open With and lets the system open a PDF with a version that isn't the installed one. A signature and Gatekeeper go by what's in a bundle, not its name, and the swap and going back rename it to the app's own. The renderer's helper inside is still found by a scan; it's background-only with no documents, and its name is sealed by the app's signature. A launch writes nothing here unless it's a new version's first one, or in the week it's on probation after, when each launch and its first minute write `updates.json`'s few dozen bytes. *Update automatically* is in `updates.json` and not the session's record, so losing a record can't turn it back on, and an unreadable file counts as off.

## Opening: recent files, files that change, passwords

**Recent files** are a list of at most 20 paths in the session, newest first, in the state record as `recent` (read up to 256, held to 20, relative paths dropped), moved to the front on every open and every return to an open file. File > Open Recent is a submenu Rust lists (`MenuEntry::parent`), and the UI thread reads the list from what the session thread last published, never the session. The published list is built again only when the session's `recent_version` or the tabs' version has moved, not at every reconcile. Each item's id is `recent.<key>`, sixteen hex digits from the path (`menus::recent_key`), and `AppCore::open_recent` takes that key: the item opens the file it showed however the list has moved since, and nothing if that file has left the list. `recto recent` needs Control, names and paths alike (coordinator, review O7): the names of files someone's closed say what they've been reading. A palette that lists menu entries skips those with a `parent`, so a recent file called "Close" can't stand in for the Close command.

**Files that change while open.** Before this a tab's file was looked at on restore, before it's shown and when it wakes from its sleep file, and a worker that saw its file replaced said so. Coming back to the app from another now looks at each file showing too (`CoreCall::LookAtShown`), since that's when a person has been elsewhere changing it. Each look is a stat on a thread of its own, as a wake's is, and `sleeper::LookSlots` holds them to one per tab and 8 in all, so ⌘Tab over and over with a hung SMB volume adds no threads past those; a look that's skipped happens at the next of those moments. No watch is kept. A file that's changed says "This file changed on disk since it was last read here", which blames nobody: a headless `recto` session saving it is RectoPDF too.

**A file the structure reader refuses at a limit opens to be read through PDFium alone.** `recto_core::agreement::refusal_of` turns the fork's caps (revisions, entries, structure windows, object and stream sizes, resolution depth, page count, page-tree depth) into `OpenError::TooComplex`; `recto_agent::loader` then asks the renderer as it does for `NotPdf`, and the tab opens renderer-only, edits refused and so nothing to save (coordinator's decision, review round 1). The indexer and `recto signatures` treat it as they treat `NotPdf`. `TooComplex` is what's said when PDFium can't read it either. Each worker start pays PDFium's own cost of reading such a file: a chain of 100,000 `/Prev` sections took 3.4 s to load where the fork refused it in about 3 ms, which is accepted. Opening itself runs on a read thread, never the UI thread (`40be99e`): `opening_a_slow_hostile_file_never_holds_the_window` opens three sections relisting about a million numbers each (`recto_testpdf::relisted_xref`), 3.5 s of lopdf's time in the debug app, by `recto open` and by Open Recent, and the window's worst wait was 15 ms.

**Passwords.** `recto_platform::Password` (re-exported as `recto_core::Password`) is the one place a typed password lives: no `Clone`, no `Serialize`, a `Debug` that hides it, overwritten on drop. It's in `recto-platform` so the renderer's host holds the same one: `DocRenderer` keeps an `Arc<Password>` shared with the keyring, not a copy. `inspect_with_password` opens with it; `checked_reader` tells the reader's `PasswordRequired` and `InvalidPassword` apart, which before read a user-password file as "not a PDF". The page views share a `Keyring`, keyed by the file's device and inode rather than its path, so a file moved while open keeps its password and another file put at its path doesn't get it; the renderer looks its key up by the open file's own identity (`fstat`). The session thread lets go of any key whose file no tab has open, at most 64 are held, and reads of a protected tab that went cold use its key, so it doesn't ask again. If a renderer finds a file needs a password it has none for (a file moved to another volume or replaced while open), it tells the app (`Engine::take_keyless`), the tab's facts are let go and it's marked as needing its password (`Session::needs_password_again`), and the sheet asks again.

The sheet is the system's `NSAlert` with an `NSSecureTextField`, in Rust's words (`passwords::prompt_for`). Several files can want a password at once: each is an `Ask` with its own id, waiting in turn in `passwords::Asks` (at most 8), and the prompt carries its id to Swift and back with the answer (`AppCore::password_answered(id, password)`), so a password always goes to the file the sheet named. What's typed is tried on a thread of its own, and the field is emptied. A restored protected tab has `password_needed` as its problem, and is asked about when it's showing; Cancel leaves it saying it needs its password until the person goes to another tab and back. Wrong tries are kept per file until it's opened again (File > Open, Open Recent, a drop), whichever tabs are visited meanwhile, and five stop the asking for that file.

**The copies of a password that remain.** Rust overwrites what it holds: `Password` on drop, the `String` UniFFI hands over (`Password::take`), and the open frame sent to the renderer's worker once it's sent (`secret::wipe`). Others aren't ours to overwrite: the Swift `String` from the secure field and the UniFFI buffer it crossed in, as Swift strings can't be zeroed; the copy lopdf takes out of `IndexedReaderOptions.password` and drops once it has derived the file's key, inside `IndexedReader::open_with_options`, since the options are moved in (a fix would be in the lopdf fork); the worker's copy of the open frame, and PDFium's own C string and key schedule inside the walled worker process, which go with the worker. None is ever written, logged or put in the record.

**Agents and protected documents.** A tab opened with a password the person typed is marked (`TabRecord::password`, kept in the record as `password`), and `Session::withheld_from_agents` is true for it, and for any tab that needs a password. `encrypted` isn't the gate: a file anyone may open can be encrypted too. Every agent command about such a tab, and `find` while it's the document being read, is refused with exit 8, `protected`, before the tab is touched (`recto_agent::execute`), except `where`, `tap` and `close`, which read nothing of it; and everything that lists tabs leaves out what was read with the password: `where`, `tabs`, `session show` and `compare` give no page or length and say `protected`, `sidebar` gives its tab row and none of its contents, `page_changed` and `edits_changed` events carry no page or length, and `wait` on its pages, index or contents fails as protected. `find`'s answer gives no hits from such a document, whichever tab is being read by then. The person's own Find does search it: the app hands `SessionHost` a lookup into the keyring (`set_find_keys`), and a plan with it (`FindPlan::with_keys`) reads that file page by page through a worker opened with the password, never reading, building or asking for a corpus, so its text is never written. An agent's `find` and `search` plan without it. `links`, `follow`, `back`, `forward` and `goto label` are refused like the rest, page labels go with `where`'s place, and the page view's own link reading (`DocRenderer::read_structure`) uses the shared `Arc<Password>` and never reaches an agent. Reading a protected document needs the person's consent per document (agent report §5.5), which isn't built, so until then nothing gets through. `qa state` and `qa shot` read the window, but a quiet run's `qa password` only types into the sheet for a file in its state folder or a temp folder, and reads the password from stdin, so a quiet run can't open one of the person's own protected files.

## Links, Back and Forward, page labels

**Read from the structure, judged in Rust.** `recto_core::nav` reads a page's `/Annots` links and the catalog's `/PageLabels` through the lazy reader, with no renderer. A link is a page of this document (with how far down, from an `/XYZ`, `/FitH`, `/FitBH` or `/FitR` top on a page shown upright or upside down), a web or email address (`http`, `https`, `mailto`, printable ASCII, at most 2,048 bytes, and none of `\ " < > ^ ` { | }`: a backslash is a slash to a browser, so `https://evil.example\@bank.com/` would show one host and go to another, and Foundation rewrites the rest before opening; anything else is refused rather than cleaned, as a cleaned address is another address), Back or Forward (a named `GoBack` and `GoForward`), refused with what it is (`file:`, `javascript:`, launch, other files, other schemes, other actions), or nowhere. Rectangles are on the page as the file shows it, past the crop and turned by its `/Rotate`, the frame a selection uses, so the page view hit-tests both alike. Caps: 1,024 links and 8,192 annotations a page, 16 pages a read, 4,096 tree nodes and 500 ms a read, 1,024 label ranges, a 64-byte prefix cleaned as a title is, and a label at most 96 bytes, as roman past 3,999 and letters past 16 are written as digits. The `pdf_bytes` and `pdf_tree` fuzz targets read links and labels, and check addresses, boxes and labels.

**What a read costs**, release, this Mac at load about 5, median over about 45 pages of each, `crates/recto-core/examples/links_cost.rs`: `rfc9110`, 805 links, 5.8 ms a page p50 and 6.1 p95; NASA `ntrs20240002628`, 383 pages, 7.3 and 7.7; `eu_aiact` 2.4 and 2.5. RFC 9110 was 37 and 147 before two changes: its old `/Dests` dictionary, one object of every name, is read once a read rather than once a link, and a name tree written in place is looked through rather than copied for each link (`find_named`). What's left is mostly opening the file and its page map, which grows with the page count, so a 10,000-page file pays more; that isn't measured. A read opens the file with a 4 MiB cache of objects and object streams for that read alone (`open_reader_cached`).

**In the app.** The page view holds the links of at most 64 pages of the tab showing (`recto_reader::links`), and none of a tab off screen. A page's are read on its own thread when the pointer is first over it, through the very file its renderer has open and with the password it opened with (`DocRenderer::read_structure`, in this process), so they're of the version being drawn, a protected file's too, and a disk gone to sleep holds that thread no longer than a draw would. A file seen replaced and not yet taken up offers no links, as they'd be the new version's over the old pages. The UI thread asks what's held, a short lock: the pointing hand and a hint in the lower left of the pane (`AppCore::pointer_look`), whose page words come from each pane's labels published by the session thread, never from the session. A still single click (under 3 points of movement, one click, no shift) is taken on release, and `follow_link` decides: a jump on the session thread, Back or Forward, the sheet for an address (`LinkPrompt`, numbered, so an answer is to the sheet that was shown, with the real host after any `user@`, in lower case), or a notice. The address goes to `NSWorkspace` only from the sheet's Open, and a quiet run notes it in `app.links.address_opened` and opens nothing.

**Back and Forward** are a trail per tab in the session (`recto_session::trail`): a jump marks where the reader was, from the page view's place taken in just before (`take_places`), and clears the way forward. At most 50 stops each way, 12 bytes a stop, held in the tab's record and counted in a cold tab's 4 KiB (`a_cold_tab_with_a_full_trail_stays_in_budget`), nothing for a tab nobody's jumped in. Stops follow their pages through edits, and go with a deleted page. An agent's jumps are marked as its own and can't push the person's stops out past the cap, nor clear the person's way forward (coordinator, 2026-11-08, as with undo), and in the state record as `back` and `forward`, read up to 1,024 and held to 50. The page view lands a jump at its depth (`Engine::jump_within`), even on the page it's on. Go > Back and Forward on ⌘[ and ⌘], the system's swipe (`swipe(with:)`, a positive sideways amount going back, as in Safari), `recto back` and `recto forward`. A two-finger swipe, which needs AppKit's scroll-event tracking, isn't done.

**Page labels** travel in `Toc` with a warm tab's contents, and in its sleep file, so a tab woken from one says `iv` at once. A page is labelled by its own file's page, so a moved page keeps its label and a page added from another file has its number. The corner says `iv (4 of 120)`; the go-to field opens on the page number and takes a label first, as Preview does, then a plain number (`Session::page_for_typed`).

## The search index

**The corpus.** A document's pages as text on disk, one folder per version of a file, under `~/Library/Caches/RectoPDF/corpus.noindex/<key>/v3/`, or the state folder's `corpus.noindex/` with `RECTO_STATE_DIR`, so a QA run leaves nothing anywhere else. `app/` holds what the search reads: `text.pack`, each page's exact normalised text in turn, and `pages.bin`, a fixed record per page. **The text is kept once.** `agent/` holds every page again, as `manifest.json` and `pages/0001.md` onwards, the way the agent report's §6.1 has it for Phase 6's `Read` and `Grep`. Nothing reads that yet, so a build doesn't make it: `recto index --agent` does, from the pack alone, with no PDF involved (owner, 2026-11-07: "Feels a bit inefficient?"). No page's text is in memory past that page, and the session holds no state about any of it. `crates/recto-index/src/corpus.rs` has the layout.

**A page's file** starts with a line a page can't write, `<!-- recto page=12 cite="PDF p. 12" text=native hidden=clean untrusted=document_text -->`, and line `n` of the page is line `n + 1`. It's the page's text as it is, so a plain `rg` works and a phrase over two lines is a plain multi-line search, which a `| ` on every line, as `text` prints them, would break. A line holding text that looks hidden starts `! `, with the words inside `[hidden: ...]`, by the same code as `text`. A page's own line that would read as one of those marks gets a `\` first, so `! ` at the start of a line means what it says, and no page can write the first line's comment. The other spellings of hyphen decisions go last, so `Grep` can find those too. Pages that couldn't be read or have no text say so in words. `cite` is only `PDF p. N` until page labels exist.

**Keyed to what the file is.** The key hashes the device, inode, size, modification and change times and first and last 64 KiB. A file replaced with its size and time put back has another inode, or another change time if written in place, so its old text can't answer for it. It takes one `fstat` and two small reads, because every search asks for it, which is why it isn't the agent report's hash of the whole file: 2 GB takes seconds. So a copy gets its own corpus, and a moved or touched file is built again. That costs time and is never wrong. A build checks the key every 64 pages and at the end, and throws away what it's read if the file changed. Reading a finished corpus only ever answers for the version just looked at. Its name and path aren't in the key or in the folder. **Only a file on APFS is indexed.** Its nanoseconds and a change time nothing can set are what make a same-size rewrite show. exFAT has no change time, and at best 10 ms on its modification time, HFS+ has whole seconds, and a network volume says what its server says. Reading more of a file wouldn't settle it short of the whole of it, per search, so a search of a file on those reads its pages, as it always has, slower and never wrong, and `index.note` says why. Checked on this Mac: `/Volumes/EksternalHome` is APFS, and a file on an exFAT disk image was refused with exit 1 and its search read pages, with nothing written. A volume's device number can change when it's mounted again, and that costs a rebuild.

**A folder from an earlier build.** Before it was named `corpus.noindex` it was `corpus`, with plain text that nothing here would otherwise look at. A session's start removes that one folder, and not a link there or anything named like it.

**An old version's text goes.** Each key stands alone, so a saved edit, a redaction or a file since encrypted would otherwise leave the old version's plain text. `by-file/` holds a small file per hash of a file's path, of where that really leads, and of its inode, each with the keys it's had, so a new version at that path, or the same file renamed, is connected. None holds a path. A key is noted before a page is written, so a build stopped partway can be found too: that's the redaction case. When a build for a new key finishes, or the new version is refused, the other noted keys' folders go, and one that can't be removed stays noted. `recto index clear` takes every version on record, even if the file's gone. Until then the old text stays: an edit nobody has searched or cleared since hasn't told this anything.

**What makes it build.** Someone asking: a `search`, `recto index`, or `recto wait indexing-done`, which would otherwise wait out its time on something nobody started. **Never opening a tab or switching to one,** so 200 open tabs cost nothing here, and a tab holds nothing about its index. One helper runs at a time for the whole session, and at most 16 files wait, the newest ask first and the oldest giving way. Whoever still wants one asks again, so nothing's lost. `crates/recto-control/src/indexing.rs` has the rest.

**What stops one.** `recto index clear` takes a file off the queue and stops its build before clearing, so the queue can't write it all back, and it gives the helper up to 3 s to go. Lowering access to Off stops whatever's running and empties the queue, since those are agents' asks, and the user has said no. What's written stays until something clears it. Nothing starts again until someone asks.

**The helper.** `recto-indexer` is a process of its own at `PRIO_DARWIN_BG`, which its render worker inherits (`ps` shows both at priority 4, against 31), and it exits when done, as `SPEC.md` §2 has it. So what it uses ends when it does: a page of two million characters takes tens of megabytes to read, and the session's footprint stays where it was. It takes its job on stdin, so a file's name stays out of `ps`, and it ends as soon as stdin closes, so it can't outlive whoever started it however they ended. The session's one thread for it exists only while there's something to build. `stop` closes that pipe. Anything that stops it leaves a usable state.

**Killed at any moment, it's sound.** A page's text is written, then its record, and only a record counts. Starting again checks every record against what's there, cuts off anything past the last that holds up, and goes on from there, coming out byte for byte the same as a build never stopped. `ready.json` goes last, after a sync of the pack and table, and nothing is used without it. An agent's folder has its `manifest.json` written last. **Page files aren't synced:** on this disk an `F_FULLFSYNC` costs 5 ms a file against 0.09 ms with none (load 12 to 17), so 383 pages would be 2 s and 10,000 pages 50 s, for a cache. Asking for the folder checks each file's size against what it should be and rewrites any that's wrong, so an empty or missing page after a power cut is mended when it's next handed out.

**Its limits,** from outside. 256 MiB for its worker, half a reader's, with no heavy step: only the hidden-text check draws, and by the numbers above 17 of 5,872 real pages need more at 2x. Such a page reads as `hidden=not_checked`, and a search draws it if it ever finds something on it, under a reader's limits. After 16 such failures in a document the rest go unchecked, because kills are capped per document, and spending them all on a check would leave pages unread. 10 s a page, twice a reader's, since this is on the slower cores. 512 MiB a document, past which it's refused and its text removed. 200,000 pages. An hour for a build, after which the next ask goes on from there. All corpora together 2 GiB, the least recently used going first, and anything unused for 90 days (agent report, D6). That's looked at when a build ends, however it ended, and on the first ask of each session, on the indexer's thread, so a deleted PDF's text goes at 90 days without any build. It doesn't go sooner: nothing here can see that a PDF was deleted, and `recto index clear` is how to say so. A full disk gets at least 64 MiB back, however far under its cap the folder is. Only folders named as keys are ever looked at or removed. A file that needs a password has nothing written, and `refused.json` holds only that. A file readable with no password is indexed, as `text` reads it: `aes_128` and the like. The real `form_bomb` fails its page in 2.4 s, where a reader's limit sequence takes 3.1.

**A page that fails.** What goes down depends on whether it's about the page. A worker that can't be started, or a failure remembered for only a moment (`Unavailable`), writes nothing: the build stops where it is, and goes on from that page after a pause. A worker lost to a deadline or for no stated reason may be the moment, not the page, so the page goes down as failed, the rest carry on, and it's read again at once, and up to 3 times in all, 10 minutes apart if someone's still searching, 64 pages a go. Past its memory limit or breaking the protocol is the page's own doing, and it isn't retried in a build. A failed page in a corpus is only what happened when it was built, so **a search reads it live, like `--scan`**, and `route` says `mixed`, up to 5 s of that per search. A worker's deadline is 5 s a page and 128 kills a document, so 10,000 bad pages would otherwise use up every search on its first few. Past the 5 s they're listed as failed with no worker, counted in `failed_pages_not_read_again`, and the clean pages behind them are still read. So answers from the index and `--scan` differ on a file like that, since `--scan` stops at its 30 s. Drawing to check for hidden text stops at the deadline too: a page past it says `checked: false`, and a ranked search leaves out top pages past 5 s more, in `top_pages_left_out_for_time`. The agent's folder and the manifest say what the build found.

**Not trusted when read back.** Lengths are checked against the file, text as UTF-8, and a corpus that doesn't add up is thrown away and built again, which only costs time. The search goes on by reading pages, in the same answer.

**Spotlight and backups.** The folder is named `.noindex` and carries the attribute `tmutil addexclusion` sets, byte for byte. Checked on this Mac, 2026-11-07: a test file with a unique word in a folder under the home showed up in `mdfind` within 25 s, and its twin under a `.noindex` folder beside it didn't, which the name alone explains, though one try on one Mac isn't a promise. `tmutil isexcluded` says `[Excluded]`, and a test holds that. No Time Machine destination is set up here, so no real backup was tried. `~/Library/Caches` is left out of backups by default anyway.

**What 0700 doesn't stop.** It keeps other users out. It doesn't stop an agent running as this user: one with a shell of its own, even with access at Off, can `rg` this folder, as it could read the PDFs themselves, since levels govern `recto` and not the file system. The difference is that **this folder also holds closed and deleted documents**, up to its limits: 90 days from their last use and 2 GiB in all, unless cleared. Phase 6's locked-down run reaches only one document's `agent/` folder, and that's what's meant to contain it. A user's own agent with wide tools isn't contained.

**No index in front of the text, because it isn't needed yet.** A search is one pass over `text.pack`, folding each page with no map back to the text, and placing hits with the normal code only on a page with one. So the same code that reads a live page makes each hit, which is what makes the answers the same. A trigram or word index would shorten a pass that's already this quick, take more room on disk, and need its results checked against the text anyway. **Measured** below: 37 MB of text takes 42 ms, and that's the largest tested. By arithmetic, the 200,000 pages a document may have would take about a second, which wasn't tried. If documents that large turn out to be common, that's the next step, behind the same command.

**The same answers, proven.** `real_pages_answer_the_same_from_the_index` holds every field of an answer from the index to `--scan`, apart from how it was read, for 8 plain searches at 2 limits each, 7 patterns and 6 ranked searches on each file. That needs a folder of PDFs, so it's `RECTO_BENCH100=<folder> tools/check.sh --corpus`, about a quarter of an hour, and not part of `--full`, where `the_hard_cases_answer_the_same_every_way` always runs the same comparison over a page with a word drawn late, words broken at line ends, hidden text and no text. `the_same_answer` leaves out `route`, `index` and the counts, and `totals_agree` holds the counts wherever a page-by-page read can know them. It covers line-order repair, hidden text and hyphen spellings because `read_page` is the one way both get a page's text. `an_edited_tab_keeps_its_page_numbers_and_marks_added_files` holds the same through moves, deletes, inserts and undo.

## Find

**One query, in the background, by `search`'s reading.** `recto_agent::find` runs a phrase over a plan of the document being read, page by page, from its corpus if there's one and through one worker if not, asking for a corpus for next time, so Find finds what `search` finds (`find_lists_what_search_finds_in_order_and_steps_from_the_reader`). It keeps at most 1,000 hits, counts the rest, and stops at 60 s. `recto_control::finding::Finder` holds the one query's hits: a new query stops the last between two pages, and its one thread exists only while a query runs, so a session at rest has none. Hits are places as characters of the page's text, which a selection counts too, so going to one is a selection (`Reader::reveal_range`), brought a third of the way down the view once its page's text says where it is. The app's sidebar reads the Finder's hits under a short lock and never the session's; every step goes through the session thread to `SessionHost::find_*`, the same calls as `recto find`.

Later queries read the corpus and start none. Hidden text: a page with hits is checked as `search` checks one, from its corpus or by drawing it, for at most 10 s a query; past that its hits are listed as not hidden, unchecked. Not measured: a worker's peak during a query (it's `search`'s worker, under a reader's limits), the made 10,000-page PDF, and the app's own footprint with Find open (the app's QA runs show no stall over 1 s while finding).

## Generated contents

Owner, 2026-11-07: "I think option 4 is the best one, dont modify the bad toc, but offer a generated toc using distillpdf". A file's own contents are never changed. Where they're missing or look bad, the sidebar offers contents made from the document's headings, and an agent gets the same through `recto contents --generated`.

**The route.** `recto contents --generated`, `recto wait contents-generated` or a tap on the sidebar's note asks `recto-control::generating::Generator`. One helper at a time for the whole session, at most 8 waiting, the newest first, and the session's one thread for it exists only while there's something to make: nothing at rest, nothing on open (decision 22's rule). The helper, `recto-headings`, takes its job on stdin, so a file's name stays out of `ps`, and ends when stdin closes. It opens the file with distillPDF's `LazyStrict` engine only, which refuses a file rather than fall back to the eager one, whose page content isn't capped. `scan_document` (the full scan, with its rendering pass, so running heads and flooding styles are known) and then `page_stream` a page at a time. Each heading block's text has distillPDF's inline markup taken out (`<b>`, entities), is cleaned like any title from a file, and capped at 240 bytes; a title on 4 pages or more and on a quarter of the pages is a running head and goes, before the list is cut at 4,000, so "Introduction" in each of a book's chapters stays. Then the check for hidden text, below. Two lines go back on stdout: numbers, and the contents in `recto_index::generated`'s form. The session reads both as hostile, with the same reader as the kept file, capped at 1.5 MiB, and writes the file itself: the helper writes nothing.

**Watched from outside.** The session reads the helper's footprint every 25 ms and kills it past 512 MiB, past 3 minutes and a second a page (half an hour at most), or when it's cancelled: access set to Off, the session ending, the tab closing, or the reader clicking *Generating contents…* to stop. It's started with `MallocLargeCache=0`, and nothing else from the environment but the two development overrides for the worker. The helper also watches itself and leaves past the limit it was given, as a second line. Its render worker has a reader's limits, 512 MiB, with no heavy step: at the indexer's 256 MiB, 58 of `ntrs20220005969`'s 196 pages couldn't be drawn for the check, and all their headings were left out. A refusal, or a stop at the memory or time limit, is remembered for that version of the file, and any other failure for a minute, so a loop of asks starts nothing, and a hostile file can't take a gigabyte every minute.

**Hidden text never makes a heading.** distillPDF 0.1.7 has no flag for hidden text, and reads text whatever its render mode or colour: on `recto_testpdf::headings_document`, a white heading and a render-mode-3 heading are both taken for headings. ## The agent interface

`recto` is the interface every test and agent uses from here on, and the Mac app and agent sidebar sit on it. It's three layers: the command table and dispatch (`recto-agent`), the session on a socket (`recto-control`), and a thin client (`recto-cli`).

**One table.** `TABLE` in `crates/recto-agent/src/table.rs` has a row per command: its level, its arguments, what `data` holds, what it tells watchers, and its examples. The CLI's parser reads the row, so a flag can't exist without being documented, and `SKILL.md` and `REFERENCE.md` are generated from it. Tests walk it: every command has a row, every row runs, every example parses, every argument reaches its command, and every row is enforced at every level over the real socket.

**The server: one thread, blocked in `poll`.** It owns every connection, so a connection costs a small struct, and a client in `wait` or `watch` costs that and nothing else. There's no thread or task per client, per tab or per wait, and no timer: `poll` is given the next real deadline, or none, in which case it sleeps until a socket has something. Work that can take time runs on a short-lived thread per job, capped at 8, of which at most 2 may draw or read pages, since each of those can use hundreds of megabytes. A job tells the loop it's done through a socket pair. With nothing happening there's one thread, asleep. `status` is answered on the loop's own thread and takes no lock, so it answers even while a slow file holds the session.

**Why no async runtime.** A runtime would have given this exactly one thing, multiplexing, in exchange for a large dependency and a thread pool, and the multiplexing is 40 lines of `poll` in `recto-platform`. The real work here isn't async anyway: PDFium's worker, the lazy reader and file reads all block, so they'd need a blocking pool either way. `poll` over `kqueue` because the connection cap is 128, where `poll`'s cost per call doesn't matter, and it's the one call with the same meaning everywhere. **Measured** below: an idle server does nothing at all.

**The session lock is held per step.** `execute` takes the session through `SessionAccess`, only as long as each step needs. `open` and `page insert` read the file with no lock held, then take it to make the change, so a slow or hostile file holds nobody else up. **What isn't solved yet:** switching to a cold tab reads its file with the lock held, as `Session::tap` and `close` do, so a file on a dead volume could hold the session until the volume answers. `status` still answers, and every client gives up with exit 7 rather than hanging.

**Hostile input.** A line is capped at 64 KiB, a selector at 1 KiB, and half a line has 5 s. Commands parse with `deny_unknown_fields`, so a mistyped or added field is refused. A silent connection goes after 60 s, a client that doesn't read its answer after 30 s. A client past 1 MiB unread has its next command left unread until it catches up, so nobody works for answers nobody's taking. An answer is capped at 32 MiB. All unread answers together are capped at 128 MiB for large ones, and at 144 MiB for anything: small answers can go past the first, so `status` still answers, and whoever would take it past the second is dropped. A watcher that stops reading is dropped past 1 MiB of backlog, and one that writes anything at all goes at once, since it could otherwise hold the only working thread. A panic in a job is an error for that one client. There's no rate limit beyond these caps yet.

**Ending a watch.** `recto watch stop` ends every watch on this session, at the level `watch` needs, and logs how many. An agent's `pkill` was refused, and its background watch stayed for its whole 10 minutes. It's for one agent to clear up after itself, and it can end another's, which only has to start again: a watch holds nothing that could be lost.

**What must always get through.** At most 128 connections, of which at most 64 may be in `wait`, `watch` or a waiting `permission request`. Past 128, up to 16 more may connect for `status`, `stop`, `permission show` and the message after `permission set`, and nothing else: anything else gets `busy`, exit 10, and each new one pushes out the oldest of these. A new connection reads the level before anything else, so a lowered level ends waits and watches even with every slot full, and a wait's look reads it again.

**`stop`.** It closes the door to anything but quick answers, refuses what's still queued, waits up to 5 s for what's running, and only then looks for unsaved or undone edits. An edit can't slip past that check. If something stays stuck, it says so and the session carries on.

**Out of descriptors.** On macOS, an `accept` that fails for want of descriptors drops the waiting connection (measured: 20 connections at a limit of 12, 8 accepted, 12 failed once each, then nothing was ready even after freeing some). So the listener doesn't stay ready, and there's nothing to spin on: those clients see their connection end. `out_of_descriptors_the_session_doesnt_spin` holds that. It would need a pause on an OS that behaves otherwise, and Windows is a different seam anyway.

**Local only.** The socket is mode 0600 in a 0700 folder that's checked, never repaired: a link, someone else's folder or an open one is refused. The peer's user is checked on every connection, and the client checks the socket and its folder the same way. There's no TCP listener, and a test holds the source and the running process to that. A client that's gone before it's accepted can't pass the peer check, so what it sent is dropped.

**Starting and stopping.** A server takes an `flock` on `run/server.lock`, held until it ends however it ends, so a second start is refused, and a socket file found while holding the lock is known to be left over. Only a socket of ours is removed. Clients take a socket nobody's listening on as "not running", exit 6. `recto serve --background` starts another copy of itself and blocks on its ready line. A session's tabs and unsaved edits end with it, and a new one starts empty.

**The app later.** `Server::bind` and `Server::run` take a `Host`, and `Stopper` ends it from another thread. The Mac app runs the same server on a background thread with a host that posts to its own session, so `recto` works the same against either, and it can show `permission request` as a prompt rather than a line on stderr. `SO_NOSIGPIPE` is set on every socket so a host needn't have ignored `SIGPIPE`.

**Asking for help.** `recto --help`, `-h`, `recto help`, `recto help page`, `recto page --help` and `recto help "page move"` all work, the last because the help's own list prints names that way. `recto --version` gives the version. `--flag=value` means `--flag value`. **A near miss gets the closest form that works, driven by the table, on every row: the whole line, mended.** An unknown flag becomes one named or spelled nearly that, or the place a value goes that has no flag, and a stray word gets its flag or the tab it could be. Every other word stays where it was, so `page delete --pages 3 --tab report` advises `recto page delete 3 --tab report`, and not a line that deletes page 3 of the active tab. More than one wrong word is mended in turn (`page rotate --page 1 --degrees 90` advises `recto page rotate 1 --by 90`). Each mend goes through the real reading of a line, and if it can't all be mended, as past `--`, or with a page given twice, no whole line is offered, only the flag and what it takes. A test walks every flag and value of every row, mistyped with all the others present, and holds the advice to the same fields as the right line. Every word is quoted so a shell passes it on unchanged, since a tab's name can come from a file, and one that can't be printed safely isn't printed. Every refusal also gives the command's usage line. `text` and `render` also take a bare page number (`recto text 60`), since three agents in three rounds tried it. A range stays refused, and says it's one page at a time. A mistyped command lists the nearest rows first, by spelling and then by the words of their summaries, so `recto doc` offers `facts`. A row that isn't built says so in `help`, the skill and `not_built`, in place of a level that reads as though it works.

**Levels.** `Off`, `Read-only`, `Control`, `Full`, default `Off`. Each command's level is in its row, read fresh from the file for every command, so lowering applies at once on connections already open, and to waits and watches, which it ends. `status` says how many PDFs are open at every level, Off included, so an agent can tell whether asking for access is worthwhile. A count isn't document content and holds no name, so this doesn't touch the rule that nothing from a document reaches Off. It fails closed: a missing, malformed, linked or open file is `Off`. Nothing over the socket can raise it: no command writes the file, and `level_changed` carries no level. No variable or flag does either.

**How the user sets it, in the headless phase.** `recto permission set <level>`. Lowering needs nothing. Raising needs stdin and `/dev/tty` to be a real terminal, and a word typed back that's different every time, read from the terminal. **The app's settings take this over later,** through the same `levels::store`. A refusal's `ask` is `recto permission request <level>`, which grants nothing. It answers at once, and tells the agent what to tell the user and to carry on with what it can. With `--timeout` it blocks until they've answered, and its help says that's only for when someone's at the keyboard: an agent in the blind test blocked for 2 minutes and then 5. It writes a line for the user only for a level higher than it's said since the level last changed, so asking in a loop can't fill that file, and a write that fails can't end the session.

**`recto skill install`** takes the same check (coordinator's decision, 2026-11-07): it writes into the user's agent's own files, and `--replace` keeps no backup. `recto skill show` stays open at Off, so an agent can read it. With a test state folder it won't write into the real home, going by where the path really leads.

**Below Full, an agent can throw away only agents' edits, never the owner's** (SPEC decision 20). Each step on a tab's undo and redo lists records its `Author`, and keeps it through undo and redo. Everything through `recto_agent::execute` is `Agent`. `Session::edit_pages` and `insert_pdf` are the app's own and are `Owner`, and `SessionHost::with_session` is how the app reaches them. `PageEdits` starts as the owner's and only the session changes that, so a path that forgets to say gets the more protected answer. It costs 8 bytes a step, nothing per page and nothing on a tab with no edits: at most about 4 KiB of a tab's history, on the 256 steps it can hold, only while it has edits.

At Control: an edit that clears undone steps, `discard` and `close` with undone steps go ahead if all that would be lost is agents'. If any of it is the owner's, it's exit 5 (`would_clear_redo`, or `would_discard_user_edits` for `discard`), the message says they're the user's edits, and `recto redo` or asking for Full are the ways on. Undoing the owner's steps is allowed, since `redo` brings them back. It doesn't hide them: `user_edits_undone` and `saved: false` say so in every answer, the sidebar model has `undone_owner_steps` so the app can show it, and `Session::close` itself refuses until they're redone or discarded, whoever undid them. So the app's own close needs `discard_edits` once it's been told "Don't Save". A tab with unsaved edits doesn't close at any level, so closing never loses edits silently: `discard` first, then `close`. A refused `close` names all it would lose and each way on that's real. `stop` still counts undone steps as unsaved, whoever's they are. At Full, what's lost is the holder's call.

**Edited means it differs from the file.** A step that does nothing isn't a step: `page move 3 --to 3`, or a whole turn. And four quarter turns, or a page moved and moved back, read as not edited, with their steps still there to go back through. It's a look along the list after each step, stopping at the first page out of place, and asking is free. **Measured** on a release build, this Mac, at the worst place, rotating the last page of an otherwise untouched document, over 2,000 edits: 80 µs at p50 and 91 µs at most at 200,000 pages, and 0.5 µs at 1,000. Reading a tab's state costs nothing more, and an edited tab's list holds 16 bytes more, with nothing per page.

**The undo cap.** When a step falls off the capped undo list its effect stays in the page order, so the cap hasn't erased it, and `is_edited` keeps saying the tab differs from its file. But `discard` would throw that effect away, so an owner's step that fell off still counts as the owner's (`owner_step_dropped`) and `discard` below Full stays refused. A redo step dropped by the byte cap is gone for good, and an agent could otherwise cause that by undoing, so the trim stops at an owner's step, and at any under it, because a redo step only applies to the state just before it. That can't take the list far over: what redo holds is the pages of undone inserts, which a document's length and the cap bound to `MAX_HISTORY_BYTES` plus one document, and `undoing_never_drops_an_owners_undone_step` holds it there. **Limit:** an agent can still delete a page the owner rotated, then make 256 more edits so the delete can't be undone. Nothing was thrown away by `discard` or the like, and the rest of the owner's edits stay, but that one is out of reach until the session ends. A cap on the agent's own steps would trap ordinary work, so this is stated rather than closed.

**What this does and doesn't protect against** (agent report, threat T16). The search corpus is outside all of this: see "What 0700 doesn't stop". It shuts every ordinary route: an agent running commands through a tool has a pipe, not a terminal. It can't stop a process of the same user that goes to the length of faking a terminal or writing the file itself: that process could read the PDFs directly anyway. A variable can point a run at a fresh state folder, which starts at Off, and writing a file into it gives access only to the throwaway session there, not the user's. The app's settings, behind a human gesture, are the stronger answer.

**Signing** is out of reach at every level. `recto sign` always refuses, and nothing in the control path links a signer. `recto signatures` reports facts through `recto_core::signatures`, a bounded walk of the form fields, with `recto-sign`'s wording: "Signature present, not checked", never "valid". Stated names and times go under `untrusted`, because they're only what the file claims.

**State folder.** `~/Library/Application Support/RectoPDF/agent`, under the real home from the user database, not `$HOME`. `RECTO_STATE_DIR` overrides it for tests and QA, and refuses the real home, anything holding it, and anything inside it unless that's in the OS's temp folder (from `confstr`, not `$TMPDIR`), through links too. If the path is too long for a socket (the kernel's limit is 103 bytes), the socket goes in `/tmp/recto-<uid>/`, checked the same way and named for the state folder.

**Activity log.** One line per action with its time, command, level and outcome, refusals included. It holds numbers, and cleaned file names under `untrusted`, and never document text: `Command::log_details` is the one place that decides, and a tab's name as typed and a search's words aren't kept. `tab` is the `#id` the command really acted on, found before it runs because `close` leaves nothing to ask afterwards. If it found no one tab, as with an ambiguous name, it says `by name`. A refusal for the level is counted rather than written out, so it keeps no details at all. At a real terminal `recto log` reads the files with no session or level, for the user. Otherwise it needs Read-only, even with no session.

An agent mustn't be able to erase its own record, so there are three files, 1 MiB each and rotated once. `activity.jsonl` has what changed something: `open`, `close`, page edits, `render`, `index clear`, `stop` and `permission set`, when they worked. `activity-overrides.jsonl` has each `--anyway` that gave text. `activity-other.jsonl` has the rest, so no flood of reading, refusals or other failures can reach the first two. `status`, bad lines, asks and refusals are written once, then as one line with a count, at most once a minute each. **Limit:** an agent at Control can still push out its own changes with enough of them, since each one is an action to record.

**Contents.** A first look at an outline needs its sections, and a root can hold only the title, as on RFC 9110, where `--depth 0` gives `RFC 9110` and `HTTP Semantics` and nothing else. So `sections_at` is the first depth whose entries are on more than one page. With no `--depth`, `contents` shows down to the deepest level that fits in 200 entries, never above the sections, and `depth_rule` says which that is, which entries are the top-level sections, and what to ask for instead, ahead of the list in plain output. An agent took two calls to work out what "top-level" meant. On RFC 9110 that's depth 2 of 4, 154 of 311 entries, in one call. Paging keeps to the same entries: the depth is decided from a fixed room of 200, not from `--limit`.

**A file only the renderer can read.** lopdf refuses some damaged files PDFium repairs, or finds no pages in them, and commands go through `session.open`. So `DrawableLoader` asks PDFium, in its worker, when lopdf says "not a PDF" or "no pages": the tab opens with PDFium's page count and `renderer_only` set. Facts stay trustworthy because nothing is made up. `facts` says `structure: renderer_only`, `contents` says `available: false`, and `signatures` says `structure_read: false`, each meaning "couldn't be read" and never "none". Editing it, or inserting it into another document, is refused, since only the structure reader's writer may change a PDF. A password-protected, missing or forbidden file stays that way: only those two answers get a second opinion.

**Search.** `recto search` looks at each page's text in order, ignoring case and line breaks: at most 200 hits and 30 s, stopping only between pages so `next_page` always moves on. A file with a finished corpus is read from that, and any other is read through one worker at a time, and asked to be indexed for next time. `route` says which, `index.note` says why in words, and `--scan` reads the pages regardless, for checking one against the other. **Three kinds of search,** over the same text `text` gives, each with the same hits, flags and coverage, and the skill says when to use which. Snippets are built only for hits that will be shown, and the count stays whole. `coverage.hits_total` counts every hit in scope past the limit too, which only a corpus makes cheap, so reading page by page gives null there once it stops, with `hits_at_least`.

**`--regex`** runs a pattern, by ripgrep's engine in this process (owner, 2026-11-07, in `SPEC.md`): `grep-regex` over the page's text in memory. **No program is ever started,** so nothing like `rg --pre`, which runs text from a PDF, can happen, and a test holds the source to that. It's the normaliser's text as it is, so lines stay lines: `^` and `$` go by lines, `.` stops at a line's end and `\s` doesn't, so `force\s+majeure` finds the phrase across a break, which a plain `rg` wouldn't. Case is ignored like any other search, and `(?-i)` turns that off. A match of nothing isn't a hit, and at most 400 characters of a match are shown, since a pattern can match a whole page. It's the crate's limits that bound a hostile pattern: 1 MiB compiled, 2 MiB of matching state, 64 levels of nesting, 1 KiB of pattern, and past those it's refused, with `pattern_too_large` or `bad_pattern`, exit 1. The engine has no look-around or back-references, so its time grows with the pattern times the page and doesn't explode. **Its time is bounded, in two parts.** The engine restarts a pass for every match, so a pattern that matches over and over on one page goes quadratic: `\w+\d|\w` took 37.6 s on 512 KiB of `a`, and `(?:a|b|...|j){1,3000}\d|.` 7.2 s. Those stop at the search's deadline, since there's a look at the time between matches, empty ones included, and the page goes in `failed_pages` and `pages_a_pattern_ran_out_of_time_on`. One pass can't be interrupted, so that part is bounded by size: **a page past 128 KiB of text isn't run over,** which the longest of bench100's 5,872 pages, 11 KB, isn't near, and a plain search still reads it. The worst single pass found under the limits is then 3.5 s on 128 KiB, `[a-z]{1,3000}\d` on `a`, at load about 30 (`examples/regex_worst.rs`, with `[size-limit] [page-bytes] [deadline-ms]`), against 25 s at 512 KiB. So **a search with a pattern goes at most about 3.5 s past its 30 s,** on what was tried. That's the worst found, not proved: the engine's guarantee is its states times the bytes, which at these limits is about 10 s by arithmetic. It holds one of the two draw slots meanwhile. It's listed in `pages_too_long_for_a_pattern` if it's over the cap. **What it holds in memory** goes beyond the 2 MiB of matching state, since the engine's other strategies aren't under that limit: the whole `recto` process on NASA, with reading all 383 pages, peaks at 6.1 MiB for a plain word, and 6.3 to 10.3 MiB for patterns, the largest for `(?:\w+\s*){1,20}\d`. On a page at the cap, the most found was 11.6 MiB, whole process. The limits do refuse some ordinary-looking patterns, since `\w` is a large class: `(\w+\s+){30}` and `\w{1,1000}` are refused, and `(\w+\s+){1,5}` isn't.

**`--rank`** puts pages in order by BM25, `recto_index::rank`. **It needs no index and no more disk:** one pass over the pages gives each word's count per page, each page's length and how many pages have each word. In memory, it holds numbers for the pages with any of the words, 8 bytes a page and 4 a word, and no text. **At its worst,** 200,000 pages with all of 16 words each (`examples/rank_worst.rs`), that's 14.4 MiB by arithmetic, and the whole process peaks at 68 to 70 MiB in about 1 s, against 65 MiB for opening a file of that many pages by itself, since opening's peak has passed by then. Then the top pages, 10 if not told, are read again for one snippet each. Words are runs of letters and digits, lower-cased, so `data-driven` is two. Each Han, Hiragana or Katakana character is a word by itself, since those are written with no spaces, so `数学` counts `数` and `学` wherever they are. Greek's final `ς` counts as `σ` and `İ` as `i`, for plain searches too. A pattern goes by the engine's own folding, which has both sigmas, and a pattern `istanbul` doesn't find `İstanbul`. **What's weak:** no stemming, so `liability` doesn't count `liabilities`. No folding beyond case, so `cafe` misses `café`, and a decomposed `é` breaks a word in two. Thai and the like, with no spaces, come out as one long word per run. A document can stuff a word to rank first, which nothing here can stop: more of a word stops counting for much, so it gets first place and no further, and the page's text stays under `untrusted`. The answer says it isn't every hit, gives no `hits_total`, and never calls the score anything but a count of words.

**Added files in search.** Every hit says `from_added_file` and `source_page`, whatever they are, and one from an inserted PDF also says `added_file` under `untrusted`. Plain output says so only when it isn't the number shown. Plain output also opens with what it covered: hits shown, pages really read of how many, how many couldn't be read or had no text, and whether there's more. `pages_searched` counts only pages read, and "Nothing found" isn't said if any page couldn't be. An agent read past "stopped early" at the bottom. That stays at the bottom too, with where to go on from.

**Hidden text in search:** only a page with a hit is drawn to check it. Drawing every page costs too much for what it adds, since a page with no hit is never read: rfc9110, 194 pages, went from 1.14 to 3.2 ms a page, and NASA's 383 pages from 3.5 to 16 ms a page (release, this Mac, 3 runs each, `recto local F search zzzqqqxx`, with the check switched on in code for the second). Each hit says `hidden_text: { checked, flagged }` and `page_has_tag_chars`. `overlaps_hidden` says whether its own words include hidden text, so a page's flag doesn't fall equally on the innocent hit beside them: `true`, `false`, or `null` if that can't be said. That needs nothing more than the draw a hit already pays for.

**Characters past 16 bits.** A font's ToUnicode gives these as two halves, and PDFium reports each as a character. `recto-render` joins them, or an emoji is lost and a tag character, the plainest hidden instruction there is, never raises its flag.

**Files that change.** A tab, and each PDF added to it, keeps the size and modification time its page numbers were recorded from. If an added file, or an edited tab's own file, has changed or gone, `text`, `render`, `contents` and `signatures` refuse with `source_changed`, and `search` lists those pages as failed and names the file. An unedited tab has no numbers to get wrong, and reads the file as it now is.

**Edits and pages.** Every edit's answer starts by saying what it did (`did`), in plain output too: "Rotated page 34 by 270 degrees. 34 pages now, 34 in the file." `tabs` and `where` give each tab's `pages` with edits and its `file_pages`. A tab's place follows the page it's reading, and if that page is removed it lands on the nearest and says so once. A draw's note goes when the page order changes. Page numbers on every command mean the document as edited: `text` reads the page now in that place, from whichever file it came from, and says `source_page` and `from_added_file`. `render` doesn't show an unsaved rotation, and says so in `unsaved_rotation_degrees`. Deleting a page is `Control` rather than the report's `Full`: nothing reaches a file, and it can be undone. The two-step plan and confirm belong to `save`, when that exists.

**Stack depth in the session's own process.** The structure reader runs in the session, where an overflow would abort it, unsaved edits and all, and `catch_unwind` can't help. lopdf's fork already stops at 100 levels of nesting, 4 MiB an object and 256 levels of page tree, and our own walks keep explicit stacks. Arrays and dictionaries nested 1,000,000 deep, page trees, outlines, field trees and name trees 500,000 deep, object streams, and chains of 100,000 `/Length` references and `/Prev` sections all returned on a release build, through `facts`, `contents` and `signatures`. `crates/recto-core/tests/deep.rs` keeps these at 100,000 on a test thread's 2 MiB in debug. **For the fork, not changed here:** a `/Prev` chain has no cap, and 100,000 sections in an 8 MiB file take about 4 s to open, in proportion, with no lock held and no thread lost except a job's. `IndexedReaderOptions` could take a maximum number of sections.

## Fuzzing

**One check per thing that takes hostile input,** in `crates/recto-fuzz/src/targets/`, a plain function on bytes. `tests/smoke.rs` runs each on stable with a fixed seed and a mutator that needs no crate, so every `tools/check.sh` runs them, and a failure repeats on any machine. `fuzz/`, outside the workspace, runs the same functions under libFuzzer, on nightly. `tools/fuzz.sh --seconds 300 [target ...]` builds and runs them, each under the heavy lock and releasing it between targets, keeping its corpus and any crash in `target/fuzz-work`. A longer campaign is the same with `--seconds 3600` overnight, eight hours in all, since a run picks up from its corpus. Each target's whole log is in `target/fuzz-work/<target>.log`, and the build queue won't run a command again on the same code after it fails, so a rerun after a crash takes `HEAVY_RETRY=1`. `RECTO_FUZZ_ROUNDS` and `RECTO_FUZZ_SEED` run the stable loop for longer, with no coverage feedback, if nightly isn't to hand.

| Target | What it runs | What must hold |
|---|---|---|
| `pdf_bytes`, `pdf_tree` | `inspect`, `signatures`, the sidebar and `contents` on mutated real PDFs, and on PDFs built from the bytes with a true cross-reference table | Returns, within 30 s and 512 MiB. Caps hold, text is clean, "none" only said of what was read |
| `proto` | Every decoder and validator, and `FrameReader` on a real channel | No allocation before the bytes arrive, decode and encode agree, a reply that differs from its job is refused |
| `index` | `repair_line_order`, `read_page`, `normalize`, `hidden_report`, up to the wire's 2,000,000 characters, with NaN, infinities and huge boxes | Only whitespace is added or lost, offsets in bounds, within 60 s |
| `agent` | JSON lines and command lines through `parse`, `parse_cli` and `execute`, selectors, page specs, level files | Caps hold, what the CLI builds the socket takes, a tab's name doesn't reach Off |
| `control` | Bytes from a client to the real server on a real socket | Every answer is a line of JSON, no job panics, `status` is answered, and the next client gets in |
| `record` | Bytes as a main record, a journal and a log of places, as they are and with their checksums made good | No panic or bomb, caps hold, and what's accepted is restored, undone and redone all the way, and written back the same |
| `edits` | Random steps by the owner and by agents through `execute` at Control, against a plain model | The order is the model's, undo inverts, `is_edited` means it differs, no owner's step is lost below Full, caps hold |

**What a hostile page costs in the normaliser.** At the wire's 2,000,000 characters, each with the hyphen flag, a read took 5.2 s and takes 64 ms (release, without LTO, this Mac, one run on the page the `index` target found): only the first 4,096 markers on a page have their words looked at, and the search for a page's own spelling reads at most 32 MiB. Neither is near a real page: all of bench100 has 13,924 markers across 5,872 pages. Past the first cap a hyphen stays a hyphen, which on such a page is no loss.

**A hang or a bomb is a failure.** `recto_fuzz::guard` counts every allocation in the process, ends it past 1 GiB, and holds each check to its time and memory. A fuzz build has debug assertions and overflow checks on, and the default sanitizer is none, for speed: everything here is safe Rust but the OS seam, and `FUZZ_SANITIZER=address tools/fuzz.sh control` covers that. **An open question:** under that sanitizer with libFuzzer's leak check on, two runs ended with the server not answering a new client, on a different input each time and not on replay. With the check off, which is what `tools/fuzz.sh` now does, two runs didn't, and no run without the sanitizer has. So the leak check is the likely cause, which isn't proved. `select` holds hit-testing, ranges and copies to the same on hostile characters, boxes, frames and pointer sequences, and goes through the page view's `Selecting` with text arriving or failing at any moment and a copy under way. **Not covered:** PDFium, which runs in a worker that can be killed. The search corpus's reader in `recto-index` and `recto-indexer`, which came after these targets and need one of their own. `recto log`'s reading of the log files, which only this user's processes can write. The fork's `/Prev` chain, noted above, which is slow in proportion rather than a hang.
