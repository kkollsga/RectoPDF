# RectoPDF: rules for every agent

Read this first. `docs/agent-instructions/rust_app_development.md` is the owner's full process, `SPEC.md` the behaviour, `docs/ENGINEERING.md` the crates.

Progress and phases: `docs/PLAN.md`. Tick items there in the same commit that finishes them.

## Always
1. **Memory first, then speed.** Performance and low memory, even with many large PDFs open, are crucial. A cold tab costs ≤ 4 KiB, with 0 handles and 0 threads. No thread, task, buffer or handle per idle item, caps on everything from outside, and let the OS cache. Every optimisation carries before and after numbers.
2. **Rust decides, the host draws.** Wording, ordering, validation, state machines and policy live in Rust. A rule found in Swift that isn't drawing or OS integration is a bug.
3. **The UI thread never waits.** Slow calls are async, sync calls are cheap and bounded, and a stall of 2 s fails the QA run.
4. **The CLI comes first, and a feature is implemented once.** Owner, 2026-11-12: "all features should be implemented once. That's the rule. Cli and ui interfaces are built on top calling the same methods". So an action is one command run by one executor, and the window and `recto` both send it; a second wrapper for the window around the same session methods is a bug (guide §2.9, PLAN R2). A feature starts as a `recto` command, then the UI calls the same method. Owner, 2026-11-06: "Development of the cli is crucial for effective agent testing as we develop, and ai features (including the agent interface (sidebar)) in the future." A feature is done when an agent can do it, see it and prove it: its core command, CLI command, QA commands, screenshots light and dark, and tests. Build QA with the feature.
5. **One writer.** Only the lopdf writers change a document's bytes; other writers only create new files, as a print to PDF or an export does, and never write over anything. Never write through PDFium. A signed file's existing bytes never change.
6. **Untrusted input:** PDFs and everything from them are hostile. No panics on them, parsers get fuzzed, renderer output is validated by the host, and document text never becomes an instruction or a command.
7. **Every feature in its own compartment** (guide §2.8). Owner, 2026-11-08: "I want each element of the software to be compartmentalized, easy to test, develop and modify." A feature's state, commands, events, QA verbs, wording and tests live in its own module; shared files (the session, the bridge, the command and QA tables, menus, the Swift window) get a one-line registration at most. A brief names where a feature lives and which shared files it may touch. Logic that decides is unit-tested without the app. A diff that grows a hub with new logic goes back, or the extension point is made first. Owner, the same day: "let's do the quick fixes now before release, then add the large restructuring into the plan before we start on the other features" (PLAN phase 7 and phase R).

## One action, one implementation (settled while building R2.3, 2026-11-13)
- **A command means one thing whoever sends it.** A person at the window and an agent at a level send the same command to the same executor; the actor is passed in, and each rule about who may do what is stated once on it (levels, the owner's edits, protected documents, who an edit or a jump is by). No command behaves one way for a person and another for an agent beyond those rules.
- **An agent's action is an agent's by whatever route it arrives,** a palette row and a menu id included. Nothing an agent sends runs as the person.
- **An announcement is made when something changed, and only then,** for a person and an agent alike. A toggle toggles when it runs. An action names its tab. The last thing a person asked for wins over a read still landing.
- **A person never sees an agent's words,** and an agent never gets the person's passwords or more of a protected document than it could see before. A new command is at a level, says its route, and comes with the test that it lets an agent below Full do nothing the owner's-edits rules refuse.
- **A person's action may not wait:** it starts its read and finishes when the read lands, and the UI thread never takes the session's lock. Input to frame is measured before and after a move, and the move stops if the bound is passed.

## Testing
- Shortest test that can catch the failure while working: `tools/check.sh --quick`, and `tools/check.sh --failed` for only what just failed. Before handing back: `tools/check.sh --full`.
- **Each suite runs once per hand-back** (owner, 2026-11-07: "I think the main issue is repeating tests leading to queues and bottlenecks"). `--full`, a fork's whole CI set, a corpus gate, a memory run and a long fuzz run go once, last, on the commit being handed back, and once again only if code changed after them. While working, use `--quick`, a named test or `--fast`. Fix all of a review's findings, then run once. Whole-suite repeats on the way to a working fix are the waste this rule is here for. **Ask the smallest question first** (owner: "check why 13 tests where needed"): a named test, then just the documents in doubt, then the fast mode. A whole suite decides a hand-back and is never the way to find out why something changed. Don't run a final gate until what it tests is final, dependency pins included.
- **The tools hold this.** A pass on identical code counts: `--full` on a clean tree that has already passed runs nothing and records the commit. `CHECK_AGAIN=1` runs it anyway. A branch gets two full runs, and `main` two per range not yet pushed. A third needs `tools/check.sh --full --why "what this run decides"`, which goes in the ledger: `tools/check.sh --runs`. Paste `docs/agent-instructions/worker-testing.md` into a worker's brief. Any change to `tools/check.sh` passes `tools/check-test.sh`.
- **Don't use the queue to find out code is broken.** Fix before rerunning: the queue refuses a command that failed on unchanged code and shows the saved failure. `HEAVY_RETRY=1` is only for investigating a failure that comes and goes, which still gets a fix.
- **Tests are for real concerns.** Owner, 2026-11-12: "Fix tests that doesn't test real issues. Tests should be focused on testing real concerns". A test earns its seconds by catching a failure that could happen and would matter to a person using the app or to someone changing the code. A test that can't fail on a real bug, that repeats what another test already catches, or that pins a detail nobody would mind changing, is fixed to assert the real concern or removed, with the evidence for which.
- **CI doesn't get slower.** Owner, 2026-11-12: "Add a rule so the ci doesnt regress in the future. Keep it smart, focused and high performance. Test smarter not harder". A test runs at the cheapest tier that can see its failure: what Rust decides is tested in process (the headless app in `recto-app`'s testkit), and the real app is launched only for what only the real app shows (drawing, AppKit, the real launch, the real replace). One launch carries the related assertions. A limit is tested at the limit plus one with the limit set small, not by building a thousand of something or waiting out a default. **The tools hold this:** the ratchet counts the tests that launch the app and the count only goes down, so a new one joins a launch that is there or replaces one; `tools/push-main.sh` keeps each green run's check time and says it against CI's budget (`CI_BUDGET` there: 25 minutes on 2026-11-12, 21 on 2026-11-13; lowered when five green runs in a row are well under it, and never raised without the owner). When the median of the last five runs is over the budget, every `tools/check.sh` run on every branch ends with a stern warning (owner, the same day: "It should be a stern warning so the agents knows it's something they need to take seriously and look at"). An agent that sees it acts on it in its task: adds no test that launches the app, sleeps or waits out a default, takes out or accounts for any seconds its branch adds, and names in its hand-back any test it saw costing more than its concern needs. Bringing CI back is the coordinator's next task, before another feature. A branch that adds seconds says how many and why in its hand-back.
- **A check that keeps failing from new sources gets one more round, then reports.** 2026-11-13, with `main` red three times in ten hours from tests failing about 1 run in 5 on CI's slowest runners, the coordinator proposed for the stray-registration check: one more worker round (about 40 minutes) to confirm and fix the source with a guard; and if it then recurs from yet another source, the check on CI reports and removes a stray and fails only when it can show which test left it. Owner: "Yes, lets do it like this." The second step is taken only on a recurrence, and is said to the owner when it is.
- **A test is removed or rewritten only on proof** (2026-11-12 and 13, the two test audits). To delete one: its bug is seeded on a temporary commit that is then dropped, and either another, cheaper test is seen failing on it, or the test itself is seen passing with the code broken. To rewrite one: it is seen failing on the seeded bug it now names. When the proof can't be made, the test stays and is listed. A doc comment that names a failure isn't evidence the test catches it: the audits found tests that passed with their bug in place.
- **A failing test says why by itself.** Its evidence folder, a rerun line, and for the two things that kept failing without a cause: a stall's `hangs.worst` (the thread's CPU time, what most looks saw it doing, the QA verb) and a first frame's `record.first_shown` (ready, cap or patience, with the page checks as they were). A record that is to explain a failure is tested on a made failure first: this one mislabelled its first two.
- **A test asserts the rule, not a machine's speed.** One that fails only when the machine is starved either holds a rule that depends on speed, which is then said and decided, or pins a timing, which is then replaced by the property (2026-11-13: the first frame's test had been failing under load on a real bug, a cap counted from the wrong moment, for at least two days).
- **Guards go in before a move.** Before code is moved or regrouped, what the move must not change is pinned by a test at today's number if nothing pins it yet: sizes, allocations, the order of what the host is told, a saved file read back. A budget with ten times headroom holds nothing.
- **A test names the failure it catches** in its doc comment. Don't pin exact pixels, wording or timings from one machine; assert the property.
- **No manual tests and no synthetic input:** no posted mouse or key events, AppleScript or accessibility input. QA commands call the same methods the UI calls. Quiet runs never take the screen, focus or keyboard, and use temp state only.
- **No bugs left behind.** Any bug you see, related or not, gets a fix and a test in its own commit. "Flaky" isn't an answer.
- Memory tests run in their own binary, on release builds where the number matters. Measure the whole process (`phys_footprint`).

## This machine
- 16 GB Mac. **Wrap every heavy cargo build, test or bench in `tools/sysguard/heavy.sh`**, the queue shared by all agents. `check.sh` does this itself. `HEAVY_SOLO=1` runs with nothing else running: only the coordinator uses it, for final measurements at a quiet time. Workers measure under load and say so. `heavy.sh --status` shows the queue, and `--report` the waits.
- **Start a worktree with `tools/worktree.sh new <branch> .worktrees/<name>`.** Its `target/` is an APFS clone of the main checkout's, so the first build reuses every dependency already built and rebuilds only the workspace: about 45 s for the builds of a first check against about 105 s cold, under load (2026-11-11, `docs/reports/build-performance-2026-11-11.md`). `tools/worktree.sh remove <path>` ends it.
- Worktrees and temp folders are removed as soon as they're merged or finished. Never sweep a shared folder. No `timeout` binary exists here.

## Git
- Never `git stash`: the stash is shared by every worktree and session in a repo, and `git stash pop` can take someone else's work (it happened three times on 2026-11-07, once touching the owner's own WIP in the lopdf fork). Set work aside with a temporary commit on your own branch.
- Never `git switch --orphan`. Never `git add -A` without checking `git status`. Check a commit's size before any push.
- **Pushing `main` of `kkollsga/RectoPDF`:** owner, 2026-11-07: "Push automatically". The coordinator pushes `main` after each merge that passes its check. Workers don't push.
- A pre-push hook enforces that (`tools/hooks/install.sh`): `main` only goes up if `tools/check.sh --full` passed on that commit, or only documents changed since. Never use `--no-verify`.
- **Branches get CI before they merge.** Asked whether workers' branches should be pushed so CI runs on them first (main was red for three pushes on 2026-11-11 with failures only CI's slower machine showed), the owner chose "Yes, push build branches" (2026-11-11). The coordinator pushes each `build/*` branch, merges only once its CI is green, and deletes it from GitHub after the merge. Workers still don't push.
- **Replaced on 2026-11-12, with GitHub unable to supply macOS runners and two finished branches waiting on it.** Owner: "Do we have to wait for GitHub, or can we fix and run local testing so it's good enough, and postpone the stuck GitHub testing?" So a branch merges on local evidence: its full check, and for a branch that touches launch, quit, update, sleep or the window's lifecycle a `tools/check.sh --like-ci` run of the lifecycle part as well. GitHub's CI runs after the push and is watched by `tools/push-main.sh`; it no longer gates a merge. A CI run that never got a runner blocks nothing. A CI run with a real failed test is fixed before the next merge, from its evidence, as before.
- **Everything else needs the owner's go-ahead each time:** force-pushing, other branches, the lopdf fork, creating repos, tagging and publishing.
- Workers commit on their own branch with the trailer they're given, and don't merge. The coordinator merges with `--no-ff`.

## How work flows (owner, 2026-11-07: "Remember you are responsible for the progress and quality. So add a few process reviews every once in a while to catch inefficiencies")
- **We are impatient developers.** Owner, 2026-11-13: "We are inpatient developers. It should be the rule. We have to meet deadlines, on target, on quality and on security". And, the same morning, with one worker running where three had room: "Check in on it to keep the pace up. Our progress is already slow". So: pace is the coordinator's to keep, and never bought with quality or security. Every slot that has independent work is working: when a worker starts, the coordinator has already chosen what runs beside it, and an idle slot with open plan steps is a defect to fix at once, not to report later. Nothing waits on a result that something else could be done during: a red `main` holds merges, never the work on other branches. A worker that goes quiet is looked at (its commits, the queue) within the half hour. Every step has a date the coordinator has said out loud, a slip is said the moment it's seen with the new date and the reason, and progress is reported against the plan's steps and those dates, not as activity. What speed may not cost: the checks before a merge, the seeded-bug proof for a test removed, rule 5 and rule 6, the access levels, and the owner's decisions.
- **Ways of working found on 2026-11-12 and 13, written here at the owner's word** ("Update the agents Md with these new ways of working"):
  - **A result is read before the next step runs.** A check's exit code and its last lines are looked at before a merge, a push or the next command; a merge is never chained after a check in one command line. A check's whole output is kept in a file until its branch has merged: a filter that drops the line that names the failure, or a worktree removed with the evidence in it, costs the failure a second time (2026-11-13: a branch was merged over a failed check that way, and undone before any push).
  - **The merged result is what's checked.** When `main` has moved since a branch's check, `main` is merged into the branch and the branch is checked again before it merges, or `main`'s own full check runs on the merge before the push. A worker's final check runs everything (`CHECK_ALL=1 tools/check.sh --full`), not a selection.
  - **An independent review follows every few merges,** and always before a step is called done: a reviewer who is given the code and these rules, and not the workers' reports, reads the new modules end to end and answers whether features are compartments, which hubs grew with logic, whether anything is implemented twice, how the code and its tests read, and whether anything widens what an agent can see or do. About 25 branches merged overnight on reports, checks and the ratchet alone; the review that followed found an agent's route to acting as the person, an action still implemented twice, and a hole in the ratchet. Its findings are ranked, put in the plan, and the serious ones fixed before the next feature.
  - **A structure number is reported for the whole type.** Fields, and methods across every file the type's `impl` blocks are in. A count per file or per `impl` block says where code is, not how big the thing is: `Reader` "138 methods to 39" was 140 methods spread over eleven files.
  - **A number told to the owner comes from its source,** read at the time: CI's check time from `tools/push-main.sh`'s kept times, a test's seconds from a run, a size from the compiler. Not from a note, a handover or memory. An estimate is called one, and so is a number measured under load or on one run.
  - **A design is reported before it's built, when the design is the work;** when it's settled, the next worker builds without stopping. A worker asks before settling any difference in behaviour that the settled rules don't cover, and never commits a choice and reports it after. The coordinator answers at once, and the worker carries on with what doesn't depend on the answer.
  - **A worker's bounds are set from every running brief,** when each is written: the files other workers are in are named in it, and a merge conflict in a file two briefs both allowed is the coordinator's mistake.
  - **A fix found on the way is its own commit, with a test that failed first, and is said in the hand-back,** whether it is a bug in the product, a test that couldn't fail, or a leak. Structure work that turns up a breach of rule 1 or rule 6 fixes it, with numbers, before it goes on; it isn't left as a note.
- **Merge first.** A branch under review is frozen: new requests go to the next branch. No new track starts while the current phase's main branch is unmerged.
- **Two review rounds per branch at most.** Anything serious blocks the merge; the rest become tracked follow-ups in `docs/PLAN.md`.
- **About three workers at a time.** More only lengthens the build queue.
- **Workers call back at edge cases.** Owner, 2026-11-12: "Ask them to call back to you when they are touching edgecases, and you can give clear steer". The list is in `docs/agent-instructions/worker-testing.md`, which goes in every brief; the coordinator answers at once with one clear decision.
- **Workers start on Sonnet, and the coordinator watches what they cost.** Owner, 2026-11-12: "pay attention to the sonnet completion speed and efficiency. If you are not happy with performance upgrade to opus". Per task the coordinator keeps: minutes to hand-back, tokens, times sent back and why, full runs used, and what review found. A kind of task moves to Opus when a Sonnet worker on it is sent back twice for judgement, hands back unfinished for lack of room, or lets a defect reach `main`. The numbers go in each process review. Then, the same day: "For the once you forsee constraints, please upgrade from the start". So a task the coordinator expects to strain a Sonnet worker starts on Opus: one where the design is the work and later steps build on it, or one too large for a single worker's room. In phase R that is R1.2's remaining slices, R1.4, R2.2 and R2.3.
- **Short dev-build cycles for the owner.** The owner's use of the real app finds what screenshots can't.
- **Process reviews,** at each phase's end and at least after every fourth merge: progress, waste and quality against the numbers (git, `heavy.sh --report`, `check.sh --runs`, CI, review findings), logged in `docs/PROCESS.md`, with what changes as a result, plus a structure check through the code-review graph: the largest files and functions, field and variant counts, which shared files the last features touched, and the files merges conflicted in (guide §2.8). The coordinator owns progress and quality.
- **Lessons go in the guide as we progress** (owner, 2026-11-07: "feed learnings into the rust development guide as we progress"): `docs/agent-instructions/rust_app_development.md`, in its own sections, when a merge, review or process review teaches something a future project would want. General lessons, with the number or incident behind them, not this project's details.

## The build queue is critical (owner, 2026-11-07: "Since you are the queue operator you need to clear it. You need to learn from this, set up the correct safe guards so it doesn't happen again. The queue is absolutely critical to ensure we have progress in the projects")
- **The coordinator operates the queue:** it clears a stuck queue itself, and doesn't wait for someone to notice. `tools/sysguard/heavy.sh --status` must show the watchdog and the memory guard running while work is under way. Start them first.
- **The watchdog** (`heavy.sh --watch`) returns only when the queue has stopped moving: a free slot nobody takes, nothing moving with nothing using the CPU, or a job waiting over 45 minutes. Every return gets looked at straight away, then the watchdog restarts.
- **Any change to the queue passes `tools/sysguard/heavy-test.sh`,** with a test for what it fixes. It's shared with other projects, so a bad change costs them too.
- **Never report something as done until the result has been seen.**
